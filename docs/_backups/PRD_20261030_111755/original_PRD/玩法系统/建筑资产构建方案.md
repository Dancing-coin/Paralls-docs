### 0.1 稳定身份与对象映射

`building_id` 是建筑的稳定数据身份，不等于文件名、资产名或 Actor 名。视觉体、逻辑体、Level Instance、Packed Level Actor、HLOD 代理和登记 manifest 必须通过同一个 `building_id` 关联；`SM_`、`LI_`、`PA_`、`LC_` 只表示对象类型。

一个里是逻辑和流送的所有权边界，不要求一个里只能有一个运行时包。一个里内部可以拆成 8—15 个近层 Level Instance/PLA；这些包共享里级边界和建筑 ID 清单，不能把边界拆到每栋房门口。

每个资产包至少要能追溯到：`asset_id`、`building_id`（非建筑资产可为空）、批次、依赖资产、源文件、导出文件、UE `/Game/...` 路径、验证证据和回退版本。字段定义以[资源 manifest 模板](../../art_resources/asset_manifest_template.yaml)为准。

下游必须继承本文件的实体盒厚度、Slot 0/1/2、L1 裸接口、HLOD 参数、FastGeo 配置、OFPA 外部文件、Data Layer、NavMesh 切换和自动检查，不得在场景文档重新解释。

## 一、范围与规范基准：不再论证，只作为执行前提

| 指标 | 锁定值 |
|---|---|
| 城墙内面积 | **90 万 m²**（950m × 950m） |
| 含城墙城壕 | 约 **1.2 km²** |
| 完整场景边界 | 约 **2.5 km²** |
| 户数 / 人口 | **11,000 户 / 约 50,000 人** |
| 可进入建筑/单元 | **8,000+** |
| 里数 | **约 18 个里** |
| 官寺核心建筑 | **10—15 栋** |
| 市垣列肆 | **60—120 间** |
| World Partition Cell Size | **64m**（城内密集城市核心区） |

Cell Size 的选型依据：64m 是**密集城市环境**的标准选择，优点是流送粒度细、单 Cell 内存低，代价是 Cell 数量多、加载操作频繁。你的县城是 950m 见方的高密度建成区，128m 或 256m 会让一整个街坊的资产在同一个 Cell 里“同生共死”，流送粒度不足以支撑“走进一条巷子只加载这一小片”的需求。

**三条模块宪法**：

1. **网格**：100cm 基本单位，400cm 主模块；门洞宽 100/180/240cm；层高 300cm。
2. **枢轴**：**底部后左角（Bottom-Back-Left）** ，落在网格点上。中心枢轴是“每个角落 1cm 裂缝”的根源。
3. **纹素密度**：标准件 **512 px/m**；近景交互件（门、案、井栏、市楼栏杆）局部 **1024 px/m**。

**几何策略**：所有墙、地、屋顶为**实体盒**，墙 20—30cm，地面 10—20cm，屋顶坡面 15—25cm。槽0 = 外侧/顶面，槽1 = 内侧/底面，槽2 = 切面/收边。不做单面平面，从室内和室外看是同一块几何体。

**联网预留契约（当前只做组织方式，不做网络代码）** ：

- 每栋 L2 建筑拥有**全局唯一建筑 ID**，格式 `BLD_<类型>_<县域编号>_<序号>`。
- 每栋建筑拆分为**逻辑体**（进入判定包围盒、门洞局部坐标、可交互锚点列表）和**视觉体**（网格、材质、陈设）。逻辑体不依赖视觉网格存在。
- 流送边界处记录该区块内所有建筑的 ID 列表。后期服务器用同一份列表做兴趣管理，视觉资产永远不跨服传递。

## 二、资产五层详细设计

### L0 基础构件层：唯一必须锁死规范的层

**定位**：L0 是整套县城语法的字母表。制作优先级是可拼接、可检查、可自动验收；“不追求好看”只表示不在 L0 单件上做地标级独特设计，不表示采用 Low Poly 或简化风格。所有可见建筑仍须达到[场景素材需求](06-召陵县第一阶段Demo场景素材需求.md)规定的汉末写实比例、构造和材质基线。L0 的枢轴或纹素密度任何一件不合格，都会在 L1—L2 阶段被放大为满城裂缝和材质跳变。

**数量与分组：60 件基线，按地区和材质变体扩展至 60—80 件。**

| 子组 | 件数 | 核心内容 | 制作要点 |
|---|---|---|---|
| **L0-A 墙体** | 16 | 实墙（民居夯土 / 官寺包砖）、门洞墙（100/180/240）、窗洞墙（60/100/140）、半墙（院墙 200/150）、山墙（硬山/悬山）、内外转角 | 夯层用材质法线/顶点色表现，不做几何凹槽；门洞 Socket 在洞口中线底部 |
| **L0-B 地板与台基** | 10 | 素土/砖铺/木地板；台基 10/20/40/60cm；台阶一步/两步/三步 | 台基**顶面标高**必须与相邻地板件精确对齐；高差由 L4 台基边缘件收边，台基本身不“斜着糊” |
| **L0-C 屋顶** | 12 | 悬山/硬山/四坡坡面，草顶，正脊/垂脊，檐口（带/不带瓦当），檐下收边 | 坡面不参与行走碰撞；Socket `S_Ridge` / `S_Eave` / `S_Hip` 用于拼合 |
| **L0-D 框架与连接** | 12 | 柱（圆 200/300，方 200）、础石、横梁/顺梁、简化柱头托木、门框（单/双扇）、直棂窗框 | **不做精细斗拱**；县城大量建筑看不到近景斗拱，把顶点留给门窗和室内 |
| **L0-E 洞口收边与排水接口** | 10 | 门窗洞收边（覆盖墙厚方向）、地漏、墙基排水口、门槛、墙顶压顶 | **洞口用独立框件覆盖墙厚方向**，门窗框不直接“贴在墙面上” |

**L0 验收：盲搭测试。** 只用 L0 件，不手动微调，只靠 100cm 网格吸附和 Socket，完成三项：

1. **一间一堂二内**：4m×8m 或 8m×8m，堂在前、二内在后/两侧；180cm 角色胶囊可通行门洞；窗洞从室内外均有框件收边；屋顶与山墙 Socket 闭合。
2. **一段巷道 + 两侧院墙/山墙**：巷宽 250—350cm；院墙半墙与山墙形成连续界面；转角无漏光。
3. **一段官寺台基 + 正堂前阶**：台基 600 与砖铺地板对齐；三步台阶可走；240 门洞可通行。

**Editor Utility 自动检查**：枢轴是否在网格点、纹素密度偏差是否 ≤5%、碰撞是否为实体盒、Socket 命名是否合规。**L0 盲搭不通过，不进入 L1。**

---

### L1 房间单元层：可进入的最小空间，预拼装而非最终资产

**定位**：L1 是 L0 的预拼装产物，每一件是一个**完整闭合、可独立进入的最小空间**。L1 不承担“独特外观”的任务，它的价值在于**标准化接口**。

**L1 单元清单：约 9 类，2 个变体/类，合计 40—60 件。**

| 单元 | 尺寸 | 组成 | 变体 | 联网逻辑摘要（随单元打包，与视觉分离） |
|---|---|---|---|---|
| 民居一堂 | 4m×4m | 堂 + 前门 + 侧窗，堂南壁开放或帷幔 | 2 | 进入判定包围盒 4×4×3m；门洞局部坐标 |
| 民居一内 | 4m×4m | 内室 + 帘/隔断 + 小窗 | 2 | 包围盒；可交互锚点（席、几） |
| 一堂二内整体 | 4m×12m / 8m×8m | 堂 + 两内 + 院墙接口 | 2 | 组合包围盒；门洞列表 |
| 吏舍单元 | 4m×4m | 单间 + 门 + 窗 | 2 | 包围盒；案/架锚点 |
| 诸曹单元 | 4m×8m | 两开间 + 案/架锚点 | 1 | 包围盒；简牍架锚点 |
| 列肆单元 | 3.5m×6m | 前棚架 + 柜台 + 后仓储间 | 2 | 前店/后仓双包围盒；柜台交互锚点 |
| 仓廪单元 | 6m×8m | 高台基 + 厚墙 + 单门 + 粮囷锚点 | 1 | 高台基包围盒；粮囷锚点列表 |
| 狱舍单元 | 3m×3m | 厚墙 + 小门 + 高窗 | 1 | 紧凑包围盒；仅一门一窗 |
| 门屋单元 | 4m×6m | 门道 + 门扇 + 门亭 | 1 | 门道通行包围盒；门扇交互锚点 |

**L1 的关键约束**：**L1 不是最终建筑，不要给 L1 做“独特收边”** 。如果每个一堂二内都单独设计檐口和墙角，L2 组合时反而接不上。L1 的接口必须“裸”到可以被 L0-E 件统一覆盖。

---

### L2 完整建筑层：玩家会反复辨认和进入的地标

**定位**：L2 决定县城的“可记忆性”。玩家会反复进入官寺正堂、穿过城门楼、在市楼前辨认方向。**L2 精耕，L1/L0 保复制。**

**数量与优先级：30—50 件。**

| 类别 | 件数 | 优先制作 | L2 独有构件 |
|---|---|---|---|
| 官寺类 | 10—14 | 正堂、便坐、门屋、狱院、仓廪、武库 | 四坡屋顶、高台基、朱漆柱、阙 |
| 民居类 | 6—10 | 标准宅院、合院、排屋、里门 | 院墙组合、院内水井锚点、里门门亭 |
| 市类 | 4—6 | 市楼、列肆列、市门、市井亭 | 两层木地板、悬鼓、市门题额 |
| 仓储与公共 | 4—6 | 粮仓、社/祠、传舍、亭/邮亭 | 干栏/高台基、神主/祭台 |

**L2 与 L1 的关系**：L2 由 L1 组合，再加 L0 收边和 L2 独有的地标构件。**L2 不重新发明房间，只负责“把这些房间组织成一栋可辨认的建筑”。**

**L2 的 ID 规则**：每栋 L2 建筑获得全局唯一建筑 ID。这个 ID 必须写入逻辑体摘要，并通过 manifest 和结构化映射关联视觉体、Level Instance、PLA、HLOD 和登记表；它不等于这些对象的文件名或 UE 对象名。当前单机阶段，ID 只用于流送调度查表；后期联网时，ID 直接成为服务器兴趣管理的网络键。

### L3 簇与基础设施层：县城的骨架与流送单元

**定位**：L3 的核心产出不是网格，而是**围合、连接和流送边界**。

**四组内容：**

**① 城墙系统（20—30 件）** ：标准墙段 10m（夯土收分）、转角件、马面基座、雉堞段/无雉堞土垣顶段、城门（单/双门道，门洞 4—6m）、角楼基座、护城河岸坡、穿城墙排水涵洞。城墙碰撞是**连续实体**，几何由标准段拼接，碰撞对齐依赖 L0 枢轴规范。

**② 街巷系统（15—20 件）** ：主街路面 8m×8m、巷道路面 4m×4m、排水明沟（直线/转角/汇水口）、路缘石、石板小桥（2m/4m 跨度）。街巷路面件带**排水坡向 Socket**，坡向指向最近的排水沟或涵洞。

**③ 基础设施插入件（30—40 件）** ：水井（井台 + 陶井圈 + 可选井亭）、里门、市门、阙、街鼓/市鼓、拴马桩、排水陶管、地漏、院落排水口。吸附在骨架或区块网格点上，不单独流送。

**④ 流送打包规则（L3 最重要的非网格产出）** ：

- **里区块** = 该里所有 L2 民居 + L3 里门 + L3 里内巷道 + L3 水井，打成一个 Packed Level Actor / Level Instance。
- **衙城区块** = 衙城墙以内全部官寺建筑 + 衙城墙 + 望楼。
- **市区块** = 市楼 + 列肆列 + 市垣/市门 + 市井。

**流送边界放在里门处，而不是单栋房子门口。** 玩家穿过里门时整个里区块已在内存中；在里内巷道行走时，不会因为逐栋加载而 pop。

### L4 地面与地形层：落地、高差与城外过渡

**定位**：L4 解决“建筑不能悬空、街巷不能断头、城墙不能坐在无限平面上”。

**四组内容：**

**① L4-A 城内功能地面（20—30 件）** ：主街路面件、巷道路面件、庭院铺地件（带地漏 Socket）、广场/空地件、建筑基座周边散水件、路缘石。所有地面件**顶面标高必须与相邻建筑台基/地板标高对齐**；高差由 L4-B 过渡，不用倾斜地面件“糊”。

**② L4-B 地形衔接件（25—35 件）** ：台基边缘件（10/20/40/60cm）、挡土墙段（0.5—2m）、坡道（5%—15%）、踏步、排水坡件、城墙基槽件、城壕岸坡（30°—45°）。**每一个高差都由一个明确的件过渡**，建筑落地、街巷排水、城墙与地面关系全部可检查。

**③ L4-C 城外环境地面**：城壕外侧、城外道路、农田件、河岸/陂塘岸坡、城外关厢地面。大形用 Landscape 刷，功能性面层用 L4 件覆盖。**城门外的道路和桥必须与城门同步完成**，否则玩家出城即断。

**④ L4-D 地表材质层**：一个地面 Master Material 派生素土、夯土、碎陶、砖铺、草地、泥地、碎石、水底；Decal 层叠车辙、脚印、水渍、炭渣；城外大范围用 **RVT** 统一投影，消除 Landscape 与 L4 件交界处的材质跳变。

**L4 关键纪律**：L4 件覆盖区域内，Landscape 高度应**略低于 L4 件底面 5—10cm**，避免 Landscape 穿透模块地面。灰盒阶段用高度检查工具验证。

## 三、两级视觉流送详细设计

### 远层 Block Proxy：从近层自动合并生成，不另制风格化低模

**生成方式**：远层不要手工另做一套风格化低模。每个里/衙城/市区块的远层，直接从该区块的 L2 建筑和 L3 围合件**自动合并生成并按屏幕尺寸简化几何**；代理保留写实材质、主要轮廓和建筑类型识别，满足性能预算即可，不得回流替代近层成品。

- **HLOD 层类型**：选择 **Simplified Mesh**（合并后执行网格体简化）或 **Merged Mesh**（仅合并）。不要用 Instancing 层类型——那是给树木和枝叶用的，建筑需要轮廓正确的合并代理。
- **ClusterSize**：设置为 **500—2000 三角面**，让每个 HLOD 代理块的面数落在远层可接受的区间内。
- **Screen Size 阈值**：按距离递减，建议 **0.5 / 0.2 / 0.05** 三档，对应不同的减面比例。
- **MergeDistance**：**略大于流送距离**，避免远层代理与近层之间出现空隙。
- **天际线地标单独 Override**：城门楼、角楼、市楼、官寺望楼不参与街区的粗合并，单独设置 HLOD Layer Override，保证轮廓精度。

**远层流送**：在流送半径内**常驻**，作为近层未加载时的兜底视觉。HLOD 在 Cell 卸载后自动用代理网格替代原始内容，玩家在任何距离都不会看到“空洞”。远层不参与精细碰撞，不承担“进入”功能。

---

### 近层 Enterable Set：Level Instance 按距离带异步调度

**打包单位**：每栋 L2 建筑或每 3—5 栋相邻小建筑打包为一个 **Level Instance**。重复性最高的民居“一堂二内”，其 L1 单元可以直接做成 **Packed Level Actor**，在多个里区块中复用实例。

**关键警告**：**Level Instance 的高密度使用会增加流送运行时代价。** 社区反馈显示，大量 Level Instance 在游戏启动时可能被全部加载并迅速隐藏，造成启动峰值；编辑时 Level Instance 也无法在放置状态下流送。因此：

- **不要碎到“每一间屋子一个 Level Instance”** 。一个里区块内，近层建筑控制在 **8—15 个 Level Instance** 是合理密度。
- 用 **Packed Level Actor** 处理“多个 L0/L1 件组成的静态建筑”，减少 Level Instance 数量。

**距离带参数**：

| 距离带 | 行为 | 技术细节 |
|---|---|---|
| **40—60m 预加载带** | 异步加载该建筑/建筑组的 Level Instance | `Should Block on Load = false`；通过 Soft Reference + `RequestAsyncLoad` 发起非阻塞加载 |
| **15—25m 替换带** | 近层加载完成后，隐藏远层 Proxy 对应部分，显示近层 | 优先在拐角、门洞、墙后切换；无法遮挡时用 **0.1—0.2 秒 dissolve** |
| **60—80m 卸载带** | 卸载近层，远层恢复显示 | 碰撞从精细碰撞切回远层粗碰撞或关闭；导航局部重建 |

**加载风暴的抑制**：

- **每帧最大流送 Cell 数**：`wp.Runtime.MaxStreamingCellsPerFrame=2`（默认值），防止一次性加载过多 Cell 造成卡顿。
- **每帧最大 Actor Spawn 数**：配合上述变量限制，避免 Actor 生成尖峰。
- **速度自适应 + 视线扇形**：玩家骑马/冲刺时预加载距离按速度外推，但只加载**视线前方扇形区域**。
- **Fast-Geo Streaming**：如果使用 UE 5.8+，接入 **FastGeo** 插件。其 Cell Transformer 会在流送时将 Cell 内静态网格合并为 AutoInstancedActor，减少流送时的 Actor 数量。需要的配置包括 `FastGeo.Enable=True`、`FastGeo.AsyncRenderStateTask.TimeBudgetMS=1`，以及 `s.StreamableAssets.UseSimpleStreamableAssetManager=true`（必须放在 `DefaultEngine.ini`，不能只放控制台）。

**NavMesh**：远层用简化 NavMesh 兜底；近层加载后局部重建。碰撞切换在近层加载完成后执行，不在加载中途切换。

---

### 性能预算与监控指标

| 指标 | 目标值 | 监控命令/工具 |
|---|---|---|
| 显存峰值 | **8—10 GB** | `stat memory`；Unreal Insights memory trace |
| 纹理流送池 | 设为显存的 **70%—80%**，通过 `r.Streaming.PoolSize` 配置，**作为实测变量而非固定值** | `stat streaming` |
| 同时近层建筑 | **50—80 栋**（Level Instance 级别） | 自定义流送统计蓝图 |
| 每帧流送 Cell | ≤ **2** | `wp.Runtime.MaxStreamingCellsPerFrame` |
| Draw Call（近层场景） | 基线 ≤ **1500—2500**，通过 ISM/Packed Level Actor 压制 | `stat scenerendering` |

**Nanite 与 ISM 的配合规则**：对于启用 Nanite 的网格（L2 地标外壳、L0 高精度构件），**使用 ISM 而非 HISM**。HISM 的集群树裁剪在 Nanite 下没有意义，Nanite 自身处理裁剪和 LOD；ISM 的实例化开销更低。对于非 Nanite 的重复小件（L0 墙段、门窗框、家具），如果实例数在数万以上且大量在屏幕外，用 HISM；如果实例数在数千以内或需要频繁修改单个实例，用 ISM + Custom Primitive Data。

## 四、协作方案详细设计

### 工具链固定配置

| 项 | 配置 |
|---|---|
| 世界分区 | **World Partition**，城内 Cell Size **64m** |
| 协作核心 | **OFPA（One File Per Actor）** ，World Partition 下**默认启用** |
| 版本控制 | **Perforce**（OFPA 与 Perforce 集成最成熟；可用 UnrealGameSync 简化同步） |
| 实时协作 | **Multi-User Editing** 插件（关键联调阶段启用；需要 Perforce 和 UDP 消息配置） |
| 自动化检查 | **Editor Utility Widget / Python 脚本**，用于枢轴、纹素密度、命名、碰撞检查 |

OFPA 的本质是把每个 Actor 的数据存到独立外部文件，修改一个 Actor 不需要保存整个关卡。编辑器内的提交和同步是必须的，`ExternalActors` 和 `ExternalObjects` 文件夹必须纳入 Perforce 管理。

---

### 地理分工：按区块认领，Actor 级锁

| 角色 | 负责区块 | 不碰什么 |
|---|---|---|
| **A 美术** | 衙城区块（官寺正堂、便坐、吏舍、仓、狱、衙城墙、望楼） | 市、里区块、L0 基础件 |
| **B 美术** | 市区块（市楼、列肆列、市垣、市门、市井） | 衙城、里区块、L0 |
| **C/D 美术** | 各 4—6 个里区块（每个里约 60 户） | 衙城、市、L0 |
| **L0 负责人** | **唯一有权修改 L0 基础件的人** | 不参与具体区块摆放 |
| **TA / 关卡设计师** | 流送调度蓝图、远层 Proxy 生成规则、PCG 布局规则、自动化检查工具 | 不手工摆建筑 |

**OFPA 的锁粒度是 Actor**：签出只锁当前选中的那一个或一组 Actor 文件，不是整个关卡。两个美术可以在同一条巷子里摆不同的房子，只要不同时选中同一个 Actor。**绝对禁止两个人同时编辑同一栋 L2 建筑或同一个里区块的同一个 Level Instance。**

---

### 数据层辅助分工

在 OFPA 的地理分工之上，用 **Editor Data Layer** 做垂直分层：**美术层**（建筑、道具、地面）、**玩法层**（交互锚点、进入判定体、NPC 刷点）、**光照层**、**流送层**（远层 Proxy/HLOD 专用）。Editor Data Layer 本身不在运行时生效，但帮助团队分工和优化编辑体验。玩法层和美术层可以分给不同的人，互不抢 Actor。

---

### 提交纪律与自动化检查

**提交前先同步**，在编辑器内解决 Actor 级冲突。每个 L0/L1/L2 资产入库前跑一次 Editor Utility 检查：

- 枢轴是否在网格点；
- 纹素密度偏差是否 ≤5%；
- 碰撞是否为实体盒且闭合；
- Socket 命名是否合规；
- 建筑 ID 是否唯一。

对于里区块和 Level Instance，额外检查：流送边界是否闭合（玩家不会走进未加载的里）、远层 Proxy 与近层 Level Instance 的 ID 是否一一对应。

每个资产包入库前还必须检查：`asset_id` 与 `building_id`（如适用）是否稳定且唯一、源文件和导出文件 SHA-256 是否记录、依赖资产是否已登记、UE `/Game/...` 路径是否可追溯、当前状态是否有批准人和验证证据、替换版本是否保留回退目标。源文件和 `approved` 版本不得覆盖；替换必须创建新版本并更新依赖图。

---

## 五、制作路线详细设计

### 第 1 阶段：垂直切片（风险闸门，不通过不进入下一阶段）

**范围**：一个里（约 60 户）+ 衙城前院 + 市楼 + 一段城墙与城门 + 一块 2—3m 高差台地。

**只做**：

- L0 核心约 **20 件**（墙段、地板、屋顶坡面、门框、台阶、台基边缘）；
- L4 的 **3 种地面件、2 种台基边缘件、1 种坡道件、1 种挡土墙件**；
- L1 三个原型（一堂二内、吏舍、列肆）；
- L2 三座地标（官寺正堂、市楼、城门楼）。

**验证四件事**：

1. 建筑落地、街巷排水坡向、城墙基槽高度关系；
2. 远层 Proxy 与近层 Level Instance 替换无穿帮；
3. 快速跑动时加载队列不崩，`wp.Runtime.MaxStreamingCellsPerFrame` 限制生效；
4. 显存峰值、同时近层建筑数、纹理流送池在预算内。

**这一阶段跑通，后面 18 个里和几百个县城才只是“同一套语法的展开”。**

---

### 第 2 阶段：L0 完整化 + L1 原型全部通过

补齐 L0 的 **60 件基线**；只有在需要覆盖地区、材质或功能变体时，才扩展到 60—80 件。L1 全部 9 类单元做出原型，通过“独立可进入、网格闭合、接口可被 L0-E 收边”的验收。完成 L4-A 城内功能地面和 L4-B 台基边缘/挡土墙/踏步核心件。

---

### 第 3 阶段：L2 地标精耕 + L4-B 衙城台地

优先制作官寺正堂、市楼、城门楼、标准宅院、粮仓。同步完成衙城台地的挡土墙、坡道、踏步，把官寺放到抬高的台地上。**五件地标完成，县城就有了可辨认的核心区。**

---

### 第 4 阶段：L3 骨架 + L4-B 城壕岸坡/城墙基槽

城墙段、城门、角楼、街巷、水井、里门、排水沟与 L4 的基槽件、岸坡件同步制作。**城门外的道路和桥必须在这一阶段与城门同步完成。**

---

### 第 5 阶段：L4-C 城外环境 + 变体扩展

城壕外侧、城外道路、农田、河岸。同时在 L1/L2 原型基础上扩展变体：不同规模的衙城、单/双门道城门、带后院/不带后院的宅、不同物产的市肆。变体靠**材质实例、陈设组合和少量附加网格**实现，不新增结构语法。

---

### 第 6 阶段：全量铺设 + 自动化验收

用 PCG 或布局数据驱动，把“一个里”的模板复制到 18 个里、衙城、市。每个区块自动检查：流送边界闭合、建筑 ID 唯一且与 Level Instance/PLA/HLOD/逻辑体命名和映射对应、远层 Proxy 覆盖完整、依赖图无断边、manifest 字段齐全、性能预算达标。自动检查结果、导入日志、编辑器/PIE 截图和回退版本必须写回对应 manifest，登记表只做索引。

---

## 六、联网预留的底线检查清单

当前不做联网实现，但以下四条从第 1 阶段就必须成立：

1. **每栋 L2 建筑有全局唯一建筑 ID**，格式统一，写入逻辑体摘要和视觉体命名。
2. **逻辑体与视觉体分离**：逻辑体（进入判定包围盒、门洞局部坐标、可交互锚点）可以独立于视觉网格存在和导出。
3. **流送边界与建筑 ID 对应**：里区块流送边界处记录该区块内所有建筑 ID 列表，后期服务器用同一份列表做兴趣管理。
4. **跨服需要携带的数据被显式标记**：哪些状态需要落全局数据库（建筑进入状态、玩家与建筑交互记录），数据设计中预留字段，当前单机阶段留空但不删除。

---

资产五层解决“用什么拼”，两级视觉流送解决“什么时候拼和卸”，协作解决“谁在什么时候改哪一块”，制作路线解决“先做什么后做什么、在哪一步停下来验收”。L0 盲搭通过、垂直切片跑通显存与流送、远层从近层自动生成、建筑 ID 从第一栋开始全局唯一——这四件事做到，后面 18 个里、几百个县城，都只是同一套语法在不同种子和地形下的展开。
