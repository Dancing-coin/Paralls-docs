# 04-分水岭实验

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

**这是 v2 的验收实验。做不到，则 v2 不成立。**

---

<a id="claim"></a>

## 一、要证明的命题

> 在已打通的域上新增一个全新事实类型：**零 Owner 改动、零 runtime 改动、只加规则包。**

这句话是 [成功判据](../README.md#success) 的唯一形式。它把"支持多样玩法"从主张变成可测量的实验。

---

<a id="three-experiments"></a>

## 二、三个实验

按难度递增。前一个不通过，不做下一个。

### 实验 A：新增一个池（精神力）

**目标**：验证"加资源 = 加数据"。

**前置**：Inventory 域已完整打通（阶段 4）。

**步骤**：

```yaml
1. 规则包新增池定义
   pool_def: spirit@1
     bound: [0, 100]
     initial: 100
     integration: rate_based
     hysteresis:
       - enter_below: 20, exit_above: 30, state: exhausted
2. 声明 FactType
   fact:character:*:spirit
     primitive: pool
     owner_ref: Body
     visibility: { class: private }
     resolution_order: 25            # 由拓扑生成
     aggregation: none
3. 绑定消耗模型
   model_binding: spirit_cost_abilities@1
     applies_to: [skill:charge, skill:shout]
     cost_model: spirit_cost_v1
4. 在实体类型上挂载
   entity_type: soldier
     slots: [+ fact:character:*:spirit]
5. 注册期校验通过
```

**必须为零改动的对象**：

| 对象 | 要求 |
|---|---|
| Body Owner 的代码 | 0 行改动 |
| 任何 `*_runtime.py` | 0 行改动 |
| EventStore | 0 行改动 |
| 校验器 | 0 行改动 |
| 其它域 | 0 行改动 |

**允许的改动**：仅规则包文件 + FactType 注册文件。

**判定**：改动行数（代码）= 0。

---

### 实验 B：新增一类可受伤实体（云梯）

**目标**：验证"加可受伤物 = 加剖面"。

**步骤**：

```yaml
1. 规则包新增 entity_type
   entity_type: siege_ladder
     slots:
       - fact:siege-equipment:*:frame-durability   (pool)
       - fact:siege-equipment:*:rung-durability    (pool)
       - fact:siege-equipment:*:state              (machine)
2. 新增 impact_profile
   profile: siege_ladder@1
     layers:
       - order 10: frame-durability, resolver structure_damage_v1
       - order 20: rung-durability,  resolver structure_damage_v1
       - order 30: state,            resolver structure_break_v1
```

**必须为零改动的对象**：

| 对象 | 要求 |
|---|---|
| Combat Owner | 0 行改动 |
| Production / Facility Owner | 0 行改动 |
| 冲击管线代码 | 0 行改动 |

**判定**：一次冲击打到云梯，正确逐层扣减并转入破损态，无需改任何代码。

---

### 实验 C：新增一条玩法链路（门破 → 通行性重估）

**目标**：验证"加玩法 = 加 reaction"。

**步骤**：

```yaml
reaction: gate_breach_to_presence_reeval@1
  on: { fact_type: "fact:facility:gate-*:integrity", threshold_crossed: breach }
  emit:
    command: reevaluate_passability
    target: { scope: "gate_of(event)" }
```

**判定**：

- 门完整度破口后，Presence 收到命令并**独立**评估通行性；
- 通行性**不自动**改变；
- 无代码改动。

**这条同时验证了"分域不代写"的结构保证。**

<a id="measurement"></a>

## 三、测量方式

不能只凭感觉说"没改代码"。用可核查的方式：

| 项 | 方法 |
|---|---|
| 代码改动行数 | `git diff --stat` 只允许规则包与注册文件 |
| 运行时改动 | 二进制/模块哈希不变 |
| 行为正确 | 固定向量测试 + PIE 观察 |

### 报告格式

```text
实验 A 结果
  改动文件：3（均为 .yaml）
  代码改动行数：0
  测试：全部通过（含 12 个新增固定向量）
  观察：精神力随冲锋消耗，低于 20 进入 exhausted 状态，效果为动作受限
  结论：通过 / 不通过
```

<a id="failure-modes"></a>

## 四、失败模式与含义

实验失败时，失败**方式**比失败本身更有信息量。

| 失败方式 | 说明什么 | 处置 |
|---|---|---|
| 需要改 Body Owner 才能加池 | Owner 把机制写死了，未被抽出 | 回到阶段 2 补抽取 |
| 需要改 FactType 注册表结构 | 注册表字段不足以表达新事实 | 补 FactType schema |
| 需要改校验器 | 校验规则过严或过松 | 调整校验，但不得放宽 H 系列硬约束 |
| 需要改冲击管线代码 | 剖面没有真正做到路由 | 重做剖面为纯数据 |
| 需要新 Owner | **该事实确实是新域** | 仍算通过，但需说明理由 |
| Bond 原型无法支撑 | 原语切法错误 | **回到阶段 1，L2 以上重写** |

最后一行是最严重的。其余都可局部修补。

<a id="why-strict"></a>

## 五、为什么这个判据必须严格

宽松的判据会让架构退化成"给 34 个 runtime 贴标签"：

```
✗ "新增 FactType 时允许少量 Owner 改动"
    → 每个域都会主张自己需要"少量改动"
    → 累计回到 34 个自制 runtime
```

```
✗ "新增 FactType 时允许新建一个托管 Owner"
    → 托管 Owner 数量会随玩法线性增长
    → 回到 207 个交付格
```

唯一的严格形式是：**代码改动 0 行**。

若某次实验确实需要新 Owner，必须按 [新增 Owner 门槛](../04-Owner/01-Owner定义.md#new-owner) 四条全部成立，并单独记录为"新增域"，不计入本次实验的通过条件。

<a id="when"></a>

## 六、何时做

**阶段 5**，在以下均已完成后：

1. 阶段 1 原语原型通过
2. 阶段 2 基类抽取完成
3. 阶段 3 L0 三洞补齐
4. 阶段 4 Inventory 域完整打通

**不要提前做。** 提前做会因为基础设施不全而失败，失败原因不可区分——无法判断是架构错了还是还没做完。
