<a id="four-conditions"></a>

## 一、切片完成判据

一个纵向切片只有在以下四项**同时**成立时才算完成：

| # | 判据 | 反例 |
|---|---|---|
| 1 | 玩家能做出选择 | 只有自动播放，玩家无决定 |
| 2 | 世界产生后果 | 有 UI 反馈但事实未变 |
| 3 | 玩家能看到后果 | 事实变了但无投影 |
| 4 | 系统能解释后果 | 只看到胜负，不知原因 |

**只完成接口、假数据或单元测试，不算切片完成。**

---

<a id="causal-chain"></a>

## 二、必须可追溯的因果链

玩家看到的每个结果都必须能沿五个环节回溯：

```
意图  →  传达  →  事实  →  获知  →  表现
```

这是本项目与传统 RTS 的核心区别：**结果不是直接发生的，是通过信息与命令发生的。**

| 环节 | 需要可查的内容 |
|---|---|
| 意图 | 谁在什么情况下想做什么 |
| 传达 | 命令经过哪些节点、是否送达、是否被接受 |
| 事实 | 哪个 Owner 提交了什么、依据什么 |
| 获知 | 玩家通过什么渠道、在什么时刻知道 |
| 表现 | UI / 动画 / 音效对应哪条事实 |

任一环节断裂，玩家就无法理解因果。

<a id="demo-scenarios"></a>

## 三、Demo 必须跑通的场景

| # | 场景 | 验证的玩法要点 |
|---|---|---|
| 1 | 接收军情 | 有限知情：不是全知 |
| 2 | 判断真伪 | 报告可能有误、可能失真 |
| 3 | 下令求援 | 受理 ≠ 送达 ≠ 接受 ≠ 执行 |
| 4 | 传令中断 | 信使被杀，命令过期 |
| 5 | 布防 | 命令抵达后守军反应 |
| 6 | 城防受损 | 门破 ≠ 路通 |
| 7 | 士气变化 | 伤亡 → 士气 → 阵型 |
| 8 | 补给消耗 | 缺粮产生逐层后果，不是全球混乱值 |
| 9 | 战损 | 生命 / 体力 / 伤势 / 效果分别确认 |
| 10 | 胜负 | 只由已确认事实判定 |

### 场景 3 详解（最能体现本架构）

```
玩家下令求援
  → Organization 校验职权        receipt: authorized
  → Government 校验政令          receipt: policy_ok
  → Dispatch 创建传令            receipt: order_issued（这不是送达）
  → Presence 移动信使            receipt: arrived（到的是信使人，不是命令）
  → Dispatch 确认送达            receipt: delivered
  → Organization 确认接受        receipt: accepted
  → 后续才开始执行
```

**七步七张 receipt。** 任何一步失败，玩家看到的是具体哪一步失败，不是笼统的"求援失败"。

### 场景 6 详解（分域不代写）

```
冲车撞击城门
  → 门扇耐久下降               Production/Facility
  → 门闩耐久下降               Production/Facility
  → 完整度跌破阈值 → breach    Production/Facility
  → （reaction 触发）           —— 不是自动继承
  → Presence 独立评估通行性     Presence
  → 玩家看到：门破了，但路还可以走（或不能走，由 Presence 判定）
```

<a id="visibility-scenarios"></a>

## 四、有限知情的验收场景

这是本项目的体验内核，必须单独验。

| # | 场景 | 期望 |
|---|---|---|
| V1 | 军情未送达 | 玩家投影中不存在该信息 |
| V2 | 军情送达但经过一日 | 玩家知道，但知道的是"一天前的情况" |
| V3 | 报告内容有误 | 玩家看到错误内容，且系统知道它是错的（内部） |
| V4 | 两条矛盾报告 | 玩家看到两条，可信度不同，自行判断 |
| V5 | 敌方动向 | 无侦察则不知；侦察后延迟可知 |
| V6 | 城内谣言 | 传播路径可见，可信度低 |
| V7 | 密信被截 | 玩家不知道密信内容，但知道"信使没回来" |

**关键**：这些不是 UI 效果，是可见性机制的直接产物。若 V1 失败（玩家提前知道），说明可见性未强制。

<a id="failure-scenarios"></a>

## 五、失败与边界场景

必须验证的中断：

| # | 场景 | 期望 |
|---|---|---|
| F1 | 信使被杀 | 命令过期，不是静默消失 |
| F2 | 命令拒绝 | 玩家看到拒绝理由（经合法渠道） |
| F3 | 中途暂停 | 全部冻结，恢复后校验 |
| F4 | 断线 | 不扩权，恢复对账 |
| F5 | 提交结果未知 | 不重复扣血，不重复消耗 |
| F6 | 守将失能 | 继任链启动，幂等 |
| F7 | 粮道被截 | 部分交付，损失保留 |
| F8 | 玩家死亡 | 失败判定，不静默继续 |

<a id="not-this"></a>

## 六、不算证据的东西

明确排除，避免虚报：

| 不算 | 原因 |
|---|---|
| 单元测试通过 | 证明机制，不证明体验 |
| 编辑器截图 | 不是 PIE |
| 桌面截图 | 不是游戏画面 |
| 假数据 Demo | 未走真实 Owner |
| 只演示胜利路径 | 缺少失败与中断 |
| 自动播放 | 玩家未做选择 |
| "看起来对了" | 无 receipt 与事件流支撑 |

<a id="evidence-format"></a>

## 七、证据格式

```text
场景编号：3（下令求援）
执行时间：YYYY-MM-DD
环境：commit <hash>，pack <version>，PIE
操作：<玩家实际输入序列>
产物：
  - PIE 截图（含 HUD 与 UI）
  - 七张 receipt 的完整链路
  - 事件流片段（order_issued → arrived → delivered → accepted）
  - 时间线（event_time / known_time / presented_time）
结论：通过 / 不通过
剩余风险：<如有>
```
