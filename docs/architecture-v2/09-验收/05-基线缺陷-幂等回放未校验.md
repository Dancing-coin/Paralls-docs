<a id="summary"></a>

## 一、缺陷

**幂等回放路径直接信任存储的回执，未校验其引用的事件是否真实存在。**

当幂等记录中的 `committed_event_ids` 指向不存在的事件时，系统仍返回
`committed=True, idempotency_status="duplicate_replayed"`，而不是拒绝。

### 复现

```python
first = economy.settle_package_declared_negotiated_exchange(intent)
assert first.committed

# 篡改幂等结果：塞入一个不存在的事件 ID
store._idempotency_results[(PRINCIPAL, key)] = first.model_copy(
    update={"committed_event_ids": [*first.committed_event_ids, "missing:event"]}, deep=True
)

duplicate = economy.settle_package_declared_negotiated_exchange(intent)
# 实际：committed=True, duplicate_replayed
# 期望：拒绝，error_code="idempotency_key_reused"
```

对应测试：`tests/test_infra_package_declared_negotiated_exchange.py:331`
`test_package_exchange_rejects_corrupt_receipt_event_reference`

**该测试在原始代码上同样失败**（已用 `git stash` 对照确认），非本次重构引入。

<a id="root-cause"></a>

## 二、根因

问题在 `economy_runtime.py:1269-1282` 的 `_package_exchange_duplicate_result`：

```python
def _package_exchange_duplicate_result(self, *, command_id, idempotency_key, request_digest):
    record = self._store.get_idempotency_record(self._PRINCIPAL, idempotency_key)
    if record is None:
        return None
    if record.payload_digest != request_digest:
        return self._rejected_append(command_id, "idempotency_key_reused")
    result = self._store.get_by_idempotency(self._PRINCIPAL, idempotency_key)
    if result is None:
        return self._rejected_append(command_id, "idempotency_record_missing_result")
    return result.model_copy(update={"idempotency_status": "duplicate_replayed"}, deep=True)
    # ^ 直接返回，从不检查 result.committed_event_ids 是否可解析
```

**对比同模块的正确写法**（`economy_runtime.py:1335-1350`）：

```python
if existing.committed_event_ids and len(set(existing.committed_event_ids)) == len(existing.committed_event_ids):
    batch = self._store.get_transaction(existing.transaction_id)
    if batch is not None and tuple(e.event_id for e in batch.events) == tuple(existing.committed_event_ids):
        try:
            replay_events = tuple(self._store.get_event(eid) for eid in existing.committed_event_ids)
        except KeyError:
            replay_events = ()          # ← 事件不存在则视为无效
        if replay_events and all(...):
            prior = ...                 # 只有全部校验通过才信任
```

**同一个模块内两种写法并存**——这是关键证据：不是"全局设计未考虑"，而是**回放路径从未统一**。

<a id="why-it-survived"></a>

## 四、为什么这个缺陷长期存在

1. **正常路径覆盖充分**。约 1000 个测试文件，绝大多数走正常幂等重放，不会构造损坏回执。
2. **篡改场景只有少数测试覆盖**。`test_package_exchange_rejects_corrupt_receipt_event_reference` 这类测试存在但失败已有一段时间。
3. **错误不显式**。返回的是合法对象（`committed=True`），没有异常、没有日志、没有断言失败，除非专门测。
4. **两套写法看起来都对**。不带校验的版本更短、更像"正常代码"，review 时不易察觉。

<a id="relation-to-v2"></a>

## 五、与 v2 的关系

这个缺陷直接冲击 v2 的两条不变式：

| v2 不变式 | 冲击 |
|---|---|
| 「重复提交返回原 receipt，不产生第二次事实事件」 | 未校验时返回的 receipt 可能引用了不存在的事件 |
| 「补偿追加新事件，不擦除已提交历史」 | 无法判定"已提交"是否真实 |

它也解释了 [阶段 2](../08-迁移/02-共享Owner基类.md) 中我标记的风险：

> `result_digest` 三种算法并存——形态差异是可见的，摘要不一致是不可见的

同一个根因：**恢复完整性校验是逐域各写的，没有统一入口。**

### 对共享基类设计的影响

`replay_duplicate()` 目前**如实复刻了现有行为**（不校验事件解析），因为阶段 2 的约束是行为保持。

**这需要一次显式决策**：

| 选项 | 后果 |
|---|---|
| A. 保持不校验，另开专项修复 | 阶段 2 安全收敛，缺陷保留 |
| B. 在 `replay_duplicate()` 中加入校验 | 行为改变，77% 的回放路径行为会变，不在阶段 2 范围 |
| C. 加入**可选**校验参数，默认关闭 | 可逐域渐进启用，但增加分支 |

**建议 A + 后续专项**：先完成结构归一，再统一加上校验。理由是修复本身需要逐域确认"该域的事件类型能否从 `committed_event_ids` 反查"——有些域的多事件批次不满足这个前提。

<a id="fix-shape"></a>

## 六、修复的正确形状

不是简单地"加一个 `get_event` 调用"，而是：

```python
def replay_duplicate(store, *, principal, idempotency_key, payload_digest,
                     error_factory, missing_result_code, validate_events: bool = False):
    ...
    result = store.get_by_idempotency(principal, idempotency_key)
    if result is None:
        raise error_factory(missing_result_code)

    if validate_events:
        # 1. 事件必须全部可解析
        try:
            events = tuple(store.get_event(eid) for eid in result.committed_event_ids)
        except KeyError:
            raise error_factory("idempotency_result_event_missing")
        # 2. 事件必须与事务批次一致
        batch = store.get_transaction(result.transaction_id)
        if batch is None or tuple(e.event_id for e in batch.events) != tuple(result.committed_event_ids):
            raise error_factory("idempotency_result_transaction_mismatch")

    return ...
```

三个校验点缺一不可：

| 校验 | 防的缺陷 |
|---|---|
| 事件可解析 | 引用不存在的事件 |
| 批次存在且一致 | 回执来自另一次事务 |
| 事件数匹配 | 部分提交伪装成完整 |

参考实现：`economy_runtime.py:1335-1350` 已经做了前两项。

## 九、同一轮暴露的其他基线问题

修复过程中跑测试时发现，基线本身并不健康。这三类问题**与幂等缺陷无关**，
但会影响后续所有迁移判断，必须一并记录。

### 9.1 测试收集失败（55 处）

```text
ERROR tests/test_population_*.py
ERROR tests/test_vla_*.py
ERROR tests/test_siming_*.py
ERROR tests/test_*_main.py
!!!!!!!!!! Interrupted: 55 errors during collection !!!!!!!!!!!
```

根因：

```
ModuleNotFoundError: No module named 'tools'
ModuleNotFoundError: No module named 'backend'
```

**这不是代码缺陷，是测试环境配置问题。** `backend/tests/` 中部分测试需要以仓库
根目录为导入基准，而 `conftest.py` 只把 `backend/` 加进了 `sys.path`。

后果：**无法运行完整回归**。迁移过程中只能依赖定向测试子集。

#### 已修复（2026-11-04）

**根因分类**（55 个逐一定位）：

| 缺失模块 | 数量 | 来源 |
|---|---|---|
| `scripts` | 48 | `from scripts.verification...`，脚本目录在仓库根 |
| `backend` | 4 | `from backend.tests...`，测试互相引用 |
| `tools` | 2 | 仓库根的 `tools/`（`backend/` 侧无同名目录） |
| `zlib_ng` | 1 | 真实依赖缺失，已在 `pyproject.toml` 声明 |

**修法**（两处，都很小）：

1. `backend/conftest.py` 追加仓库根到 `sys.path`：

```python
REPO_ROOT = BACKEND_ROOT.parent
if str(REPO_ROOT) not in sys.path:
    sys.path.append(str(REPO_ROOT))
```

用 `append` 而非 `insert(0)` 是有意的：`backend/` 必须优先，否则仓库根的
`tools/` 可能抢占 `backend/tools`（若日后新增）。

`scripts/`、`scripts/verification/`、`backend/` 在仓库根下都没有 `__init__.py`，
以 PEP 420 命名空间包导入——已验证可用，不需要新增包文件。

2. 安装 `zlib-ng==1.0.0`（`pyproject.toml` 已声明，环境未装）。

**结果**：

```
修复前：9546 收集 → 55 errors，无法运行
修复后：9546 tests collected in 3.95s，0 errors
```

**这条很重要**：在修复之前，本文件里所有"定向回归 N 项通过"的结论都只覆盖
子集。修复后才能对全量套件做真正的回归判断。

### 9.2 时钟相关的测试失效（1 处）

```text
FAILED tests/test_economy_random_command_application.py::
       test_real_fastapi_websocket_controller_bind_then_random_command
```

失败位置：

```python
assert bind_ack["payload"]["accepted"]
# 实际: {'accepted': False,
#        'error_code': 'trusted_local_launch_expired',
#        'route': 'embodied_execution_ingress',
#        'source_type': 'embodied_controller_bind'}
```

`trusted_local_launch_expired` 表示"受信任的本地启动凭据已过期"。这类测试依赖
真实系统时钟，在长期未运行的项目里会自然失效。

**这是测试设计问题，不是产品缺陷**：回放与恢复的正确性不应依赖墙钟。

### 9.3 恢复完整性校验缺失（2 处）

```text
FAILED tests/test_economy_temporal_replay_application.py::
       test_economy_temporal_application_checkpoint_tail_survives_durable_reopen
FAILED tests/test_economy_random_replay_participant.py::
       test_shared_cut_replays_ten_domain_participants_after_cadence_and_restart
```

失败原因：

```text
AssertionError: ('replay_social_participant_missing',)
assert 'incomplete' == 'verified'
```

这两个是 **§一 幂等缺陷的同族问题**：回放链在参与者缺失时未能声明 verified。
它们与主缺陷共享同一个根因——**恢复完整性校验是逐域各写的，没有统一入口**。

### 9.4 三者的共同含义

| 问题 | 性质 | 对 v2 的影响 |
|---|---|---|
| 55 处收集失败 | 环境配置 | 无法做全量回归，只能定向验证 |
| 时钟测试失效 | 测试设计 | 回放正确性被墙钟污染 |
| 回放校验缺失 | 代码缺陷 | 与 §一 同源，需要统一入口 |

**第二条尤其值得警惕**：v2 的 `world_tick` 是唯一的、单调的、暂停时不变的整数，
其目的正是让回放与墙钟无关。这条测试的失效说明现有系统里仍有依赖墙钟的路径。
