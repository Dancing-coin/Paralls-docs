## 四、Pool：7 条不变量全部强制

| 不变量 | 用例 | 结果 |
|---|---|---|
| P1 有界 | 上/下界越界均抛出 `pool_upper_bound_exceeded` / `pool_lower_bound_exceeded` | 通过 |
| P2 reserved 合法 | 预留不超过可用量 | 通过 |
| P3 available ≥ 0 | `check_invariants()` 可随时调用 | 通过 |
| P4 先预留后消耗 | 未预留直接消耗被拒；超预留被拒且状态不变；`consume` 原子归还余量 | 通过 |
| P5 窗口不重复积分 | 同 `window_ref` 二次积分被拒，值不变 | 通过 |
| P6 阈值跨越触发 | 进入阈值产生一次 `pool.threshold_crossed` | 通过 |
| P7 滞回带内不翻转 | 25 → 32 → 28 → 33 均不翻转；越过 35 才退出 | 通过 |

### 关键设计决定

**越界直接拒绝，不静默 clamp。**

```python
if candidate > self.definition.upper:
    raise PoolError("pool_upper_bound_exceeded", ...)
```

理由：静默 clamp 会把"配置或公式写错"变成"看起来正常但数值不对"。这类错误在 30 天守城流程里极难定位。

### 承接 effective_stats

| effective_stats 概念 | v2 归属 | 验证 |
|---|---|---|
| `StatBaseline` / `StatModifier` | Pool 的修正源 | 通过 |
| `clamp_min` / `clamp_max` | 下沉为 Pool 不变量 | 通过（投影阶段生效） |
| `stacking_policy` | 修正合并规则 | 部分（原型实现了 priority + id 稳定排序） |
| 有效值 | 投影，不存储 | 通过：`effective()` 不写回、不增 revision |

「有效值是投影」这条被显式断言：

```python
base_revision = pool.revision
effective = pool.effective(mods)
assert pool.value == Decimal(100)
assert pool.revision == base_revision   # 投影不得产生事件
```

## 五、Bond：五种契压进同一形状

| 不变量 | 用例 | 结果 |
|---|---|---|
| B1 有向 | 端点为空被拒 | 通过 |
| B2 有作用域 | scope 为空被拒 | 通过 |
| B3 有期限 | 到期产生 `bond.expired`，持有者列表清空 | 通过 |
| B4 可撤销 | 撤销产生新事件，`active=False`，历史保留 | 通过 |
| B5 同键不冲突 | 重复 grant 被拒；转移目标已有同键契被拒 | 通过 |
| B6 来源可追溯 | `source_event_ref` 为空被拒 | 通过 |
| B7 属性不可变 | 未知属性被拒 | 通过 |

### B5 的反面：这是 v1 做不到的

```python
store.grant("own-1", "house-zhao",  "granary-01", OWNERSHIP, scope, ...)
store.grant("cus-1", "magistrate",  "granary-01", CUSTODY,   scope, ...)
store.grant("ctl-1", "garrison",    "granary-01", AUTHORITY, scope, ...)

rights = store.all_active_for("granary-01", scope)
# rights == {ownership: [house-zhao], custody: [magistrate], authority: [garrison]}
```

现有 `ownership_runtime.py` 的 `OwnershipProjection.active_right_by_asset` 是 `Mapping[str, str]`——**单值映射，无法表达产权、保管、控制归三个不同主体**。

而 v1 在四处反复强调"产权 ≠ 保管 ≠ 控制"、"持有物品不等于法律拥有"。**这个区分在文档里是对的，在代码里被压成了一个值。**

这正是"机制没抽象出来"的直接后果，也是 Bond 必须存在的理由。

## 六、跨验：真实模块字段

自验只能证明"我按自己设计的规格实现了"。跨验用真实字段检验**规格本身**是否够用。

对照了四个真实类型：`OwnershipRight`、`CredentialLink`、`SimpleDebtContract`、`DebtClaim`。

### 结果 1：三个字段落在 Bond 六槽位之外

| 字段 | 类型 | 实际语义 | 处置 |
|---|---|---|---|
| `principal_amount` | DebtClaim | 初始金额，不变 | 可作 `obligation` 属性 |
| `outstanding_amount` | DebtClaim | **随还款递减** | **不是 Bond 属性** |
| `issued_holder_inventory_revision` | CredentialLink | 绑定到某 inventory revision | 跨 FactType 不变式，归 Owner |

### 结果 2：Bond 属性必须不可变（新增 B7）

`debt_runtime.py:366` 显示 `outstanding_amount` 在还款时递减：

```python
DebtClaim(**{**claim.__dict__,
             "outstanding_amount": claim.outstanding_amount - amount, ...})
```

若允许这类变更作为 Bond 属性，Bond 会退化成一个能装任意状态的袋子——**那正是万能 Owner 的雏形**。

正确结构是三原语叠加：

```
bond.obligation      债权人 → 债务人，契约存在（可撤销、有期限）
pool.debt.<id>       outstanding_amount，界 [0, principal]，按还款递减
machine.debt.<id>    active → overdue → satisfied / cancelled
```

这与"食品变质拆成 Pool + Machine + Process"同理。**一个领域事实由多个 FactType 组成是正常结果，不是抽象失败。**

### 结果 3：凭证是独立概念，不并入 Bond

`credential_runtime.py:106-140` 的验证逻辑同时读两个投影：

```python
inventory = self._inventory_projector.rebuild(presenter_ref, ...)
credential_present = link.credential_item_ref in inventory.items and ... 
right = self._ownership_projector.rebuild(...).rights.get(link.right_id)
presenter_is_right_holder = right is not None and right.holder_ref == presenter_ref
```

结论：

```
Bond      存契约关系：谁对什么享有什么
Credential 存证明物：哪件实体物品可以证明它
```

两者是引用关系。Bond 的 `target_ref` 需要能指向实体物品，这一条已写入规格。
