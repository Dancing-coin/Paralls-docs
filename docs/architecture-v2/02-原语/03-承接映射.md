# 03-承接映射（实证）

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)
- 证据源：`D:\Paralls-phase0-1`，HEAD `c5f249bd`，`backend/app/gameplay/`

本文件回答一个决定性的问题：**六个原语能否从现有代码收敛出来，以及各自缺什么。**

收敛不了，整个 v2 停止。

---

<a id="result"></a>

## 一、结论

**六原语全部有承接物。没有一个需要从零发明。**

但四个需要"去领域化"——现在的实现带有具体领域语义，需抽成通用机制。两个（Process、Place）的实现分散在多个模块里，需要归并。

| 原语 | 承接模块 | 状态 | 主要缺口 |
|---|---|---|---|
| Pool | `effective_stats.py` | 半有 | 有界、预留、窗口积分、阈值滞回 |
| Machine | `life_state_runtime.py` | 单例有 | 泛化为可注册；条件三值 |
| Holdings | `inventory_runtime.py` | 有 | 去领域化；质量与数量拆分 |
| Bond | `ownership_runtime.py` | 单种有 | 泛化为五种契 |
| Process | 分散 8+ 模块 | **散** | 归并；统一 step 幂等 |
| Place | `population_continuity/presence_runtime.py` | 有但薄 | 占用互斥；通行性独立提交点 |

<a id="pool"></a>

## 二、Pool ← effective_stats.py

### 已有

```python
StatBaseline          stat_id, value, source_ref
StatModifier          modifier_id, stat_id, operation, value, priority,
                      stacking_key, stacking_policy, source_ref,
                      source_event_id, condition_ref
EffectiveStatEntry    stat_id, baseline, effective_value,
                      accepted_modifier_ids, rejected_modifier_reasons,
                      explanation_digest
EffectiveStatResolver resolve(baseline, modifiers, active_condition_refs)
```

已有操作：`additive`、`multiplicative`、`override`、`clamp_min`、`clamp_max`
已有叠加策略：`stack`、`highest`、`lowest`、`exclusive`、`replace_same_source`

### 判断

`effective_stats.py` 实际上是**两个原语的混合体**，这正是抽象没做出来的证据：

| 其中内容 | 归属 |
|---|---|
| `StatBaseline` / `StatModifier` / `EffectiveStatResolver` | **派生属性**，不是 Pool——它是投影 |
| `clamp_min` / `clamp_max` | Pool 的界 |
| `stacking_policy` | Pool 的修正合并规则 |
| `condition_ref` | Pool 阈值判定的雏形 |

### 缺口

1. **有界**：现在 clamp 是 modifier 的一种操作，应是 Pool 的不变量 `0 ≤ value ≤ bound`。
2. **预留**：完全没有。Pool 的 `reserved` / `available` / `consume` 三者缺失。这是 P4「未预留的消耗一律拒绝」的落地缺口。
3. **窗口积分**：没有。现在只做瞬时修正，无 `∫ rate dτ`。
4. **阈值滞回**：没有。v1 正文提了 `0.30` 进 / `0.35` 出，代码里无实现。
5. **聚合**：没有 `sum` / `distribution`。

### 动作

抽出 `Pool` 通用实现，`effective_stats` 保留为它的**派生投影层**——即 Pool 存基础值，`EffectiveStatResolver` 计算有效值，两者是"存储 vs 投影"关系，不是重复。

<a id="machine"></a>

## 三、Machine ← life_state_runtime.py

### 已有

```python
CanonicalLifeStateAuthority          初始 alive + 显式确认的 case-death
LifeStateCallerResult
CaseDeathLifeStateCaller
```

### 判断

这是一个**单例状态机**，语义正确但不可复用：

- 状态集硬编码（alive / dead）；
- 转移条件硬编码；
- 无 `condition_ref` 版本化机制；
- 无 `unknown` 三值——条件不满足时默认保持，但没有区分"不满足"与"无法判断"。

### 缺口

1. **泛化为可注册**：状态集、转移表、条件引用全部声明化（L4 `machine_defs`）。
2. **条件三值**：`true / false / unknown`，`unknown` 时记录 `machine.pending`，不是静默保持。
3. **终态保护**：死亡后普通治疗不能覆盖（v1 已有此合同，需落到通用机制）。

### 动作

`life_state_runtime` 变为 `Machine` 原语的一个**实例化**。它的规则（生命归零不等于死亡、需显式确认）成为 L4 规则包里的一个 `machine_def`。

<a id="holdings"></a>

## 四、Holdings ← inventory_runtime.py

### 已有

```python
ItemDefinition
ContainerSpec
InventoryItem         quantity, reserved_quantity, available_quantity
InventoryReservation  reservation_ref, reservation_context_ref
InventoryContainer
InventoryProjection   reservations, capacity_reservations
CommerceCapacityReservation
```

已有：数量、预留、容器、容量、可用量计算。**这是六个原语里最完整的一个。**

### 判断

机制正确，但**领域耦合**：

- `CommerceCapacityReservation` 把"市场容量"写进了通用容器；
- `ProductionOutputCustodyBindingContract` / `HarvestCustodyBindingContract` 把特定业务流程写进库存；
- 质量没有独立事实地位——v1 的食品变质需要它。

### 缺口

1. **去领域化**：`Commerce*`、`Production*`、`Harvest*` 三类契据应改为 `Bond` 原语实例，不写进 Holdings。
2. **质量拆分**：`quantity` 是 Holdings（守恒），`quality` 是 Pool（连续衰减）。现在混在 `InventoryItem` 里。
3. **聚合**：`distribution` 未实现，远场大宗物资无法用统计量表达。

### 动作

抽出 `Holdings` 通用实现；`inventory_runtime` 保留为 `Inventory` Owner 的领域规则层，其 FactType 声明指向 Holdings 与 Pool。

<a id="bond"></a>

## 五、Bond ← ownership_runtime.py

### 已有

```python
OwnershipRight        right_id, asset_ref, holder_ref, source_event_id
OwnershipProjection   rights, active_right_by_asset,
                      source_revision_vector, projection_revision
OwnershipProjector    rebuild(events) — 从事件重建
```

### 判断

形状完全正确：有向（holder → asset）、有来源、可从事件重建。**这是 `Bond` 原语的正确原型。**

但它只实现了一种契（产权），而系统需要五种：

| 契类型 | 现有承接 | 缺口 |
|---|---|---|
| `ownership` 产权 | `ownership_runtime.py` | 已有 |
| `custody` 保管 | `inventory_runtime` 的 `*CustodyBindingContract` | 散在库存里 |
| `authority` 授权 | `organization_government_runtime.py` + `credential_runtime.py` | 分散两处 |
| `affiliation` 归属 | `organization_government_runtime.py` | 部分 |
| `obligation` 承诺/债务 | `contract_runtime.py` / `debt_runtime.py` | 分散两处 |

### 缺口

1. **统一形状**：五种契用同一套 grant / revoke / transfer / supersede 语义。
2. **有效期**：`OwnershipRight` 无 `term` 字段，无法表达到期。
3. **作用域**：`OwnershipRight` 无 `scope`，无法表达"仅在本县有效"。
4. **冲突检测**：`active_right_by_asset` 是单值映射，无法表达"产权与保管同时存在且归属不同"。

最后一条最关键：**v1 反复强调产权 ≠ 保管 ≠ 控制，但代码用单值映射把它们压成一个。** 这正是"机制没抽象出来"的典型后果。

### 动作

抽出 `Bond` 通用实现，五种契为它的五个 type。`ownership_runtime` 等五个模块保留为各自 Owner 的规则层。

<a id="process"></a>

## 六、Process ← 分散 8+ 模块

### 现状

| 模块 | 承担的过程语义 |
|---|---|
| `construction_production_runtime.py` | 生产工序、开放义务 |
| `contract_runtime.py` | 合同步骤 |
| `economy_due_calendar.py` | 到期调度 |
| `ecology_temporal_consumer.py` | 周期推进 |
| `status_temporal_consumer.py` | 效果 tick |
| `action_window_runtime.py` | 动作窗口 |
| `civilization_capability_runtime.py` | 进度 |
| `status_tags.py` | 效果实例与到期 |

**八个模块各自实现了一份"带步骤和进度、可中断、有到期"的机制。** 这是本设计要消除的最大重复。

### 缺口

1. **归并**：统一 `step_index` 语义、幂等键形状、开放义务表达。
2. **恢复**：中断后从哪一步恢复、已消费资源如何保留，各模块规则不同。
3. **tick 型特化**：`status_temporal_consumer` 与 `status_tags` 合为 `temporal_process` 的一个实现。

### 动作

抽出 `Process` 通用实现。八个模块保留各自的**过程定义**（L4 数据）与领域规则，不再各自实现步骤机。

风险提示：这是六原语里归并量最大的一个，也是回归风险最高的一处。必须行为保持、逐模块迁移。

<a id="place"></a>

## 七、Place ← presence_runtime.py

### 已有

`app/population_continuity/presence_runtime.py` 提供 `PopulationPresenceAuthority`。

### 判断

存在，但**薄**：

- 服务于群体存在性，不是通用空间事实；
- 无占用互斥；
- 无通行性语义提交点；
- UE 侧的 `CharacterMovement` / NavMesh / EQS 提供执行与证据，但没有事实层。

### 缺口

1. **占用互斥**：同一位置同一时刻只能有一个占用者。
2. **通行性独立提交点**：门破口后**不自动**改变通行性（v1 已正确要求四域各自 receipt）。
3. **语义提交点**：`move_started / arrived / blocked / rerouted / intercepted / withdrawn` 需作为事件 schema 固定。
4. **与 UE 的接缝**：Actor 坐标不得每帧写账，只在语义点提交。

### 动作

保留 `population_continuity/presence_runtime.py` 为远场实现，新增近场 `Place` 事实层与 UE 执行器的适配合同。

## 八、缺口汇总与工作量信号

| 原语 | 有可用原型 | 缺口数 | 归并风险 |
|---|---|---|---|
| Pool | ✓ 半 | 5 | 中 |
| Machine | ✓ 单例 | 3 | 低 |
| Holdings | ✓ 最完整 | 3 | 中 |
| Bond | ✓ 单种 | 4 | 低 |
| Process | ✗ 分散 8 处 | 3 | **高** |
| Place | ✓ 薄 | 4 | 中 |

**Process 是唯一没有单一原型的原语**，也是最大的重复来源（8 份实现）。它的归并应当最后做，因为风险最高。

<a id="what-this-proves"></a>

## 九、这份映射证明了什么

1. **六原语是收敛的**，不是拍脑袋分类——每一个都能在 81k 行里找到原型，且原型形状与规格一致。
2. **重复实现的根因被定位了**：不是"各域各有业务"，而是**同一种机制（步骤机、状态机、契据）被八个、一个、五个模块各写一遍**。
3. **"实体与构成"确实不该是原语**：代码里没有任何一个模块在实现"原语级的实体构成"，那部分一直是硬编码的领域假设。
4. **"属性与修正"确实是投影**：`EffectiveStatResolver` 明确是只读解析（模块 docstring 写着 "Deterministic, read-only effective-stat resolution"），它从未写事实。

<a id="next"></a>

## 十、下一步（阻塞全案）

在写 L2 及以上的正式规格之前，必须先做：

1. **Pool 原型**：在 `effective_stats` 基础上补有界 + 预留 + 窗口积分 + 滞回，写固定向量测试。
2. **Bond 原型**：把五种契压成同一形状，验证 `scope` + `term` + 多值共存（产权与保管不同人）。
3. **收敛判定**：若 Bond 压不进同一形状（某种契需要额外不变量且无法表达为 type 参数），则原语清单要重审。

第 3 条是真正的判定点。**Bond 收敛失败 = 六原语改为七个或五个**，L2 及以上全部重写。

Pool 与 Bond 的原型尚未完成前，本目录 L3 及以上内容应视为**待验证**。
