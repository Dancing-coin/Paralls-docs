<a id="epoch"></a>

## 二、Authority Epoch

### 定义

`authority_epoch` 是某个事实流在某个作用域上的**写入权限代数**。每次权威迁移，epoch 递增。

```text
fact_stream:  fact:facility:gate-03:durability
scope:        county:zhaoling
epoch:        7
canonical_writer: ue.near_actor
```

### 规则

1. 每条提交必须携带 `epoch`。
2. 提交时校验 `epoch == 当前登记 epoch`，不等则拒绝（`stale_epoch`）。
3. epoch 只增不减，不重用。
4. 同一 `(stream, scope)` 在任一时刻只有一个合法 epoch 与一个 canonical writer。

### 迁移顺序（不可重排）

```
1. 冻结旧写入者（停止接收新命令）
2. 排空至交接边界，结清积分窗口
3. 保存已确认事件、未决命令、开放义务、游标
4. 未知结果先查 receipt，或显式带入恢复状态
5. 递增 epoch，登记新 canonical writer
6. 新写入者从确认 revision 恢复
7. 旧写入者的迟到写入 → 按旧 epoch 拒绝
```

第 3 步不能跳过：未知结果若被丢弃，新写入者会重复结算。

<a id="fencing"></a>

## 三、Fencing

### 写路径

```
Owner 产出授权 fragment
  → 提交端校验 epoch、revision、principal
  → EventStore 校验 CAS
  → 提交或拒绝
```

三道校验缺一不可：

| 校验 | 拒绝原因 | 后果 |
|---|---|---|
| epoch | 权限已迁移 | 停止写入，回查新 epoch |
| revision (CAS) | 读集已过期 | 重新读投影后重试 |
| principal | 非该 FactType 的 Owner | 架构违规，记录告警 |

### 迟到的旧写入

必须被**拒绝**，不是"接受但标记"。接受会产生两个 writer 写同一事实流。

### 双写检测

同一 `(stream, scope, epoch)` 出现两个不同 principal 的成功提交 = 架构缺陷，必须告警并进入对账。

<a id="commit-modes"></a>

## 四、两种提交配置

| 配置 | 何时算最终事实 | 后端职责 |
|---|---|---|
| **本地权威**（近场目标） | UE 提交端可靠持久化并产生 receipt 后 | 异步接收已提交事件，更新投影与 Agent 输入，**不重算** |
| **仅后端 store**（过渡） | 后端接受授权批次并返回 receipt 后 | 正式提交；此前 UE 反馈为 `pending` / `predicted` |

共同约束：

- 一个事实流在同一 epoch 只有一个提交权威。
- 本地为权威时，后端是同步副本/投影，不得另建可独立裁决的 canonical 账。
- 断线时，仅后端 store 配置**不得**擅自升格本地为权威。
- 本地权威配置在已有授权范围内可继续，恢复后按 cursor 补同步。

**pending / predicted 不得冒充 committed。**

<a id="atomicity"></a>

## 五、原子性边界

### 同提交端

多个 Owner 若能在一次冻结 revision 下提交互不重叠的授权片段，合并为 `AtomicEventBatch`。

语义：全成或全不成。

### 跨提交端

不承诺全局原子。走：

```
步骤 receipt → 开放义务 → 恢复游标 → 补偿（新事件）
```

**任何配置都不得假称全局原子提交。**

### 由谁声明

原子性不再是"若技术允许"的运行时判断，而是 L5 pipeline 的显式属性：

```text
pipeline: impact_profile
  atomic: true | obligation
```

`atomic: true` 而实际跨提交端 → 注册期拒绝。

<a id="receipt"></a>

## 六、Receipt 合同

每个 receipt 至少包含：

```text
command_id
result_status        committed | rejected | partial | expired | cancelled | unknown
owner_ref
fact_type_refs
committed_events
before_revision / after_revision
reason_code
evidence_refs
event_time
known_time_by_recipient
next_action / recovery_action
```

### 结果语义

| 状态 | 含义 | 禁止的处理 |
|---|---|---|
| `committed` | 已提交为事实 | — |
| `rejected` | 明确拒绝 | 不得重试同一 revision |
| `partial` | 部分提交 | 不得当作全成或全不成 |
| `expired` | 超时未决 | **不等同未提交** |
| `cancelled` | 显式取消 | 不得撤销已提交部分 |
| `unknown` | 结果未知 | 不得盲目重发；先按幂等键查询原 receipt |

`expired` 与 `unknown` 的处理是本层最容易出错的地方：**超时不等于失败**。

<a id="idempotency"></a>

## 七、幂等键

幂等的形状由 L1 原语决定，不是各域自定：

| 场景 | 幂等键形状 |
|---|---|
| 效果 tick | `effect_id + scheduled_world_tick` |
| 治疗步骤 | `treatment_id + step` |
| 传输批次步骤 | `process_id + step_index` |
| 命令 | `command_id`（含 principal） |
| 任意提交 | `principal_ref + idempotency_key` |

重复提交返回**原 receipt**，不产生第二次事实事件。

<a id="acceptance"></a>

## 八、验收

| # | 用例 | 期望 |
|---|---|---|
| K1 | 同一命令重复提交 | 返回原 receipt，事件数不变 |
| K2 | 旧 epoch 写入 | `stale_epoch` 拒绝 |
| K3 | 旧 revision 写入 | CAS 拒绝，提示重新拉取 |
| K4 | 提交前崩溃、重启后重放 | 状态一致 |
| K5 | 已提交但未收到 receipt | 按幂等键查回原结果 |
| K6 | 跨提交端中途失败 | 记录开放义务，不伪造回滚 |
| K7 | 暂停期间网络返回 | 入站缓存，不触发提交 |
| K8 | 双 writer 同 epoch | 告警并对账 |
