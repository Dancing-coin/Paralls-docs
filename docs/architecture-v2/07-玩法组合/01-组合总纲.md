# 01-组合总纲

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

**"支持多样玩法"这件事发生在这一层，不在原语层。**

原语对了但组合靠写代码，每加一个玩法仍是一次 runtime。

---

<a id="problem"></a>

## 一、v1 缺的是什么

v1 的九条跨 Owner 闭环是一张表格：

| 闭环 | 责任链 |
|---|---|
| 军情—求援—抵达 | Information → Dispatch/Organization → Presence → Objective → Campaign |
| 命令—执行—回报 | Organization/Government → Dispatch → Agent → 目标 Owner → Information |
| 命中—身体—后果 | Combat → Equipment → Body → Status/LifeState → Morale |

这些描述准确，但**没有任何合同**：一个流程长什么样、怎么声明、怎么注册、怎么校验、订阅机制是什么，全部空缺。

后果：新增玩法 = 新写一个 Workflow 类。成本仍是 O(n)，只是从 Owner 层挪到了 Workflow 层。

---

<a id="three-constructs"></a>

## 二、三种组合构造

| 构造 | 语义 | 是否有状态 | 例 |
|---|---|---|---|
| **reaction** | 某事实变化时触发别的动作 | 无 | 伤亡 → 士气重算 |
| **pipeline** | 一次操作按顺序结算多个 FactType | 无（一次执行） | 冲击管线 |
| **workflow** | 跨 Owner 的有状态流程 | 有 | 求援、医疗、运输 |

三者都**没有 `writes` 字段**。它们只能发命令、读投影、等 receipt。

<a id="reaction"></a>

## 三、Reaction

```yaml
reaction_id: casualty_to_morale
on:
  fact_type_pattern: "fact:character:*:lifestate"
  transition_to: dead
when:
  condition_ref: morale_relevant_casualty@1
emit:
  command_type: recompute_morale
  target:
    scope: "group_of(subject)"      # 派生目标
  payload:
    cause_ref: "$event.event_id"
cooldown_world_ticks: 0
priority: 100
```

### 字段说明

| 字段 | 说明 |
|---|---|
| `on` | 事实类型 + 事件类型（或状态转移） |
| `when` | 可选条件，返回三值；`unknown` 时不触发并记录 |
| `emit` | 只能是 Command，不能是事实写入 |
| `target` | 目标选择器，支持派生（`group_of`、`scope_of`、`owner_of`） |
| `priority` | 同事件的多个 reaction 顺序，稠密唯一 |

### 为什么必须是异步

Reaction 的目标通常跨 scope（个人 → 队伍）。按 [结算顺序](../03-事实类型/02-结算顺序.md#cross-scope)，跨 scope 不允许同批次语义，因此 reaction 一律异步：

```
事实提交 → receipt → reaction 触发 → 新 Command → 新结算
```

这保证"伤亡 → 士气"不会因为批次边界不同而产生不同结果。

### 禁止

| 禁止 | 原因 |
|---|---|
| `emit` 直接写事实 | reaction 无写权 |
| 循环触发（A → B → A） | 校验器检测并拒绝 |
| 跨事实同步读 | 会造成同批次语义漂移 |

<a id="pipeline"></a>

## 四、Pipeline

```yaml
pipeline_id: impact_soldier
profile_ref: impact_profile/soldier@1
atomic: true
host_requirement: single
steps:
  - fact_type_pattern: "fact:character:*:shield-durability"
    resolver: shield_absorb_v2
  - fact_type_pattern: "fact:character:*:armor-durability"
    resolver: armor_mitigation_v3
  - fact_type_pattern: "fact:character:*:health"
    resolver: body_damage_v2
  - fact_type_pattern: "fact:character:*:status-bleeding"
    resolver: bleeding_threshold_v1
  - fact_type_pattern: "fact:character:*:lifestate"
    resolver: lifestate_transition_v1
```

### 与受击剖面的关系

受击剖面（L4）声明"哪类目标按什么层序受伤"。Pipeline（L5）声明"这次操作走哪条管线、是否原子"。

两者可合并：**剖面的实例化就是 pipeline**。分开保留是因为剖面是设定（换目标类型时改），管线是玩法（换玩法时改）。

### 硬约束

- 同一管线内所有 step 共享 `input_revision_vector`；
- `atomic: true` 要求所有 step 同宿主；
- 跨 scope 的 step 不允许同批次。

<a id="workflow"></a>

## 五、Workflow

```yaml
workflow_id: siege_supply_relief
steps:
  - id: authorize
    command: government.issue_relief_order
    on_reject: abort
  - id: reserve
    command: inventory.reserve
    depends_on: [authorize]
    on_reject: abort_with_compensation
  - id: transport
    command: transport.create_shipment
    depends_on: [reserve]
    on_fail: record_obligation
  - id: deliver
    command: inventory.receive
    depends_on: [transport]
    on_fail: record_obligation
open_obligations:
  - step_id: transport
    recovery: reconcile_then_retry
  - step_id: deliver
    recovery: reconcile_then_retry
timeout_policy:
  default: record_obligation
  per_step:
    authorize: abort
```

### Workflow 有什么、没有什么

| 有 | 没有 |
|---|---|
| 步骤定义与依赖 | 任何事实写权 |
| 成功/拒绝/超时语义 | 被编排 Owner 的规则副本 |
| 开放义务与恢复动作 | 药物库存、生命值、伤势、流血、死亡 |
| 流程进度与游标 | 第二份领域状态 |

### 状态归属

Workflow 的中间状态（进度、obligation、cursor）**属于 Workflow 自身，不是领域事实**：

```
Workflow 状态   可丢可重建（从已提交事件与 receipt）
领域事实        必须持久可回放
```

Workflow 状态丢失时从事件流重建，**不能因此重算领域事实**。

### 医疗是标准范例

```
1. Medical Workflow 校验医护、设施、目标、时长、方案
2. Inventory Owner 预留/扣除药材
3. Body Owner 提交生命/伤势变化
4. Status Owner 提交效果减轻/解除
5. receipts 汇总，更新投影
```

Workflow 只做第 1 步和串接，第 2–4 步由各自 Owner 提交。

<a id="play-pattern"></a>

## 六、play_pattern：玩法的单位

一个 `play_pattern` 组合上述三者：

```yaml
play_pattern_id: county_siege
reactions:
  - casualty_to_morale
  - gate_breach_to_control_contest
  - supply_low_to_morale_pressure
  - messenger_killed_to_order_expired
pipelines:
  - impact_soldier
  - impact_gate
  - impact_siege_engine
workflows:
  - siege_supply_relief
  - reinforcement_request
  - medical_treatment
content_refs:
  - pack: han_realistic@2.1
  - pack: zhaoling_siege_tuning@1.0
```

**"玩法" = 一个 play_pattern。**

守城不是新 Owner，不是新 runtime，是一个组合了若干 reaction / pipeline / workflow 的声明。

<a id="structure-guarantee"></a>

## 七、结构保证：不能变成万能 Owner

`SiegeOwner` 反模式之所以危险，是因为它能同时写伤害、库存、士气、控制权、胜负。

一个 `play_pattern` **结构上做不到**：

| 检查 | 结果 |
|---|---|
| schema 有无 `writes` 字段 | 无 |
| emit 能否是事实写入 | 只能是 Command |
| 能否绕过 Gateway | 不能，所有命令经它 |
| 能否直接调 Owner | 不能，没有该接口 |
| 能否改可见性 | 不能 |

这是**类型层面的禁止**，不是纪律要求。即使用户或配置作者想写出一个万能 Owner，也无法表达。

<a id="cost"></a>

## 八、成本对比

| 新增内容 | v1 | v2 |
|---|---|---|
| 新数值资源（精神力） | 新建或改 Owner + 合同 + 写权矩阵 + 节奏矩阵 + 模型包 + 交付证据 | 加池定义 + FactType 声明 |
| 新可受伤实体（云梯） | 改 Combat + 可能新 Owner | 加 entity_type + impact_profile |
| 新玩法（守城） | 新 Workflow 类 | 新 play_pattern 声明 |
| 新纪律（士气） | 改 Morale Owner | 加 aggregation_model |
| 新流程（运输） | 新 runtime | 加 workflow 声明 |

**这就是成功判据的量化形式。**
