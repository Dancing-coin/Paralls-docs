<a id="terminology"></a>

## 二、术语

| 术语 | 含义 |
|---|---|
| **宿主**（host） | 运行代码的位置：UE / Paralls / 群体模拟 |
| **写权**（authority） | 对某类事实的唯一写入资格 |
| **canonical writer** | 持有某个 scope + epoch 写权的那个 Owner 实例 |
| **提交**（commit） | 事件被可靠持久化并产生 receipt |
| **预测**（predicted） | UE 本地算出的、尚未提交的表现性结果 |

**关键**：宿主与写权是两件独立的事。UE 可以承载一个 Owner 的权威实现，也可以只做预测。

<a id="ue-as-host"></a>

## 三、UE 作为宿主

### 允许的三种模式

```text
execution_mode: authoritative | predicted | presentation_only
```

| 模式 | 能否提交事实 | 用途 |
|---|---|---|
| `authoritative` | **能**，且是该 scope 的唯一写入者 | 近场实时链 |
| `predicted` | 不能 | 本地即时反馈 |
| `presentation_only` | 不能 | 纯表现 |

### 硬约束

| 约束 | 违反后果 |
|---|---|
| `authoritative` 必须同时声明 `commit_store` 与 `canonical_writer` | 注册失败 |
| 同一 scope + epoch 只能有一个 `authoritative` 宿主 | 架构违规，双写检测 |
| `predicted` 结果不得进入投影 | 投影污染 |
| 不存在 `hybrid` 模式值 | 注册失败 |

**最后一条是有意的**：v1 明确指出「避免使用 `hybrid` 作为 authority 值」。若 UE 做高频模拟、Owner 在语义点结算，应分别标出执行位置、执行模式、唯一提交 Owner——三者是不同字段，压成一个值就会丢失信息。

### 哪些 Owner 应该在 UE

按 v2 的 Owner 分类：

| 类别 | 典型宿主 | 理由 |
|---|---|---|
| 托管 Owner（Body、Equipment、Status、LifeState、Morale 的数值部分） | **UE** | 判定响应必须即时，不能等后端往返 |
| 托管 Owner（Inventory 的弹药/药品子流） | **UE** | 战斗回路依赖 |
| 托管 Owner（Facility 的城门机械） | **UE** | 撞击响应必须即时 |
| 原生 Owner（Dispatch、Organization、Politics、Economy） | Paralls | 规则密集，无实时要求 |
| 原生 Owner（Presence 的位置承认） | **UE** | 位置证据只在本地存在 |
| 原生 Owner（Information 的传播） | Paralls | 传播延迟天然是低频的 |

**判定标准不是「重要不重要」，是「不即时生效会不会破坏手感」。**

<a id="commit-semantics"></a>

## 四、提交语义

### 三个不同的完成态

必须区分：

```
Owner 计算完成  ≠  canonical 提交完成  ≠  后端投影同步完成
```

| 配置 | 何时算最终事实 | 后端职责 |
|---|---|---|
| **本地权威** | UE 提交端可靠持久化并对该 scope 产生 receipt 后 | 异步接收已提交事件、更新投影与 Agent 输入，**不重算** |
| **仅后端 store** | 后端接受授权批次并返回 receipt 后 | 负责正式提交；此前 UE 反馈为 `pending` / `predicted` |

### 硬约束

| 约束 | 说明 |
|---|---|
| `predicted` 不得冒充 `committed` | 表现层可以立即响应，但状态标记必须诚实 |
| 本地为权威时，后端是**同步副本**，不是第二份可裁决的账 | 后端不得重新结算同一伤害 |
| 仅后端 store 配置下，**断线不得擅自升格本地为权威** | 这是最常见的错误捷径 |
| 提交结果未知时，先按幂等键查原 receipt | 不盲目重发 |

### 本地提交端必须实现

```
revision / CAS
幂等 receipt
可靠事件持久化
outbox
稳定排序
checkpoint / replay
崩溃恢复
epoch fencing
```

缺任何一项，「本地权威」都不成立。

**注意**：这不是「缓存一份 UE 数值然后无条件上传」。那份数值不是事实，提交端的事件才是。

<a id="frame-loop"></a>

## 五、帧循环与语义提交点

### 分层

```
帧循环（每帧）          输入 / 移动 / 动画 / 物理 / 局部碰撞
────────────────────────────────────────────────────────
语义提交点（离散）      攻击尝试 / 命中候选 / 到达 / 被阻挡 /
                        运输装载 / 运输拦截 / 命令送达 /
                        目标状态变化 / 阈值跨越 / 状态转换
────────────────────────────────────────────────────────
Owner 结算             验证证据、权限、revision、成本
                        → Event + Receipt
                        → Projection / Reconciliation
```

### 绝对不能每帧写账的东西

| 项 | 理由 |
|---|---|
| Actor 坐标 | 每帧写会产生海量事件，且位置是连续量 |
| 骨骼变换 | 纯表现 |
| 动画状态 | 表现 |
| 物理速度 | 派生量 |
| UI 数值 | 投影 |

**判据**：若某个量在两次语义提交点之间变化多次但语义不变，它不该每帧入账。

### 语义提交点的定义

一个提交点是一次**语义上不可再分**的变化：

```text
不是：位置从 (10,5) 变成 (10.3,5.1)
而是：从 A 地到达 B 地
```

```text
不是：刀挥到第 12 帧
而是：命中确认
```

### 更新节奏按 FactType 分别声明

| 事实 | 节奏 | 触发 |
|---|---|---|
| 生命 | `event` | 命中 / 治疗 / 效果 tick |
| 体力 | `window` | 动作成本 + 时间积分 |
| 士气 | `window` | 伤亡 / 军旗 / 指挥事件 + 周期压力 |
| 位置 | `step`（近场） | 语义点提交，不逐帧 |
| 饥渴疲劳 | `window` | 生存窗口 |

**画面帧、模型评估、事件提交、投影同步、Agent 决策是五个不同的节奏。** 混成一个是一类常见错误。

<a id="disconnect"></a>

## 六、断线

### 分配置的行为

| 配置 | 断线时 | 恢复时 |
|---|---|---|
| 本地权威 | 在既有授权范围内**可以继续**确认结果 | 按 cursor 补同步 |
| 仅后端 store | **停止确认**，反馈降为 `pending` | 对账后补提 |
| `presentation_only` | 用最后的投影继续表现 | 重新拉取投影 |

### 禁止的降级

| 禁止 | 理由 |
|---|---|
| 仅后端配置下离线升格本地为权威 | 会造成双写 |
| 断线时放宽权限或视野 | AI 不能因断线获得特权 |
| 用"本地战术脑"产生新的自主意图 | 只能在已登记降级权限与有效 lease 内工作 |
| 断线期间的预测结果标为 committed | 预测始终是 predicted |

### 恢复对账

```
1. 按 revision / cursor 比对本地与后端
2. 差异事件按幂等键查证
3. 已提交但未同步的 → 补发
4. 未提交的预测 → 丢弃并重放投影
5. 结果未知的 → 保留开放义务，不猜
```

<a id="handoff"></a>

## 七、近远场交接

### 交接单位

| 轴 | 级别 | 含义 |
|---|---|---|
| 认知精度 | B0 dormant | 不运行独立 Agent |
| | B1 batch_reasoned | 群体批处理 |
| | B2 agent_prepared | 预热，不写世界 |
| | B3 agent_active | 运行完整 Agent |
| 表现精度 | P0 far_marker | 地图图标 |
| | P1 mid_proxy | 轻量代理 |
| | P2 near_actor | 完整 Actor |
| | P3 focal_actor | 近景完整角色 |

**两个轴独立。** 一个角色可以 B3/P0（远处但需要判断），或 B1/P2（近处但只是队列成员）。

#### 命名说明（v2 相对 v1 的更正）

v1 用 `C0–C3` 表示认知精度轴。Paralls 代码里同一概念用 **`B0–B3`**（`population_continuity/activation_policy.py`、`character_modules.py`），而 `C0–C4` 在那里表示**任务时延分级**，是另一件事。

**v2 统一采用 `B0–B3`**，理由是接入时必须与既有代码对齐，否则两套字母指同一件事会造成实现分歧。`C` 轴名称在 v2 中不再使用。

### 交接顺序（不可重排）

```
1. 冻结旧推进者（停止接收新工作）
2. 排空至交接边界，结清积分窗口
3. 保存已确认事件、未决命令、开放义务、游标
4. 未知结果先查清，或显式带入恢复状态
5. 递增 epoch，登记新 canonical writer
6. 新推进者从确认 revision 恢复
7. 旧推进者的迟到写入 → 按旧 epoch 拒绝
```

**第 3 步不能跳过**：未知结果若被丢弃，新推进者会重复结算。

### 交接不改变的事

| 不改变 | 说明 |
|---|---|
| Owner 身份 | Body 换宿主仍是 Body |
| 角色身份 | `character_id` 不变 |
| 事实归属 | 只换写入者，不换事实域 |
| 私有记忆 | 随 Paralls 保留，不随 Actor 迁移 |

<a id="equivalence"></a>

## 八、UE 与 Paralls 的等价性

### 必须相同的

| 项 | 判据 |
|---|---|
| 规则包版本 | 完全相同的解析路径 |
| 模型版本 | 同一 `model_id` + `model_version` |
| 单位与精度 | 同一 `dec` scale |
| 随机算法与 seed | 同一算法、同一 seed 来源 |
| 排序 | 同一 `resolution_order` |
| 输入 revision | 同一向量 |

### 验证方式

每个托管 Owner 至少提供 20 组固定向量：

```text
给定：FactType 状态 + 输入 + 模型版本
期望：逐字节相同的 EvaluationResult + 事件
```

在 C++ 与 Python 各跑一次，结果必须完全相同。

### 禁止

| 禁止 | 理由 |
|---|---|
| C++ 与 Python 各自维护同名公式 | 必然漂移 |
| 用浮点 | 平台差异 |
| 遍历节奏依赖容器顺序 | dict vs unordered_map |
| 用系统时间 | 不可回放 |

<a id="manifest"></a>

## 九、Owner Manifest 的 UE 字段

每个 Owner 在 UE 上承载时必须登记：

```text
execution_host        ue_runtime | paralls_runtime | population
execution_mode        authoritative | predicted | presentation_only
canonical_writer      owner_id
commit_store          canonical EventStore 引用
commit_boundary       semantic_event | transaction
latency_budget        见性能基准
prediction_policy     none | short_horizon
reconciliation_policy accept | correct | reject_and_replay
pause_behavior        freeze
disconnect_behavior   continue_within_lease | stop
```

### 三条校验

| 检查 | 拒绝码 |
|---|---|
| `authoritative` 且缺 `commit_store` | `manifest_commit_store_missing` |
| 同 scope + epoch 两个 `authoritative` | `manifest_dual_authority` |
| `presentation_only` 却声明 `canonical_writer` | `manifest_presentation_cannot_write` |

<a id="what-ue-does-not-do"></a>

## 十、UE 不做的事

| 不做 | 理由 |
|---|---|
| 作为第二份事实账 | 只有一个 canonical EventStore |
| 用动画完成替代 Owner receipt | 表现不是事实 |
| 用 Actor 字段存事实 | Actor 是表现载体 |
| 绕过 Command 直接调用 Owner | 所有行动经统一 Command |
| 自行推进世界时钟 | 时钟来自 WRK，暂停时静止 |

**最后一条特别重要**：UE 的 `Tick`、`Timer`、`AnimNotify` 都不是世界时间的来源。它们是表现节奏，不是世界节奏。

<a id="acceptance"></a>

## 十一、验收

| # | 用例 | 期望 |
|---|---|---|
| U1 | 近场命中 | UE 本地结算并在预算内确认 |
| U2 | 仅后端配置下断线 | 返回 pending，不标 committed |
| U3 | 本地权威断线 | 在 lease 范围内继续，恢复后补同步 |
| U4 | 交接中途崩溃 | 旧 epoch 写入被拒，新推进者从确认 revision 恢复 |
| U5 | 同一角色 B1→B3 升级 | `character_id` 与私有记忆不变 |
| U6 | C++ 与 Python 固定向量 | 逐字节相同 |
| U7 | 暂停期间 Timer 触发 | 不产生玩法事件 |
| U8 | Actor 位置每帧变化 | 只有语义点入账 |
| U9 | 双 authoritative 声明 | 注册拒绝 |
| U10 | 预测结果进入投影 | 拒绝 |
