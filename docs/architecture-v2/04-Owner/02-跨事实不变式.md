# 02-跨事实不变式

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

本文件是 Owner 存在的**唯一理由**。若一条约束只涉及单个 FactType，它属于 FactType；只有跨 FactType 的约束才需要 Owner 作为责任单位。

---

<a id="why"></a>

## 一、为什么必须是 Owner 的责任

考虑"预留不超过总量"：

```text
fact:lot:wheat-07:quantity   Holdings  → Inventory 写
fact:lot:wheat-07:reserved   Pool      → Inventory 写
```

登记表只说两者都归 Inventory 写。**没有人负责检查它们的关系。**

后果是具体的：一批粮先被生产预留 40，又被军需预留 40，两条提交各自合法（都在自己的 revision 上成功），合计 80 > 总量 60。**这是 v1 架构无法防止的缺陷**，因为约束没有归属。

v2 的解法：这类约束写进 Owner 的 `invariants`，由 Owner 在提交前统一校验。

---

<a id="categories"></a>

## 二、四类跨事实不变式

### A. 数量约束

```text
Inventory:   Σ reserved(fact_type) ≤ quantity(fact_type)
             Σ contents ≤ capacity(container)
Body:        health == 0 ⟹ stamina == 0
Equipment:   durability == 0 ⟹ protection_level == 0
```

### B. 状态一致性

```text
Body:        lifestate ∈ {dying, dead} ⟹ health ≤ 濒死阈值
Status:      status.instance 存在 ⟹ 其 source_event 存在且已提交
Morale:      formation ∈ {routed} ⟹ morale < 溃退阈值
Production:  facility.state == running ⟹ latch.open == false
```

### C. 时序约束

```text
Dispatch:    order.accepted_time ≥ order.delivered_time
Transport:   shipment.arrived_time > shipment.departed_time
Process:     step[n].time ≤ step[n+1].time
LifeState:   已确认 death 后不得接受普通 thum 治疗的 body 写入
```

### D. 因果约束

```text
Territory:   control.transferred 必须有已提交的 military/governance 依据
Objective:   victory.confirmed 必须有已提交的 Territory/LifeState/Campaign 依据
Ownership:   right.transferred 必须有已提交的授权依据与对价/征发理由
Combat:      hit_confirmed 必须有已提交的命中证据
```

D 类最容易被漏掉，因为它不是"数值关系"，而是"必须有前序事实"。v1 用散文反复强调（"Objective 只读已确认事实"），v2 把它变成可校验的不变式。

---

<a id="enforcement"></a>

## 三、校验时机

不变式在**提交前**校验，不在提交后审计。

```
Owner 产出授权 fragment
  → 校验本 fact_type 的原语不变量
  → 校验 Owner 的跨事实不变式        ← 这里
  → 校验 epoch / revision / principal
  → 提交
```

失败时返回 `invariant_violated` 加具体规则 ID，**不静默通过**。

### 性能

不变式校验需要读多个 FactType。为避免 O(n) 全量读取：

- 只校验**本批次触及**的 FactType；
- 读取用固定 revision（本批次冻结的读集）；
- 不变式可声明 `check_scope: batch | periodic`，`periodic` 的用低频扫描兜底。

---

<a id="declaration"></a>

## 四、声明格式

```text
invariant:
  id: inventory_reserved_not_exceed_quantity
  owner_ref: Inventory
  reads: [fact:lot:*:quantity, fact:lot:*:reserved]
  expr: "Σ reserved(lot) ≤ quantity(lot)"
  check_scope: batch
  on_violation: reject
  reason_code: invariant_reserved_exceeds_quantity
```

字段说明：

| 字段 | 说明 |
|---|---|
| `reads` | 该不变式依赖的 FactType pattern；用于确定校验时的读集 |
| `expr` | 形式化表达式，由校验器解析；不允许执行任意代码 |
| `check_scope` | `batch` 每批次校验；`periodic` 定期兜底 |
| `on_violation` | `reject` 拒绝提交；`flag` 允许但告警（仅用于诊断类） |

`expr` 是受限表达式，不是脚本。这是 [规则包不带逻辑](../05-规则包/01-规则包总纲.md#no-logic) 的延伸：不变式表达必须可静态分析。

<a id="catalog"></a>

## 五、首批不变式目录

Demo 所需的跨事实不变式，按 Owner 归类。

### Inventory

| ID | 约束 | 类型 |
|---|---|---|
| `inv_reserved_le_quantity` | 预留 ≤ 总量 | A |
| `inv_container_capacity` | 内容物之和 ≤ 容器容量 | A |
| `inv_quality_range` | 0 ≤ 质量 ≤ 100 | A |
| `inv_transfer_conserves` | 转移前后总量不变 | A |

### Body

| ID | 约束 | 类型 |
|---|---|---|
| `inv_health_zero_stamina_zero` | 生命为 0 ⟹ 体力为 0 | A |
| `inv_injury_limits_capability` | 伤势等级限制能力上限 | B |
| `inv_dead_no_treatment` | 已确认死亡不接受普通治疗 | C |

### Equipment

| ID | 约束 | 类型 |
|---|---|---|
| `inv_broken_no_protection` | 耐久为 0 ⟹ 防护为 0 | B |
| `inv_equipped_owned` | 装备关系必须存在对应 Bond | D |

### Morale

| ID | 约束 | 类型 |
|---|---|---|
| `inv_routed_below_threshold` | 溃退状态 ⟹ 士气低于阈值 | B |
| `inv_formation_member_scope` | 阵型实例 ⊆ 队伍成员 | A |

### LifeState

| ID | 约束 | 类型 |
|---|---|---|
| `inv_death_requires_basis` | 死亡必须有 Body 依据 | D |
| `inv_health_zero_not_dead` | health == 0 不自动等于 dead | B |

### Dispatch

| ID | 约束 | 类型 |
|---|---|---|
| `inv_accept_after_deliver` | 接受时间 ≥ 送达时间 | C |
| `inv_order_before_execute` | 执行必须有已接受的命令 | D |

### Territory

| ID | 约束 | 类型 |
|---|---|---|
| `inv_control_needs_basis` | 控制转移必须有军事/治理依据 | D |
| `inv_contested_exclusive` | 争夺状态与实际占用一致 | B |

### Objective

| ID | 约束 | 类型 |
|---|---|---|
| `inv_victory_reads_confirmed` | 胜负只引用已确认事实 | D |
| `inv_no_control_write` | 不得写控制权 | D |

### Ownership

| ID | 约束 | 类型 |
|---|---|---|
| `inv_transfer_needs_authority` | 产权转移必须有授权依据 | D |
| `inv_distinct_rights_coexist` | 产权、保管、控制可归不同主体 | A |

最后一条是 v1 反复强调但代码违反的一条：`ownership_runtime.py` 的 `active_right_by_asset` 是单值映射，无法表达"产权与保管不同人"。v2 要求 Bond 支持多类型共存。

<a id="acceptance"></a>

## 六、验收

| # | 用例 | 期望 |
|---|---|---|
| I1 | 两次预留合计超过总量 | 第二次被 `invariant_violated` 拒绝 |
| I2 | 生命为 0 但体力 > 0 | 提交拒绝 |
| I3 | 确认死亡后再提交治疗 | 拒绝 |
| I4 | 无依据的领土转移 | 拒绝 |
| I5 | 同一资产产权与保管归不同主体 | 允许，两者共存 |
| I6 | 不变式表达式含任意代码 | 注册拒绝 |
