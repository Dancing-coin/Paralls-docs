# 02-跨域结算

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

<a id="spine"></a>

## 一、结算脊柱

```
L5 pipeline 声明 atomic: true | obligation
     ↓
L2 resolution_order 排序（不依赖调用顺序）
     ↓
各 FactType 的 Owner 产出授权 fragment
     ↓
同提交端 → AtomicEventBatch        跨提交端 → 步骤 receipt + 开放义务
     ↓
L5 补偿追加新事件（不擦除历史）
```

v1 这条链已经正确。v2 改的是三处决定从哪里来：原子性由管线声明、顺序由注册表给出、片段形状由原语统一。

---

<a id="fragment"></a>

## 二、授权 fragment

```text
fragment:
  fragment_id
  owner_ref
  fact_type_refs        本片段要写的事实
  expected_revisions    每个 FactType 的预期 revision（必填且完整）
  read_set_revisions    读到的其它事实 revision
  operations            按 resolution_order 排列的操作序列
  model_ref             使用的 Resolver
  input_revision_vector 所有输入 revision
  event_visibility      每条事件的可见性策略
```

### 三条硬约束

| 约束 | 违反后果 |
|---|---|
| `expected_revisions` 必须覆盖 `fact_type_refs` 全部 | 片段不完整，拒绝 |
| `operations` 必须按该 FactType 的 `resolution_order` 排列 | 顺序错误，拒绝 |
| `input_revision_vector` 在同 pipeline 内必须一致 | 语义漂移，拒绝 |

第二条和第三条是 v2 新增。v1 的 fragment 只要求 revision 完整，不要求顺序与输入一致。

<a id="atomic"></a>

## 三、原子性由数据声明

v1 在此处的措辞是：

> 若当前技术无法保证共同原子提交，则拆成 owner-local commits 和开放义务

这是一个**运行时判断**，取决于部署配置（本地权威 vs 仅后端），因此同一套规则在不同配置下行为不同。

v2 改为显式声明：

```yaml
pipeline: impact_to_consequence
  atomic: true            # 或 obligation
  host_requirement: single   # 若 atomic，所有层必须同提交端
```

规则：

| 声明 | 要求 | 违反 |
|---|---|---|
| `atomic: true` | 所有层在同一提交端 | 注册期拒绝（`impact_atomic_cross_host`） |
| `obligation` | 允许跨端，走步骤 receipt | 必须声明恢复动作 |

**不允许"看起来原子、实际跨端"的配置。**

---

<a id="order"></a>

## 四、结算顺序

见 [结算顺序](../03-事实类型/02-结算顺序.md)。

关键点：

- 同批次与分阶段必须产生同一结果；
- 分阶段下若前序 revision 不是本批次最后一次提交，必须拒绝重排；
- 跨 scope 必须用已提交 revision，不能同批次。

---

<a id="sequence-example"></a>

## 五、完整示例：一次命中

```text
UE：碰撞证据 → Command(impact) @ Gateway
  ↓ L2 解析 target → entity_type = soldier
  ↓ L4 impact_profile soldier@1
  ↓ resolution_order: 10/20/30/40/50
  ↓
  order 10  Equipment  shield-durability  → 片段 A
  order 20  Equipment  armor-durability   → 片段 B
  order 30  Body       health / injury    → 片段 C
  order 40  Status     status-bleeding    → 片段 D
  order 50  LifeState  lifestate          → 片段 E
  ↓
  settlement_plan 合并 A–E
  ↓ 校验：revision 完整、顺序正确、input_revision_vector 一致
  ↓ AtomicEventBatch → EventStore
  ↓ receipt
  ↓ L0 可见性过滤：谁知道他死了？经何渠道？何时？
  ↓ L5 reaction：伤亡 → Morale 重算（异步，跨 scope）
```

注意第 40、50 层：Status 读取的是**本批次 order 30 的 Body 结果**，不是"当前已提交的 Body revision"。分阶段模式下则必须是本批次最后一次提交的 revision——两者在顺序表约束下结果一致。

注意最后的 Morale：**异步，不是同批次**。因为它是跨 scope（个人 → 队伍），跨 scope 不允许同批次语义。

<a id="obligation"></a>

## 六、开放义务与补偿

### 开放义务

```text
obligation:
  obligation_id
  pipeline_ref
  completed_steps    []
  pending_steps      []
  pending_reason      rejected | unknown | timeout | host_unavailable
  owner_refs         []         # 待完成的 Owner
  recovery_action    retry | reconcile | manual | compensate
  deadline_world_tick
```

### 规则

| 情形 | 处理 |
|---|---|
| Owner A 已提交，Owner B 拒绝 | 保留 A，记录 B 的 obligation |
| 提交结果未知 | **先按幂等键查原 receipt**，不盲目重发 |
| 超时 | 状态未知，不自动回滚 |
| 补偿 | 追加新事件，不删除已提交历史 |

### 禁止

- 全局回滚
- 撤销已提交事件
- "重试到成功"而不检查是否已成功
- 用补偿掩盖未知结果（必须先查清）

---

<a id="unknown"></a>

## 七、未知结果的三种情形

三者不可混淆：

| 情形 | 判定依据 | 处理 |
|---|---|---|
| 未提交 | 幂等键查无记录 | 可以重试 |
| 已提交未收到 receipt | 幂等键查有记录 | 返回原 receipt，不重算 |
| 提交结果不确定 | 幂等键查询本身失败 | 保留 obligation，禁止重发 |

第三种最危险：**查询失败不等于未提交。** 此时必须停止依赖该结果的后续动作。

---

<a id="no-second-ledger"></a>

## 八、不建第二份事实

跨域流程的所有中间状态（流程进度、obligation、cursor）都属于 Workflow 自身，不是领域事实。

```
Workflow 状态   ≠  领域事实
可丢可重建          必须持久可回放
```

若 Workflow 状态丢失，从已提交事件与 receipt 重建，**不能因此重算领域事实**。

<a id="acceptance"></a>

## 九、验收

| # | 用例 | 期望 |
|---|---|---|
| X1 | 五层命中同批次 | 一次 AtomicEventBatch，一个 receipt |
| X2 | 中途一层拒绝 | 记录 obligation，已提交层保留 |
| X3 | 分阶段中途插入治疗 | revision 不一致，拒绝重排 |
| X4 | 跨宿主声明 atomic | 注册拒绝 |
| X5 | 提交后崩溃重启 | 按幂等键查回原结果，不重复扣血 |
| X6 | 查询本身失败 | 保留 obligation，禁止重发 |
| X7 | 补偿 | 追加事件，历史事件数不变 |
| X8 | Workflow 状态丢失后重建 | 领域事实不变 |
