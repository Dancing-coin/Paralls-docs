<a id="principles"></a>

## 一、五条原则

### 1. 机制共享，设定数据，规则原生

三者不能混：

| | 内容 | 位置 | 变化频率 |
|---|---|---|---|
| **机制** | 有界、预留、积分、幂等、revision、可见性 | L0 / L1 | 几乎不变，写一次 |
| **设定** | 界值、阈值、状态集、层序、参数 | L4 | 换玩法时换 |
| **规则** | 无法由数据表达的判断（继任、承认、撮合、传令失真） | L3 原生 Owner 的 Resolver | 随领域走 |

第三条是本设计区别于"万物皆配置"方案的关键。**不是所有领域都能数据化**：政治承认、指挥继任、通信失真、市场撮合必须保留为代码，包在原生 Owner 里。它们的收益小，但它们的成本也小——因为数量少。

收益集中的是"数值—效果—状态"主干，那部分全部是托管 Owner。

### 2. 切在独立变化处

**层边界只有两侧能独立变化时才成立。**

本项目真正独立变化的只有六个轴：

```
事实形状    → L1 原语
谁写        → L2 FactType 的 owner_ref / L3 Owner
怎么算      → L4 Resolver
跑在哪      → L2 host / L0 epoch
多久算一次  → L2 cadence
谁看得见    → L2 visibility + L0 强制
```

不在这六个轴上的划分理由（"它属于军事"、"它是玩法系统"）不构成层边界。

### 3. 写权可指名，机制不重复

这两条不矛盾，前提是 Owner 从"容器"降为"声明"：

- **Owner 名字必须稳定、手写、可审计**——写权是责任，必须能指派到人。
- **机制必须只实现一次**——幂等、revision、receipt、可见性属于内核，不属于任何 Owner。

违反第一条会长出无人负责的配置堆；违反第二条会长出 34 个各自实现幂等的 runtime。两条都要守。

### 4. 拒绝非法输入，缺省即失败

- 缺 `visibility` → 注册失败，不给默认值。
- 缺 `resolution_order` → 注册失败，不按文件名排序兜底。
- 缺输入 → `unknown`，不补零。
- 未注册原语 → 拒绝，不允许"自定义原语"逃生口。

### 5. 只有 L3 拥有写权

L0 提交机制不决定领域规则是否合法。L1 原语只守不变量。L2 声明归属。L4/L5 只声明组合与设定。**它们都不能写事实。**

这条是防止 `SiegeOwner` 反模式的结构保证，不是纪律要求。

<a id="invariants"></a>

## 二、全局不变式

以下七条在任何实现、任何配置、任何宿主下都必须成立。违反其一即为架构缺陷，不是实现缺陷。

1. **每一条事实，在每一个作用域和 authority epoch 内，只有一个 canonical writer。**
2. **模型结果不是事件。** Resolver 返回评估结果，由 FactType 的 Owner 校验后提交。
3. **配置无权声明写权。** 规则包、play_pattern 都不能扩大任何 Owner 的写集。
4. **同一时间点的结算顺序唯一且可校验。** 由 `resolution_order` 稠密整数决定，不依赖调用顺序。
5. **未知不默认。** 缺输入、过期输入、冲突输入必须显式返回 `unknown` 或拒绝。
6. **回放用旧版本，不用新公式重算历史。**
7. **补偿追加新事件，不擦除已发生的损失。**

<a id="non-goals"></a>

## 三、非目标

明确不做：

- **不建万能 Owner。** 不存在拥有所有事实的 `UniversalOwner`，也不存在披着 Workflow 外衣的它。
- **不做 DSL。** 规则包不能携带逻辑（理由见 [规则包总纲](../05-规则包/01-规则包总纲.md)）。
- **不让配置声明跨 Owner 写权。**
- **不重建 Paralls 的 81k 行。** 现有 34 个 runtime 保留为原生 Owner 实现。
- **不为第一阶段需要而提前实现全国战争、完整经济或全量 LLM 居民。**
- **不宣称未验证的能力。** 四态分别记录。

<a id="tradeoffs"></a>

## 四、已知代价

诚实的代价清单，供决策时权衡：

| 代价 | 说明 | 缓解 |
|---|---|---|
| 复杂度 | 比 v1 多两层（Owner 分类、玩法组合），L2 最易腐化 | 原语封顶六个；FactType 必须指名原语；校验器强制 |
| 出效果晚 | 原语引擎 + 校验器先做，才轮到 Demo | 先打通一个域到底，不等全量 |
| 与既有代码距离 | 需先抽共享基类，不能零改动 | 行为保持重构，靠约 1000 个测试兜底 |
| 原语收敛未验证 | 六个是假设 | **先做承重实验，收敛不了就停** |
| 调试成本 | 数据化后堆栈变浅、定义变深 | 按 FactType 打统计标签；提供定义追溯投影 |

第 4 条是最重的。原型阶段代码更快、更好调，这一点不否认。本设计的理由是：原型之后要支持多样玩法，届时重写代价更高。

<a id="decision-log"></a>

## 五、与相关方案的差异定位

| 方案 | 定位 | 本设计的取舍 |
|---|---|---|
| v1（23 Owner + 九项交付包） | 权威架构正确，成本未解决 | 继承权威部分，替换组织方式 |
| "四层权威栈"（基础权威→Owner→Workflow→宿主） | 层级论证正确、术语清晰 | **完全吸收其反层级约束**；但不采纳"Owner 内部无结构" |
| "原语 + 规则包 + 登记"（三层） | 诊断正确 | 吸收原语与规则包；补 Owner 两类划分与 L5 组合合同 |

三者的共同点（单一 writer、scope × epoch、依赖有向图、Workflow 不写事实）在 v2 中全部保留，见 [反模式与硬约束](03-反模式与硬约束.md)。
