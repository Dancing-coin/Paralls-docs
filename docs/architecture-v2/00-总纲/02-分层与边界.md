<a id="six-layers"></a>

## 一、六层职责

```
┌─────────────────────────────────────────────────────────────────┐
│ L5 玩法组合    reaction · pipeline · workflow                     │
│                守城 = 传令订阅 + 补给流程 + 冲击管线 + 目标判定       │
│                不写事实。结构上无 writes 字段。                     │
├─────────────────────────────────────────────────────────────────┤
│ L4 规则包      实体类型·池定义·状态机·受击剖面·聚合模型·命令目录      │
│                版本化数据。不写事实。无权声明跨 Owner 写权。          │
├─────────────────────────────────────────────────────────────────┤
│ L3 Owner       写集 + 跨事实不变式 + 命令词汇 + 可用模型              │
│                ★ 唯一拥有写权的一层。native / stewarded 两类         │
├─────────────────────────────────────────────────────────────────┤
│ L2 事实类型    原语 + 身份域 + 写主 + 可见性 + 结算序 + 聚合          │
│                最小写权单位。声明，不是实现。                        │
├─────────────────────────────────────────────────────────────────┤
│ L1 原语        Pool · Machine · Holdings · Bond · Process · Place  │
│                六个状态形状。只守不变量，不含任何设定。               │
├─────────────────────────────────────────────────────────────────┤
│ L0 内核        时钟·身份·提交·revision·幂等·receipt·outbox·replay    │
│                机制写一次，全层共享。不决定领域规则是否合法。          │
└─────────────────────────────────────────────────────────────────┘
```

<a id="dependency"></a>

## 二、依赖方向

**只允许向下依赖。**

```
L5 ──→ L4 ──→ L3 ──→ L2 ──→ L1 ──→ L0
```

| 允许 | 禁止 |
|---|---|
| L5 引用 L4 的包条目、L3 的命令词汇 | L4 引用 L5（配置不能知道玩法） |
| L4 Resolver 读 L1 原语规格 | L1 引用 L4（原语不含设定） |
| L3 声明写集指向 L2 的 FactType | L2 引用 L3 的具体实现 |
| L2 引用 L1 的原语类型 | L1 引用具体 FactType |
| 全部引用 L0 | L0 引用任何上层 |

**禁止向上依赖的实质意义**：换规则包（L4）不需要改 Owner（L3）；加玩法（L5）不需要改原语（L1）。这是"支持多样玩法"的结构含义。

<a id="three-cross"></a>

## 三、三条横向约束

不是层，而是贯穿所有层的强制规则。任何一层违反都视为架构缺陷。

### 1. 可见性

- L2 的每个 FactType 必须声明 `visibility`，无默认值。
- L0 在**读取端**强制过滤，不依赖写入端自觉。
- 当前实现为零（见 [可见性强制](../01-内核/02-可见性强制.md)）。

### 2. 结算顺序

- L2 的每个 FactType 必须有 `resolution_order`，稠密唯一整数。
- 由管线拓扑生成，不手填、不依赖调用顺序、不依赖文件名。
- 修掉 v1 "同批次 vs 分阶段"的语义漂移。

### 3. unknown

- Resolver 返回值域必须包含 `unknown`。
- 缺输入、过期输入、冲突输入返回 `unknown`，不返回 `false`、零或成功。
- 调用方必须显式处理三种结果。

<a id="layer-contents"></a>

## 四、每层包含什么 / 不包含什么

| 层 | 包含 | 明确不包含 |
|---|---|---|
| L0 | 时钟、身份注册、提交、revision、幂等、receipt、outbox、replay、checkpoint、epoch 栅栏、可见性过滤 | 任何领域数值、任何领域判断 |
| L1 | 六个原语的不变量、事件 schema、积分切窗、聚合方式、幂等键形状 | 具体界值、阈值、状态集（这些在 L4） |
| L2 | FactType 声明、写主、可见性、结算序、聚合方式、unknown 策略 | 任何计算公式、任何实现代码 |
| L3 | 写集、跨 FactType 不变式、命令词汇、可用 Resolver 引用、宿主与 epoch | 机制实现（幂等/revision/receipt 来自 L0） |
| L4 | 实体类型、池定义、状态机、受击剖面、聚合模型、命令目录、统一参数 | 任何逻辑（不允许 DSL）、任何写权声明 |
| L5 | reaction、pipeline、workflow 的声明与注册 | **任何 `writes` 字段**、任何直接事实写入 |

<a id="what-is-owner"></a>

## 五、只有 L3 是 Owner

容易混淆的对照：

| 概念 | 是 Owner 吗 | 理由 |
|---|---|---|
| 基础权威（Clock / Identity / Capability） | **否** | 提供约束，不结算玩法事实 |
| 领域 Owner（L3） | **是** | 唯一事实写权 |
| FactType（L2） | 否 | 是最小**写权单位**，其写主是某个 Owner |
| 原语（L1） | 否 | 机制形状 |
| 规则包条目（L4） | 否 | 数据 |
| Workflow / Composite（L5） | **否** | 编排，不拥有被编排的事实 |
| 执行宿主（UE / Paralls / 群体） | **否** | 同一 Owner 的不同部署位置 |
| Projection Consumer | 否 | 受限读取方 |
| Owner Instance | **是** | 某个 Owner 在特定 scope / epoch 上的实例，仍属同一逻辑 Owner |

<a id="scale-and-host"></a>

## 六、规模与宿主不产生新层

这是最容易被误实现成层级的两处。

### 规模

```
Morale@角色   Morale@小队   Morale@守军   Morale@战区
```

是**同一个** `Morale / Formation` Owner 的四个 `authority_scope` 实例，不是四层士气 Owner。

### 宿主

```
Body Owner
  ├─ UE-local Body Authority      玩家附近的即时伤害
  └─ Paralls Body Authority       远处居民和队伍的低频结算
```

是同一逻辑 Owner 的两个宿主。约束：同一 `canonical scope + authority_epoch` 只有一个 canonical writer；UE 写入时后端只同步投影，不重算同一份生命事实。

规模用 `authority_scope`，宿主用 `host` + `epoch`。**两者都不改变 Owner 的身份或数量。**

<a id="fact-dependency"></a>

## 七、事实依赖是有向图，不是上下级

```
Combat ───────> Body
   ├──────────> Equipment
   └──────────> Status

Government ───> Ownership
Government ───> Inventory
Transport ────> Inventory
Territory ────> Objective
Politics ─────> Campaign
```

箭头表示**读取、请求授权或提供依据**，不表示上级拥有下级事实。

`Objective` 在玩法上看起来像高层，但它不能写 `Territory` 的占领事实——只能读占领结果判断目标是否完成。`Government` 可以批准征发，但 `Ownership` 才确认产权变化，`Inventory` 才确认数量变化，`Transport` 才确认运输状态。四者协作，不是父子。
