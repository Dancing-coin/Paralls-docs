# 05-术语与轴

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

本文件定义 v2 使用的正交轴，并禁止跨轴复用同一术语。

---

<a id="why"></a>

## 一、为什么需要这份文件

架构文档里最常见的缺陷不是概念错，而是**同一个词被用在不同维度上**。

后果很具体：两个人都 "按文档做了"，但做的不是同一件事。

v2 核实过程中已遇到三处：

| 术语 | 冲突 |
|---|---|
| `hybrid` | 计算形态 vs 提交边界 |
| `Resource` | Body/Resource vs Inventory/Resource |
| `C0–C3` | 认知精度轴 vs Paralls 的任务时延分级 |

因此立一条硬约束：**同一术语不得跨轴复用。**

---

<a id="axes"></a>

## 二、五条正交轴

任何一条事实、一个 Owner、一个模型，都可以用这五条轴描述，彼此独立。

### 轴 1：事实形状（L1 原语）

```text
pool | machine | holdings | bond | process | place
```

**回答**：这类事实长什么样、守什么不变量。

### 轴 2：计算形态（L4 Resolver）

```text
numeric | condition | hybrid
```

**回答**：这类事实怎么算出来。

| 值 | 输出 |
|---|---|
| `numeric` | 数值 |
| `condition` | true / false / unknown |
| `hybrid` | 条件 + 数值 + 状态转移候选 |

`hybrid` **只在这一轴使用**。它的含义限于"一次评估同时产出多种结果"，与执行位置、提交时机无关。

v2 要求：若一个 `hybrid` 模型横跨多个 FactType，应拆成管线（见 [Resolver 合同](../06-模型与结算/01-Resolver合同.md#hybrid-split)）。因此它是**收敛中的类型**，不是扩展方向。

### 轴 3：执行位置（宿主）

```text
ue | paralls | population
```

**回答**：代码在哪跑。

**不表示**：谁有权写事实。

### 轴 4：提交边界

```text
semantic_event | contact_point | transaction
```

**回答**：什么时候算最终事实。

| 值 | 含义 |
|---|---|
| `semantic_event` | 语义事件发生即提交（如"到达"） |
| `contact_point` | 在接触/结算点提交（如"刀锋接触"） |
| `transaction` | 在一个原子批次内提交 |

### 轴 5：精度

```text
B0 | B1 | B2 | B3        认知精度
P0 | P1 | P2 | P3        表现精度
```

**回答**：这个主体被模拟到多细。

两条精度轴独立。一个角色可以是 B3/P0（远处但需要判断）或 B1/P2（近处但只是队列成员）。

<a id="no-authority-mode"></a>

## 三、废除 `authority_mode`

旧材料里有一个枚举：

```text
✗ authority_mode: ue_local | canonical_backend | hybrid
```

**这个枚举本身是缺陷**，三个成员不在同一维度上：

| 成员 | 实际在说什么 |
|---|---|
| `ue_local` | 执行位置在 UE，且隐含不写事实 |
| `canonical_backend` | 提交位置在后端 |
| `hybrid` | 执行在 UE、提交在后端——这是前两者的组合 |

把位置、提交点、组合压进一个字段，正是"丢失信息"。

### 正确写法

```text
execution_host:     ue
commit_boundary:    contact_point
canonical_writer:   <owner_ref>
```

旧材料的 `hybrid` 场景因此被完整表达，且**不需要单独一个词**。

### 三种典型配置

| 场景 | execution_host | commit_boundary | canonical_writer |
|---|---|---|---|
| 纯表现 | `ue` | —（不提交） | 无 |
| UE 高频 + 关键点提交（旧称 hybrid） | `ue` | `contact_point` | 对应 Owner |
| 后端结算 | `paralls` | `semantic_event` | 对应 Owner |

**第二行就是旧的 `hybrid`。** 它不是一个模式，是一组字段取值的组合。

<a id="naming-rules"></a>

## 四、命名规则

### 4.1 一轴一词

| 轴 | 允许的词 |
|---|---|
| 事实形状 | `pool` `machine` `holdings` `bond` `process` `place` |
| 计算形态 | `numeric` `condition` `hybrid` |
| 执行位置 | `ue` `paralls` `population` |
| 提交边界 | `semantic_event` `contact_point` `transaction` |
| 精度 | `B0`–`B3`、`P0`–`P3` |

**不得跨轴借用。** 例如不得用 `process` 表示"跨域流程"（那是 L5 的 `workflow`），也不得用 `hybrid` 表示"混合部署"。

### 4.2 已废止的术语

| 废止 | 替代 | 理由 |
|---|---|---|
| `authority_mode` | `execution_host` + `commit_boundary` + `canonical_writer` | 跨轴枚举 |
| `C0`–`C3`（认知精度） | `B0`–`B3` | 与 Paralls 的任务时延分级冲突 |
| `Body/Resource` | `Body` | 与 `Inventory/Resource` 重名 |
| `Composite Owner`（作为第 24 个 Owner） | `workflow` / `pipeline`（L5） | 组合不是写权 |

### 4.3 同名不同义的现有情况

| 词 | 在 Paralls 的含义 | 在 v2 的含义 |
|---|---|---|
| `hybrid` | （旧）提交边界组合 | 计算形态 |
| `C0–C4` | 任务时延分级 | 不使用 |
| `Owner` | 模块级 authority | L3 的写权单位 |
| `Actor` | UE 的实体 | 表现载体，非事实 |

接入时**必须显式转换**，不得直接沿用。

<a id="how-to-apply"></a>

## 五、如何应用

写任何字段声明时，先问它属于哪条轴：

```
这个字段在说「事实长什么样」吗？   → 轴 1
这个字段在说「怎么算」吗？         → 轴 2
这个字段在说「在哪跑」吗？         → 轴 3
这个字段在说「何时算数」吗？       → 轴 4
这个字段在说「多精确」吗？         → 轴 5
都不属于？                          → 它不是这五条轴上的东西，重新想
```

**若一个字段同时回答了多个问题，它应当被拆开。**

## 六、验收
