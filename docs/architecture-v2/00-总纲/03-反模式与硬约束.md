# 03-反模式与硬约束

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

本文件是 v2 的守门清单。下列反模式不是"建议避免"，而是**注册期拒绝**或**结构上不可能**。任何实现若违反其一，即为架构缺陷。

---

<a id="anti-patterns"></a>

## 一、十个反模式

### A1. 父 Owner 拥有子 Owner 的事实

```
✗ SiegeOwner ─┬─ Combat
              ├─ Inventory
              ├─ Morale
              └─ Objective
```

后果：`SiegeOwner` 最终同时持有伤害、库存、士气、胜负，成为隐藏的万能 Owner。

**约束**：Owner 彼此平级，只通过 Command / 授权 fragment / revision pin / receipt 协作。守城是 `play_pattern`，不是 Owner。

**检查**：任何 Owner 的 `writes` 不得包含另一 Owner 的既有 `writes`。

---

### A2. 把规模做成 Owner 层级

```
✗ Morale → SquadMorale → GarrisonMorale → TheaterMorale

✓ Morale@角色  Morale@小队  Morale@守军  Morale@战区
```

**约束**：规模变化用 `authority_scope`，不增加 Owner 层。跨 scope 的聚合由 L2 `aggregation` + L4 `refold_model` 处理。

---

### A3. 把宿主做成 Owner 层级

```
✗ UEBodyOwner + ParallsBodyOwner

✓ Body Owner，两个 host 实例，各自 authority_epoch
```

**约束**：同一 `canonical scope + epoch` 只有一个 canonical writer。

---

### A4. 配置声明写权

规则包或 play_pattern 里出现"把 X 事实改成 Y"的声明。

**约束**：L4 只能声明**路由**（受击剖面的每层指向已注册 FactType 及其 Owner），不能声明写。L5 结构上无 `writes` 字段。

**检查**：规则包 schema 不含任何 owner 覆写字段；静态检查器验证剖面每层的 `owner_ref` 与 FactType 注册一致。

---

### A5. 万能 Owner / 伪装成 Workflow 的万能 Owner

包含：`UniversalOwner`、`GameStateOwner`、`WorldState`、`SiegeWorkflow`（能直接写）。

**检查**：Owner 的 `writes` 必须全部指向已注册 FactType；Workflow 无 `writes`。

---

### A6. 机制在 Owner 内重复实现

每个 Owner 自己实现幂等、revision、receipt、可见性。

**现状**：真实代码 28/33/29/16 个 runtime 各写一遍。

**约束**：全部来自 L0。Owner 只提供 `writes` / `invariants` / `commands` / `resolvers`。

---

### A7. 同一时间点无序

依赖调用顺序、字典顺序或文件名决定谁先结算。

**约束**：`resolution_order` 稠密唯一整数，由管线拓扑生成。同批次与分阶段必须给出同一顺序。

---

### A8. 可见性靠自觉

在写入端标注 `visibility`，读取端不过滤。

**现状**：`event_store.py` grep `visibility` 零命中——这正是当前状态。

**约束**：L0 读取端强制。无 `visibility` 的 FactType 注册失败。

---

### A9. 未知默认成立

缺输入时返回 `false` / `0` / 成功。

**约束**：Resolver 三值域，`unknown` 必须被调用方显式处理。规则包无法关闭此行为。

---

### A10. 换设定要改代码

新增精神力、新兵种、新可受伤实体需要改 Owner 或新建 runtime。

**约束**：这是成功判据的直接否定。见 [分水岭实验](../08-迁移/04-分水岭实验.md)。

---

<a id="hard-rules"></a>

## 二、十二条硬约束

| # | 约束 | 强制方式 |
|---|---|---|
| H1 | 原语封顶六个 | 注册表拒绝第七种；新增须走 §三 流程 |
| H2 | 每个 FactType 必须指名一个原语 | 注册失败 |
| H3 | 每个 FactType 必须有 `visibility`（无默认） | 注册失败 |
| H4 | 每个 FactType 必须有 `resolution_order` | 注册失败 |
| H5 | Resolver 必须声明 `writes_fact_types` | 注册失败 |
| H6 | Resolver 的每个 `writes_fact_types` 的 owner 必须等于该 FactType 的 owner | 注册失败 |
| H7 | 只有 L3 的 principal 能提交事实事件 | 事件 schema 拒绝 |
| H8 | Workflow / play_pattern 无 `writes` 字段 | schema 不含该字段 |
| H9 | 规则包不含可执行逻辑 | schema 无脚本字段；加载器无 eval |
| H10 | 同一 Pipeline 内所有 layer 共享同一 `input_revision_vector` | 注册失败 |
| H11 | 回放按事件携带版本重算，禁用当前包 | 回放器只读事件版本 |
| H12 | 补偿追加事件，不删除已提交事件 | EventStore 无删除接口 |

<a id="adding-primitive"></a>

## 三、新增原语的唯一路径

六个是**封顶**，不是起点。新增第七个必须完成全部三步，缺一不可：

1. **证明不可组合**：用已有六个原语的两两及以上组合，构造出目标语义，并说明哪条不变量无法保持。
2. **给出不变量**：新原语必须有不变量、事件 schema、积分切窗方式、聚合方式、幂等键形状——与六个同规格。
3. **改注册表与校验器**：更新 L1 注册表与 H1/H2 检查。

未完成第 1 步就提新原语，一律拒绝。历史经验：**"实体与构成"、"属性与修正"、"效果"三者都曾被误认为原语**，它们的正确归属见 [原语总则](../02-原语/01-原语总则.md#not-primitives)。

<a id="rejection-table"></a>

## 四、注册期拒绝清单

规则包 / FactType / Resolver 注册时，下列条件触发拒绝，不进入"警告"级别：

| 拒绝码 | 条件 |
|---|---|
| `facttype_primitive_unknown` | 原语不在六种内 |
| `facttype_visibility_missing` | 无 `visibility` 或为空 |
| `facttype_resolution_order_missing` | 无 `resolution_order` |
| `facttype_resolution_order_duplicate` | 同 scope 内重复 |
| `facttype_owner_unknown` | `owner_ref` 未注册 |
| `resolver_writes_undeclared` | 输出事实类型未在 `writes_fact_types` 声明 |
| `resolver_owner_mismatch` | `writes_fact_types` 的 owner ≠ FactType 的 owner |
| `impact_layer_facttype_unknown` | 剖面层指向未注册 FactType |
| `impact_layer_owner_mismatch` | 剖面层 owner 与 FactType owner 不一致 |
| `pipeline_revision_vector_mismatch` | 同管线内 layer 的 `input_revision_vector` 不一致 |
| `pack_contains_logic` | 包内出现可执行字段 |
| `pattern_declares_writes` | play_pattern 出现 `writes` |
| `owner_overlaps_owner` | 两个 Owner 的 `writes` 相交（除显式授权代理） |
| `primitive_count_exceeded` | 原语数 > 6 |

上述清单由 [校验器规则](../05-规则包/03-校验器规则.md) 实现。

<a id="adopted"></a>

## 五、从相关方案吸收的约束

以下来自"四层权威栈"方案，v2 全部采纳并已体现在上文：

- 拒绝父 Owner → 子 Owner 的分权（A1）
- `SiegeOwner` 反模式（A1）
- 规模不产生 Owner 层级，用 scope 解决（A2）
- `Owner Instance` 术语（[分层与边界](02-分层与边界.md#what-is-owner)）
- 宿主不产生 Owner 层级（A3）
- 依赖有向图而非上下级（[分层与边界](02-分层与边界.md#fact-dependency)）
- 一条 canonical writer / scope / epoch（H10、A3）
- Workflow 不拥有被编排事实（A5、H8）
