<a id="why"></a>

## 0. 为什么需要这一版

v1 的问题不是某个 Owner 定义错了，而是 **"Owner" 一个词同时承担了五件事**：事实域、写权、解算、部署、模块。后果是机制被重复实现，新增玩法必须重写一遍底座。

真实代码的实证（`D:\Paralls-phase0-1\backend\app\gameplay\`）：

| 现象 | 数据 |
|---|---|
| 按域切分的运行时 | 34 个 `*_runtime.py` |
| 共享基类 | 0 |
| 各自实现幂等 | 28 个 |
| 各自处理 revision | 33 个 |
| 各自处理可见性 | 29 个 |
| 各自处理 receipt | 16 个 |

新增一个玩法系统的实际成本因此是 O(全部基础设施)，而不是 O(增量)。v2 的唯一目的是把这个成本降下来。

<a id="layers"></a>

## 2. 分层

```
L0 内核        时钟·身份·提交·revision·幂等·receipt·outbox·replay·checkpoint·epoch栅栏
L1 原语        六个状态形状，只守不变量，不含任何设定
L2 事实类型    最小写权单位：原语 + 身份域 + 写主 + 可见性 + 结算序 + 聚合
L3 Owner       写集 + 跨事实不变式 + 命令词汇 + 可用模型；native / stewarded
L4 规则包      实体类型·池定义·状态机·受击剖面·聚合模型·命令目录（版本化数据）
L5 玩法组合    订阅·管线·流程 —— "多样玩法"在这一层实现
```

横向贯穿三条（约束，不是层）：**可见性**、**结算顺序**、**unknown**。

**只有 L3 拥有写权。** L0/L1/L2/L4/L5 都不是 Owner，都不能写事实。

<a id="not-hierarchy"></a>

## 3. 这不是 Owner 层级

必须与"父 Owner → 子 Owner"划清界限。本设计里：

- 不存在分层上级写权。所有 Owner 彼此平级，只通过 Command、授权 fragment、revision pin 和 receipt 协作。
- 规模变化（个人/小队/守军/战区）用 `authority_scope` 表达，**不增加 Owner 层**。
- 执行位置变化（UE/Paralls/群体模拟）用 `host` + `authority_epoch` 表达，**不增加 Owner 层**。
- L4 规则包**无权**声明跨 Owner 写权；L5 玩法组合**结构上没有** `writes` 字段。

典型反模式（本设计明确禁止）：

```
SiegeOwner
  ├─ Combat
  ├─ Inventory
  ├─ Morale
  └─ Objective        ← 最终同时持有伤害、库存、士气、胜负，成为隐藏的万能 Owner
```

守城是一个 `play_pattern`（L5），不是 Owner。它只能发命令、读投影，不能写任何事实。

## 4. 从 v1 继承的部分（不改）

EventStore、revision/CAS、幂等、receipt、outbox、replay/checkpoint、统一 Command 信封、Intent/Command/Event 三分、三本账、unknown 不默认零、补偿不擦除历史、医疗是 Workflow 不是 Owner、四态（已定义/可执行/已接入/已验收）。

<a id="replaced"></a>

## 5. 被替换的部分

| v1 | v2 |
|---|---|
| 23 个领域 Owner 固定名单 + 九项交付包（207 格） | L3 Owner 声明（native/stewarded）+ L2 FactType |
| 七部分契约 | 拆开：机制→L0/L1，设定→L4，写权→L2，责任→L3 |
| Numeric / Condition / Hybrid Model | L4 Resolver；Hybrid 拆到 L5 管线 |
| Applicability Binding / Evaluation Context | L4 包 + L2 必填字段 |
| UE 协作与节奏矩阵 | L2 的 `cadence` + `host` 字段 |
| 九条跨 Owner 闭环（表格描述） | L5 `play_pattern` 数据 |

23 个 Owner **名字保留**——写权必须能指名到人。变的是它们内部由 FactType 组成，机制由原语提供。

<a id="v1-findings"></a>

## 6. 对 v1 与真实代码的差异审计

v1 文档声称有、真实代码中缺失的三项。它们全部是 v2 的内核必修项。

| 项 | v1 表述 | 代码实际 |
|---|---|---|
| 可见性强制 | "有限知情"是正式技术成功判据 | `visibility_policy` 有字段、`settlement_plan.py:22` 校验数量，但 `event_store.py` **读时不查**；全仓只有 `economy_privacy_views.py`、`state_group_views.py` 两个专用视图做过裁剪 |
| 三本账时间 | `event_time/known_time/presented_time` 统一回放 | 全仓 grep `known_time` / `presented_time` **零命中** |
| 权威栅栏 | authority epoch fencing | `authority_epoch` 仅在 `ws_protocol.py:45` 有一个字段，无 fencing 实现 |

另有一项结构性假设从未写明：v1 的"`world_tick` 来自 UE 战场时钟"与"WRK 拥有唯一 `world_tick`"要求两者同进程。这个部署前提必须在 [时间与暂停](01-内核/01-时间身份与暂停.md) 中显式登记。
