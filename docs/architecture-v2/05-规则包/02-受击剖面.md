# 02-受击剖面

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

受击剖面解决一个问题：**一次冲击打到不同的东西上，怎么结算。**

它在规则包里是**纯路由数据**，不写事实。

---

<a id="problem"></a>

## 一、为什么需要它

v1 的伤害链只为人写完整了：

```
Combat → Equipment → Body → Status → LifeState
```

这是为"士兵被砍"定制的。而县城守城必须结算的不止于此：城门、城墙、冲车、云梯、粮车、仓库着火。

v1 把这些散在不同文档里：门扇/闩锁归 Facility、通行归 Presence、控制归 Territory。**每次遇到"冲车撞门"都要重新推导一遍链路，且无法复用士兵那条链。**

受击剖面把"什么能受伤、按什么顺序结算"变成数据。

---

<a id="kernel"></a>

## 二、冲击是唯一输入

Combat 的 Resolver 只产出一个**冲击事实**：

```text
impact:
  source_ref           谁打的
  damage_type          锐器 | 钝器 | 穿刺 | 火焰 | 冲击
  magnitude            数值
  target_ref           打到什么
  location_ref         打到哪（若适用）
  evidence_refs        UE 接触证据、hit 证据
```

它**不需要知道打中的是人还是门**。分发由目标类型的剖面决定。

---

<a id="profiles"></a>

## 三、五份剖面

| 目标类型 | 层序（按 resolution_order） |
|---|---|
| 士兵 | 盾（池）→ 甲（池，减伤）→ 部位 → 生命（池）+ 伤势 → 阈值触发流血效果 → 生命周期（状态机） |
| 城门 | 门扇耐久（池）→ 门闩耐久（池）→ 完整度（池）低于阈值转破口（状态机）→ 通行性（状态机，**独立评估**） |
| 冲车 | 防护棚（池）→ 结构（池）→ 不可移动 / 残骸（状态机） |
| 粮车 | 车体耐久（池）→ 货物容器（按伤害类型折算货损）→ 火焰类型额外挂燃烧效果 |
| 仓库着火 | 火场效果（temporal_process）按 tick 产生冲击 → 建筑完整度（池）→ 容器内物资质量下降（池） |

### 数据形态

```yaml
profile: soldier@1
target_entity_type: soldier
layers:
  - order: 10
    fact_type: "fact:character:*:shield-durability"
    resolver: shield_absorb_v2
  - order: 20
    fact_type: "fact:character:*:armor-durability"
    resolver: armor_mitigation_v3
  - order: 30
    fact_type: "fact:character:*:health"
    resolver: body_damage_v2
  - order: 40
    fact_type: "fact:character:*:status-bleeding"
    resolver: bleeding_threshold_v1
  - order: 50
    fact_type: "fact:character:*:lifestate"
    resolver: lifestate_transition_v1
```

<a id="routing-only"></a>

## 四、剖面只做路由，不写事实

这是与讨论稿最关键的一处约束。

### 允许

- 声明层序
- 引用已注册的 FactType
- 引用已注册的 Resolver

### 禁止

- 声明"当完整度 < 30 时，把通行性改为 false"
- 直接指定任何事实的目标值
- 跨越 FactType 的既有 Owner 授权

### 每一层谁写

| 层 | 写主 |
|---|---|
| 门扇耐久 | Production / Facility |
| 门闩耐久 | Production / Facility |
| 完整度 | Production / Facility |
| 通行性 | **Presence** —— 独立评估，不自动继承 |
| 控制状态 | **Territory** —— 独立评估 |

**"门破了"不自动等于"路通了"。** 完整度低于阈值时，剖面声明"应当触发通行性重估"，但由 Presence 按自己的规则独立提交。

这条约束来自 v1 的正确判断（[城门四域分属](../../_backups/architecture_v1_20261103_1241/03-Owner领域/01-Owner注册表.md)），v2 保留并把它变成结构保证：**剖面数据没有能力指定写主**，写主由 FactType 注册决定。

<a id="new-hurtable"></a>

## 五、新增一类可受伤的东西

成功判据的一个具体实例。

### 步骤

```text
1. 在规则包里声明新的 entity_type
2. 声明它有哪些构成槽位（哪些 FactType）
3. 写一份 impact_profile，按层序引用这些 FactType
4. 校验器检查：每个 FactType 已注册、owner 一致、层序无环
5. 完成
```

### 不需要

- 不改 Combat
- 不改任何 Owner
- 不新增 runtime
- 不改 FactType 注册表（除非需要新的事实类型）

### 例：加"云梯"

```yaml
entity_type: siege_ladder
slots:
  - fact_type_pattern: "fact:siege-equipment:*:frame-durability"
  - fact_type_pattern: "fact:siege-equipment:*:rung-durability"
  - fact_type_pattern: "fact:siege-equipment:*:state"

profile: siege_ladder@1
layers:
  - order: 10
    fact_type: "fact:siege-equipment:*:frame-durability"
    resolver: structure_damage_v1
  - order: 20
    fact_type: "fact:siege-equipment:*:state"
    resolver: structure_break_v1
```

前提是 `fact:siege-equipment:*:frame-durability` 这类 FactType 已注册。若它们是全新的，需要先注册 FactType —— 但那仍然是**声明**，不是代码。

<a id="cross-host"></a>

## 六、跨宿主

同一剖面的各层若分属不同宿主：

```
门扇耐久（Paralls）→ 完整度（Paralls）→ 通行性（UE）
```

此时**不能**组成一个原子批次。剖面必须声明：

```yaml
atomicity: atomic | obligation
```

- `atomic`：所有层必须同提交端，否则注册期拒绝。
- `obligation`：走步骤 receipt + 开放义务 + 补偿。

**不允许"看起来原子、实际跨端"的配置。** 这是 v1 "若技术允许则原子"的悬置判断的替代方案：由数据显式声明。

<a id="acceptance"></a>

## 七、验收

| # | 用例 | 期望 |
|---|---|---|
| P1 | 同一冲击打到士兵与城门 | 各按剖面结算，结果不同但机制相同 |
| P2 | 门完整度跌破阈值 | 通行性**不**自动改变；Presence 独立评估 |
| P3 | 剖面层指向未注册 FactType | 注册拒绝 |
| P4 | 剖面层指定与 FactType 不同的 Owner | 注册拒绝 |
| P5 | 剖面声明跨宿主层但标 `atomic` | 注册拒绝 |
| P6 | 新增一种可受伤实体 | 只改规则包，零代码改动 |
