# 03-校验器规则

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

本文件把 v1 的散文告诫变成**注册期拒绝**。

v1 的反例清单原本靠人记住；v2 里它们是加载器的一部分。

---

<a id="principle"></a>

## 一、原则

**能在加载时拒绝的，不放到运行时。**

理由：运行时检查会：

- 在热路径上增加判断；
- 与 C++ / Python 的双端实现产生分歧；
- 出错时只在特定输入下暴露。

## 二、规则目录

### 原语层

| 码 | 条件 | 依据 |
|---|---|---|
| `primitive_count_exceeded` | 原语数 > 6 | H1 |
| `primitive_unknown` | FactType 引用的原语不在六种内 | H2 |
| `primitive_missing` | FactType 未声明原语 | H2 |

### FactType 层

| 码 | 条件 | 依据 |
|---|---|---|
| `facttype_visibility_missing` | 无 `visibility` 或为空 | H3 |
| `facttype_resolution_order_missing` | 无 `resolution_order` | H4 |
| `facttype_resolution_order_duplicate` | 同 scope 内重复 | H4 |
| `facttype_resolution_order_gap` | 非稠密（有空洞） | H4 |
| `facttype_owner_unknown` | `owner_ref` 未注册 | — |
| `facttype_schema_unknown` | `event_schema_ref` 未注册 | — |
| `facttype_refold_missing` | `aggregation=distribution` 但无 `refold_model_ref` | — |
| `facttype_naming_invalid` | 不符合 `fact:<domain>:<scope>:<name>` | — |
| `facttype_scope_missing` | 命名中无 scope | — |

### Resolver 层

| 码 | 条件 | 依据 |
|---|---|---|
| `resolver_writes_undeclared` | 输出事实类型未在 `writes_fact_types` 声明 | H5 |
| `resolver_owner_mismatch` | `writes_fact_types` 的 owner ≠ 该 FactType 的 owner | H6 |
| `resolver_input_undeclared` | 读取了未在 `reads` 声明的 FactType | — |
| `resolver_missing_determinism` | 未声明确定性策略（seed、精度、顺序） | — |
| `resolver_not_pure` | 声明了副作用（IO、时间、随机未固定） | — |

### 受击剖面

| 码 | 条件 |
|---|---|
| `impact_layer_facttype_unknown` | 层指向未注册 FactType |
| `impact_layer_owner_mismatch` | 层事实的 owner 与剖面不一致（剖面本身无 owner） |
| `impact_profile_cycle` | 层序有环 |
| `impact_atomic_cross_host` | 标 `atomic` 但层跨宿主 |
| `impact_layer_conflicts_order` | 层序与 FactType 的 `resolution_order` 冲突 |

### 管线与订阅

| 码 | 条件 | 依据 |
|---|---|---|
| `pipeline_revision_vector_mismatch` | 同管线内 layer 的 `input_revision_vector` 不一致 | H10 |
| `pipeline_cross_scope_atomic` | 跨 scope 声明同批次 | 结算顺序 §五 |
| `pattern_declares_writes` | play_pattern 出现 `writes` | H8 |
| `pattern_command_unknown` | 引用了未注册命令 | — |
| `pattern_workflow_cycle` | workflow 步骤有环 | — |

### 规则包

| 码 | 条件 | 依据 |
|---|---|---|
| `pack_contains_logic` | 包内出现可执行字段（`if`/`loop`/`script`/`code`） | H9 |
| `pack_invariant_executable` | 不变式表达式含任意代码 | — |
| `pack_overrides_visibility_requirement` | 试图放宽 `visibility` 必需性 | 规则包边界 4 |
| `pack_defines_primitive` | 试图定义新原语 | 规则包边界 3 |
| `pack_cycle_in_parents` | `parent_pack` 成环 | — |
| `pack_content_hash_mismatch` | 内容哈希不符 | — |

### Owner

| 码 | 条件 |
|---|---|
| `owner_overlaps_owner` | 两个 Owner 的 `writes` 相交（除显式授权代理） |
| `owner_writes_denied` | `writes` 与自身的 `denies` 相交 |
| `owner_native_without_resolvers` | `kind=native` 但 `resolvers` 为空 |
| `owner_stewarded_with_resolvers` | `kind=stewarded` 但有 `resolvers`（应升级为 native） |
| `owner_no_invariants` | 没有任何跨事实不变式（可能是 FactType 误报为 Owner） |

<a id="hot-insert"></a>

## 三、禁止热插入

规则包热加载**只允许在非运行态**。

理由：运行中更换设定会让"同一场战斗前后用了不同参数"，且无法回放。

允许的时机：

- 编辑器中（未进入 PIE）
- 世界创建前
- 显式迁移事件之后（见 [规则包总纲](01-规则包总纲.md#versioning)）

<a id="reports"></a>

## 四、校验报告

加载失败必须给出**可定位**的报告，不是单个布尔值：

```json
{
  "pack_id": "zhaoling_siege_tuning@1.0",
  "result": "rejected",
  "violations": [
    {
      "code": "facttype_visibility_missing",
      "fact_type": "fact:facility:gate-03:durability",
      "file": "packs/zhaoling/gate.yaml",
      "line": 42,
      "hint": "visibility 无默认值，必须显式声明 class"
    }
  ]
}
```

`hint` 字段很重要：报错信息要说明**为什么**，否则开发者会加一个空值蒙混过关。

### 4.1 严重级

不是所有问题都该阻止加载。三级：

| 级别 | 语义 | 加载行为 |
|---|---|---|
| `error` | 结构错误，必然导致运行期失败 | **拒绝加载** |
| `warning` | 可疑但不必然错 | 加载，记录 |
| `info` | 风格或优化建议 | 加载，可选输出 |

**默认全部规则为 `error`。** 降级需逐条声明理由。

已知可降级的（示例，不是清单）：

| 规则 | 级别 | 理由 |
|---|---|---|
| `pack_content_undeclared` | `warning` | 可能是刚加的条目还没登记 |
| `owner_no_invariants` | `warning` | 纯状态型 Owner 可能确实没有跨事实约束 |
| 参数偏离推荐范围 | `info` | 调参自由 |

**不可降级的**：所有 H 系列硬约束（H1–H12）、`facttype_visibility_missing`、`pack_contains_logic`、`pattern_declares_writes`。这些降级等于取消架构保证。

### 4.2 多错并发

一次加载要报告**全部可独立发现的问题**，不是发现第一个就停。

```
收集阶段：遍历全部条目，尽可能多地发现错误
  ↓
去重阶段：同一 (code, target) 只保留一条
  ↓
排序阶段：按 §4.3 的优先级排序
  ↓
截断阶段：超过 200 条时按优先级保留前 200，附计数
```

**为什么不在第一个错误处停止**：规则包往往有成批的同类错误（如十个 FactType 都忘了 `visibility`）。逐个报会变成十轮往返。

**为什么要去重**：同一问题被多个规则从不同角度发现时（如 `visibility` 缺失同时触发 `facttype_visibility_missing` 和 `facttype_combine_invalid`），只报根因。

### 4.3 排序与依赖折叠

按下列顺序排列，让开发者按依赖顺序修：

```
1. 解析层      pack_content_missing / pack_cycle_in_parents
2. schema 层   YAML 结构、类型错误
3. 引用层      xxx_unknown（引用了不存在的条目）
4. 语义层      owner_mismatch / combination_invalid
5. 建议层      warning / info
```

**依赖折叠**：若某条目在解析层就失败了，不再报它的语义层错误。

例：某 FactType 的 `owner_ref` 指向不存在的 Owner（引用层），则不再报它因缺 owner 而导致的语义层派生错误——修好引用后那些错误会自动消失。

```json
{
  "fact_type": "fact:facility:gate-03:durability",
  "code": "facttype_owner_unknown",
  "level": "error",
  "suppressed": 2,
  "suppressed_codes": ["facttype_combine_invalid", "owner_overlaps_owner"]
}
```

`suppressed` 计数让开发者知道「修好这一个还有没有后续」。

### 4.4 报告结构

```json
{
  "pack_resolution": [
    { "pack_id": "han_realistic", "pack_version": "2.1.0" }
  ],
  "result": "rejected",
  "counts": { "error": 12, "warning": 3, "info": 0, "suppressed": 5 },
  "truncated": false,
  "violations": [
    {
      "code": "facttype_visibility_missing",
      "level": "error",
      "phase": "semantic",
      "fact_type": "fact:facility:gate-03:durability",
      "owner_ref": "ProductionFacility",
      "file": "packs/zhaoling/gate.yaml",
      "line": 42,
      "column": 3,
      "hint": "visibility 无默认值，必须显式声明 class",
      "suppressed": 0,
      "doc_ref": "03-事实类型/04-FactType完整schema.md#rejection-codes"
    }
  ]
}
```

| 字段 | 作用 |
|---|---|
| `phase` | 解析 / schema / 引用 / 语义 / 建议，对应 §4.3 |
| `owner_ref` | 便于按 Owner 过滤 |
| `line` / `column` | 可定位 |
| `doc_ref` | 指向规则说明，避免开发者去翻文档 |
| `truncated` | 是否被 200 条上限截断 |

### 4.5 失败时的加载行为

| 有 `error` | 加载 | 已解析的内容 |
|---|---|---|
| 是 | **拒绝** | 全部丢弃，不部分加载 |
| 否 | 加载 | 保留，warning 记录 |

**不部分加载**是有意的：半份规则包会让运行时行为依赖"哪些条目碰巧通过了"，无法复现。

### 4.6 unknown 与缺失的区分

校验报告必须区分两种情况：

| 情况 | 报告 |
|---|---|
| 字段缺失，但它有默认或可推导 | 不报 |
| 字段缺失，且无默认 | `error` |
| 字段存在但无法解析 | `error` + 原值 |

**不允许"字段缺失但静默用空值"**——那正是 H3/H4 要防的。

<a id="what-is-not-checked"></a>

## 五、校验器不检查什么

明确说明，避免虚假安全感：

| 不检查 | 原因 | 由谁保证 |
|---|---|---|
| 领域规则的业务正确性 | 无法静态判定 | 测试与 fixture |
| 数值平衡 | 无法静态判定 | 调参与试玩 |
| 跨域流程的语义完整性 | 需要运行 | 验收用例 |
| C++/Python 实现等价 | 需要执行 | 固定向量测试 |
| 性能 | 需要测量 | 基准测试 |

校验器挡住的是**结构错误**，不是**逻辑错误**。
