# 01-规则包总纲

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

规则包是**设定**。它不含机制，不含逻辑，不含写权。

---

<a id="definition"></a>

## 一、规则包是什么

```text
pack_id            identifier
pack_version       语义化版本
parent_pack        null | pack_ref       支持覆盖叠层
content:
  entity_types         实体类型与构成槽位
  pool_defs            池的界、初值、积分方式、滞回阈值
  machine_defs         状态集、转移表、条件引用
  temporal_effect_defs 效果定义
  impact_profiles      受击剖面（路由）
  aggregation_models   聚合与 refold 模型
  model_bindings       模型与目标类型的适用绑定
  command_catalog      命令目录
  default_fact_types   FactType 模板（非实例）
```

---

<a id="no-logic"></a>

## 二、规则包不能带逻辑

### 为什么这是硬约束

v1 已要求两件事：

1. C++ 与 Python 用固定输入向量验证**逐位等价**；
2. 历史回放用旧版本，不按新公式重算。

一个能让 C++ 和 Python 跑出逐位相同结果的 DSL，本身就是一个多月的确定性工程。它还要处理：浮点一致性、容器遍历顺序、随机数算法、异常语义、内存布局差异。

**这份成本与收益不成比例。** 规则包的价值在于"换设定不用改代码"，而设定（界值、阈值、状态集、层序、参数）本来就不需要逻辑。

### 允许 / 不允许

| 允许 | 不允许 |
|---|---|
| 参数、曲线、查表 | 条件分支、循环 |
| 状态集与转移表 | 任意表达式求值 |
| 层序与引用 | 函数调用、脚本 |
| 阈值与滞回带 | 访问外部状态 |
| 模型引用（含参数） | 内联公式代码 |

### 两个合法逃生口

设定里确实会有"需要一点计算"的地方。两个正当出口：

1. **注册 Resolver**：把计算写成代码，注册为 L4 的 `model_id`，由规则包**引用**。代码不在包里，在包里只有引用。
2. **数据表**：曲线、插值表、分段常数——这些是数据，不是逻辑。

```text
✗ pack: { "damage_formula": "if (armor > 0) { dmg * 0.5 } else { dmg }" }
✓ pack: { "damage_model_ref": "damage_mitigation_v3", "params": { "armor_ratio": 0.5 } }
```

第二种里 `damage_mitigation_v3` 是已注册的 Resolver，参数在包里。

<a id="versioning"></a>

## 三、版本、继承、迁移

### 整包替换

```text
pack: han_realistic@2.1     →  换为 pack: fantasy_lite@1.0
```

适用于"换一套设定"。

### 覆盖叠层

```text
parent: han_realistic@2.1
override: zhaoling_siege_tuning@1.0
```

只覆盖差异项。适用于局部调整。

**覆盖只能收窄，不能放宽安全约束**：不能覆盖 `visibility` 必需性、不能覆盖 `unknown_policy` 的默认。

### 存档固定版本

存档记录**完整的包解析路径**，不是只记 pack_id：

```text
resolved_packs:
  - han_realistic@2.1
  - zhaoling_siege_tuning@1.0
content_hash: sha256...
```

### 升级用迁移事件

不允许"用新版本重新解释旧存档"。升级产生显式的迁移事件：

```text
pack.migrated  { from: [{pack, version}], to: [...], migration_ref, affected_fact_types[] }
```

回放时按事件流顺序应用：旧事件用旧包解释，迁移事件之后用新包。

<a id="boundaries"></a>

## 四、规则包的边界

四条不能越：

1. **不能违反原语不变量。** 包不能声明"这个池可以负数"。
2. **不能声明跨 Owner 写权。** 受击剖面只能指向已注册 FactType 及其既有 Owner。
3. **不能定义新原语。** 只能用六个。
4. **不能改变可见性必需性。** 为某 FactType 省略 `visibility` 是拒绝，不是默认。

<a id="loading"></a>

## 五、加载与编译

规则包在加载时编译，运行时不做解释：

```
load → schema 校验 → 静态检查 → 编译为扁平表 → 槽位索引
```

编译产物：

| 编译对象 | 产物 |
|---|---|
| 池定义 | 边界表、积分参数表、滞回带表 |
| 状态机 | 转移矩阵（状态×事件 → 目标态） |
| 受击剖面 | 层序表（按 resolution_order 扁平化） |
| 绑定 | 目标类型 → 模型列表的查找表 |
| 命令目录 | 命令 → 处理 Owner 的路由表 |

**热路径不跑脚本、不做字符串查找、不做类型判断。**

性能前提见 [性能基准](../09-验收/03-性能基准.md)。

<a id="what-pack-cannot-do"></a>

## 六、规则包做不到的三件事

明确说明，避免期待错位：

1. **不能通用化规则密集领域。** 市场撮合、指挥继任、政治承认、通信失真，这些必须留在原生 Owner 的代码里。
2. **不能消除新增 Owner 的需求。** 若是全新的独立事实域，仍需要新 Owner。
3. **不能让新玩法零成本。** 新玩法仍是新的 `play_pattern`，只是成本从"写 runtime"降为"写声明"。

规则包的收益边界就是这三条。超出这个边界去设计，会得到一个既复杂又不够用的配置系统。
