# 02-结算顺序

- 版本：1.0
- 状态：已定义
- 上级：[架构入口](../README.md)

本文件修掉 v1 中最严重的一处实现级风险。

---

<a id="problem"></a>

## 一、问题

v1 的 [跨 Owner 结算](../../_backups/architecture_v1_20261103_1241/04-模型与结算/02-数值状态效果与跨Owner结算.md) 对同一个命中给了两条路径：

> Status Owner 使用同批次已授权的 Body 结果……**或**分阶段流程中已提交的 Body revision

> 伤害、伤势与由其触发的效果可在同一批次提交……**若分阶段提交**，Status 必须读取已提交的 Body revision

两种模式的**输入不同**：

| 模式 | Status 看到的 Body 状态 |
|---|---|
| 同批次 | 本批次 Body 的裁定结果 |
| 分阶段 | 已提交的 Body revision——中间可能又落了一次治疗或另一次伤害 |

**同一个物理事件会结算出不同的流血严重度。**

而部署模式会在运行时切换（本地权威 ↔ 仅后端 store，断线还有降级路径）。于是"同一物理事件，在两种配置下得出不同结果"。

v1 同时强要求 C++ / Python 固定向量等价，因此这是一处自相矛盾。

---

<a id="solution"></a>

## 二、解法：结算顺序是数据

每个 FactType 必须有 `resolution_order`：**同 scope 内的稠密唯一整数**。

```text
scope: county:zhaoling / epoch 7
  10  character:char-07:armor-durability    Equipment 防护
  20  character:char-07:health              Body 伤害
  30  character:char-07:status-bleeding     Status 效果
  40  character:char-07:lifestate           LifeState 判定
  50  unit:gate-east:morale                 Morale 士气
```

规则：

1. 稠密：无空洞，便于校验与比较。
2. 唯一：同 scope 内不允许重复。
3. 只由管线拓扑生成，包作者不能手填。
4. 同一 pipeline 的所有 layer 共享同一顺序表。

### 同批次 vs 分阶段

有了顺序表，两种模式必须**产生同一结果**：

```
同批次：
  按 resolution_order 依次执行，每步的输入是"本批次内已算完的前序结果"
分阶段：
  按同一 resolution_order 提交，每步的输入是"前序已提交的 revision"
```

差别只在提交时机，不在读取内容。**若两者结果不同，即为架构缺陷。**

这需要一条硬约束：**分阶段模式下，若某步读取的前序 revision 不是本批次最后一次提交的 revision，必须拒绝并重新排期**。否则中间插入的治疗会造成语义漂移。

<a id="generation"></a>

## 三、顺序由拓扑生成

包作者声明的是**偏序**，系统生成全序：

```text
resolve_order:
  before: [ [equipment:armor-durability, body:health],
            [body:health,              status:bleeding],
            [status:bleeding,          lifestate] ]
  unrelated: [ morale ]        # 与上述无依赖，排在最后
```

生成规则：

1. 检查偏序无环（有环 → 拒绝）。
2. 对无依赖关系的事实，按 `owner_ref` 字典序稳定排列——**保证确定性，不表示语义优先**。
3. 输出稠密整数，写入注册表。

**为什么不让包作者手填整数**：手填会撞车、会留空洞、会在包升级时漂移。声明偏序 + 自动生成既安全又表达力足够。

---

<a id="determinism"></a>

## 四、确定性要求

同一组输入、同一 resolution_order，任意宿主必须得到同一结果。

要求：

| 项 | 约束 |
|---|---|
| 浮点 | 规则包声明精度；比较用固定 epsilon 或全用定点 |
| 随机 | seed 策略固定在 L0，不由模型自选 |
| 遍历顺序 | 一律按生成的全序，不用字典顺序（Python 与 C++ 差异源） |
| 时间 | 一律用 `world_tick` 整数，不用浮点秒 |
| 缺失 | `unknown` 显式传播，不静默跳过 |

**最容易被忽略的是第三条**：Python 的 dict 保序而 C++ 的 `unordered_map` 不保序。遍历顺序必须来自注册表的顺序表，不能来自容器的自然顺序。

<a id="cross-scope"></a>

## 五、跨 scope 的顺序

不同 scope 的事实可以并行，但跨 scope 的写入必须显式声明依赖：

```
fact:character:char-07:health      scope = self
fact:unit:gate-east:morale         scope = group:gate-east
```

士气读取成员伤亡（跨 scope）。规则：

- 跨 scope 读取**必须**用已提交 revision，不接受同批次前序（因为 scope 不同，批次边界不同）。
- 若需同批次语义，必须声明为同一 pipeline 且同提交端。

这是"伤亡 → 士气"必须是异步订阅而非同批次结算的原因（见 [组合总纲](../07-玩法组合/01-组合总纲.md)）。

<a id="what-it-fixes"></a>

## 六、这条修掉了什么

| v1 问题 | 修复 |
|---|---|
| 同批次 vs 分阶段结果可能不同 | 统一顺序表 + 前序 revision 校验 |
| 结算顺序只存在于散文 | 变成注册表里的稠密整数 |
| C++ / Python 遍历顺序可能不同 | 顺序不来自容器 |
| "版本化的稳定结算顺序"从未定义 | 由偏序拓扑生成，可校验 |

<a id="acceptance"></a>

## 七、验收

| # | 用例 | 期望 |
|---|---|---|
| O1 | 偏序有环 | 注册拒绝 |
| O2 | 两 FactType 同 scope 同序 | 注册拒绝 |
| O3 | 同批次与分阶段跑同一次命中 | 流血严重度相同 |
| O4 | 分阶段中间插入治疗 | 检测到 revision 不一致，拒绝重排，不产生错误结果 |
| O5 | C++ 与 Python 跑固定向量 | 逐位相同 |
| O6 | 包升级后顺序变化 | 历史回放用旧顺序，不受影响 |
| O7 | 跨 scope 同批次请求 | 注册拒绝，要求改为异步订阅 |
