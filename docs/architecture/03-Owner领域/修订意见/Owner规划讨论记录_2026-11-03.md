## 2. 对草案 23 Owner 的审视（轮次 1）

### 2.1 更正的早期判断

| 早期说法 | 读完文档后 |
|---|---|
| 近场命中要 5–6 个 Owner 原子提交，代价太大 | 撤回。草案已规定近场 Combat/Body/Equipment/Status/LifeState/Morale 同驻 UE，本地调用、同一提交端，"分域不等于分进程" |
| Facility 与 Production 应拆开 | 草案已用"V2 先交付城防子域、F 交付完整生产链"处理 |
| 环境事实无归属 | 草案已登记为待决 D12，属有意挂起 |
| 名单外权威缺注册 | 草案要求 A1 映射 Clock/Identity/Capability 写入口，方向已有 |

### 2.2 发现的草案问题

1. **命令类型与 Owner 不一一对应**：`retreat` 同在 Combat、Morale 下，Presence 另有 `withdraw`；Morale 有 `advance/hold`；`rest` 同在 Survival 与 Population；`consume_supply` 与 Inventory `consume` 重叠。Gateway 按类型路由，会有歧义。
2. **在途消息归属不清**：命令传递归 Dispatch、报告传播归 Information，物理过程相同却分属两处。
3. **"谁知道什么"双写**：Information 拥有"已确认知情范围"，角色记忆账也记录收到了什么。
4. **授权三处来源，Capability 事实范围未定义**：Organization、Government、Capability 都在授权；基线表把 Ability 列为 Owner，注册表又说不是。
5. **Workflow 有持久状态但无登记规则**：如 Medical 的步骤与开放义务。
6. **Territory 依赖晚于它的批次**：控制转移需要政治承认，而 Politics 在 E/F 才交付。
7. **时间权威措辞矛盾**：部分正文仍写"`world_tick` 只能来自 UE 战场时钟"，与"WRK 拥有唯一 `world_tick`"冲突。
8. **Gateway 在时序图里充当编排者**；命令送达后直接交给 Morale，而非由 Agent/群体接受后再发命令。
9. **命名混淆**：Body/Resource 与 Inventory/Resource 都叫 Resource。

### 2.3 与"先建基础设施"的冲突

- 执行计划 §12.1 选择的是双轨并行，与"先完整建基础设施"相反。
- A2 要求冻结 23 Owner 写权地图，与"Owner 不是固定事实"冲突。建议只冻结与具体 Owner 无关的公共信封与模型注册，Owner 名单做成带版本的注册表。
- 23 个 Owner 都要完整交付包，交付量大。建议分"登记级"和"实现级"。

## 5. 需求提炼（轮次 4）

**T 时间与世界**
- T1 所有层共用一个世界时钟；切换工作层/镜头/地图不暂停、不传送、不撤销结果。
- T2 主动暂停为完整时停，只能编辑草稿，恢复后重新校验，不产生新信息。
- T3 节奏分即时、短周期、日、旬/季；核心窗口约 30 世界日，不能跳天绕过结算。
- T4 存档可跨多日；保存、暂停、断线是三件不同的事。
- T5 远场用同一核心规则低精度推进；离场后照常运转；近远场切换不复制身份、不新造历史。
- T6 容量可扩展到五阶段（十三州人口与资源网络），只扩内容、不补基建。

**A 身份、权限与指挥**
- A1 身份是推导状态。
- A2 四类权限来源（职务、上级授权、所有者委托、部曲认可），可撤销、到期、条件失效。
- A3 到场不等于有权；亲卫编入军阵服从编队指挥；紧急召回需预先登记条件。
- A4 权限、通信、意愿、事实分开判断。
- A5 可达性四级：直达、经中继、仅能依预案、失联。
- A6 指挥权轮替：检测失能→依次校验候选→幂等交接不扩权→无合格者自治降级。
- A7 军制分层，预案可训练、有版本、可继承。
- A8 自治优先序：有效命令 > 训练过的预案 > 继任链 > 训练/士气/补给/疲劳/性格。

**C 通信与信息**
- C1 命令状态：草拟、已发出、传递中、已抵达、已理解、已接受、执行中、完成、拒绝、过期、取消。
- C2 媒介受距离、识字、视线、截获、失真约束。
- C3 验证制度（口令、信物、双传令、封泥），破译需投入，伪造留证据。
- C4 三本账、三种时间。
- C5 只能经合法渠道获知；失联后保留最后已知且不确定性增大；事实/推断/未知分开。
- C6 报告的发出与送达是事实，内容可以是假的。
- C7 通知说明谁、何时、何来源、何可信度。

**M 军事与战场**
- M1 队伍状态：士气、疲劳、训练、补给、阵型、指挥、军旗、撤退意愿；玩家只能间接改变。
- M2 个人意愿、军心、战斗士气、民心四者独立。
- M3 兵种 = 装备 + 训练 + 组织来源 + 忠诚 + 战术角色。
- M4 战场目标有归属、状态、压力、有效性。
- M5 器械有控制者、操作人员、补给、损坏状态。

**B 身体与战斗**
- B1 伤害链：尝试→命中/格挡→装备防护与耐久→伤害应用→持续状态→倒地/濒死/死亡/俘获；评估与应用是两个事实。
- B2 近场反馈即时，不等后端或 Agent；并发不超支。
- B3 身体分层：需求压力、疲劳、疾病风险、伤势、有效能力、恢复速度；后果连续。
- B4 救治：转运、排队、预留，消费/治疗/状态分别确认。

**R 资源与经济**
- R1 资源记录种类、质量、数量、容器、储存条件、污染损坏、位置、预留。
- R2 产权、保管、事实控制、军事占领、市场影响力五种关系独立。
- R3 账面库存与有效供应分开；损耗模型因资源而异。
- R4 生产含设施、设备、工匠、原料、工序、认证；中断留原因；拆解有代价。
- R5 运输：预留、承运人、路线阶段、护送、阻塞、改道、截获、损失、入库回执；不能瞬移。
- R6 市场只有现货；个人账与领地账分开。

**P 人口与社会**
- P1 人口不是可替换数字；转岗保留身份、伤病、关系。
- P2 同一人不能同时做互斥岗位；转岗可被拒绝。
- P3 关系受身份、亲缘、记忆、利益、声望、信任约束。
- P4 抗命/改写的后果分别落到任务、军纪、信任、声望、关系、后续授权。
- P5 细作有身份、会暴露、有证据链。

**G 治理与政治**
- G1 影响力按（主体、对象群体、领域、辖域、时间）计算。
- G2 统治力五态（未形成、形成中、生效、争议、崩解，带滞后）；占领四阶段。
- G3 治理闭环：目标、预算、责任人、核查。
- G4 政令（封锁、征发、配给、税、治安）；外交中公开承诺与私下意图分开。

**S 智能体与剧本**
- S1 关键角色激活 Agent，日常走脚本预案；司命只提候选；群体 B0/B1；同一时刻唯一推进者。
- S2 胜利：援军抵达交接或敌退；失败：失守后投降、玩家死亡、玩家逃离；胜负只读已确认事实。
- S3 战役阶段、历史压力点、跨阶段 checkpoint 继承。

**X 系统性**
- X1 唯一写者；统一 Command 入口，无特权旁路。
- X2 revision、幂等、receipt、replay、checkpoint、recovery、本地可靠提交；断线不扩权。
- X3 模型三类，有绑定、有版本，unknown 合法，结果确定。
- X4 可见结果可沿"意图→传达→事实→获知→表现"追溯。
- X5 单人 PC，不依赖联网服务。

## 7. 负责人的四点意见与重新设计（轮次 5）

### 7.1 意见

1. Body 这样设计，忽略了**非生命体的伤害**怎么结算。
2. 这样 Body 玩法就**固定**了，没法轻松换设定。
3. 需要其他 Body 相关资源怎么办，比如**精神力、士气**和其他状态？
4. 不是只为 Demo 设计，要为**完整基础设施**设计；Demo 只是证明 Owner 组合玩法可行。

根本问题：上一版把领域语义写死在 Owner 里，用基础设施固定了玩法设定。

### 7.2 三层架构

```
L0 内核      时钟 · 身份 · EventStore/revision/receipt · Gateway · 投影 · 模型注册 · 写权登记与迁移 · 暂停/恢复
L1 事实原语  数值池 · 属性修正 · 效果 · 状态机 · 容器 · 关系 · 过程 · 空间     ← 只管机制与不变量
L2 规则包    实体类型 · 构成 · 池定义 · 效果定义 · 状态机 · 受击剖面 · 模型 · 命令目录  ← 设定，有版本可替换
L3 Owner 注册  哪类事实 × 哪些实体 × 由谁写 × 宿主 × 近/远场                ← 写权划分
L4 玩法组合  交互管线 · 工作流 · 订阅
```

### 7.3 事实原语

| 原语 | 不变量 | 生命体例 | 非生命体/集体例 |
|---|---|---|---|
| 实体与构成 | 稳定 ID；类型声明构成 | 人、马 | 城门、冲车、粮车、队伍、人群 |
| 数值池 | 有界；预留后消耗不超支；窗口积分；阈值滞回 | 生命、体力、精神力、个人士气 | 门扇耐久、城墙完整度、燃料、队伍士气 |
| 属性与修正 | 只存基础值，有效值为投影 | 力量、速度 | 防护等级、通行速度 |
| 效果实例 | 来源、层数、持续、tick；tick 时向池的 Owner 发请求 | 流血、恐慌 | 燃烧、受潮、锈蚀 |
| 状态机 | 合法转移、条件有版本 | 存活/倒地/濒死/死亡 | 完好/破口/废墟；门开关闩；阵型 |
| 容器与堆叠 | 守恒；预留与转移原子 | 随身物品 | 仓库、车厢、账户 |
| 关系与凭据 | 有效期、可撤销、作用范围 | 亲缘、忠诚、授权 | 产权、保管、控制 |
| 过程 | 步骤幂等、进度、开放义务、可中断恢复 | 治疗、训练 | 传令、运输、修缮、生产 |
| 空间 | 占用、通行、到达有语义提交点 | 人的位置 | 车、器械、队伍位置 |

心智单独一本账，不属于世界真相原语。

### 7.4 冲击管线（解决非生命体伤害）

交战 Resolver 只产出**冲击**（来源、伤害类型与数值、作用部位、证据），由目标类型的**受击剖面**决定结算：

| 目标 | 受击剖面 |
|---|---|
| 士兵 | 盾 → 甲 → 部位 → 生命池与伤势 → 流血效果 → 生命周期 |
| 城门 | 门扇 → 门闩 → 完整度阈值转破口 → 空间通行性改变 |
| 冲车 | 防护棚 → 结构 → 不可移动/残骸 |
| 粮车 | 车体 → 货物容器折算货损 → 火焰挂燃烧 |
| 仓库着火 | 火场效果 tick 产生冲击 → 建筑完整度 → 物资质量下降 |

每层由该事实的 Owner 产出授权片段；同宿主合成一个原子批次，跨宿主走开放义务。新增可受伤实体只需写剖面。

### 7.5 规则包（解决换设定与新资源）

- **加精神力**：新增池定义，写清挂在哪个构成、恢复模型与节奏、谁消耗、谁扣减、阈值触发什么。内核与引擎不改。
- **士气**：同一池定义挂在个人和队伍上，队伍用聚合模型；仍与 Agent 主观恐惧分账。
- **换设定**：换整包或叠覆盖包；剧本绑定包版本，存档固定版本，升级用迁移事件。
- **边界**：不能违反原语不变量，不能跨 Owner 写；缺输入只能返回 unknown。

### 7.6 Owner 的新含义

Owner = 一条登记项：事实类型 × 实体范围 × 宿主与 epoch。写权最小粒度是"某实体的某类事实"。划分判据：必须原子一起改的放一起；节奏/宿主不同、迁移单位不同、可见性/安全要求不同的拆开。草案 23 Owner 只是其中一种划分。

### 7.7 完整基础设施清单

- L0 内核（沿用草案）
- L1 原语引擎：每个原语统一规格（不变量、命令语义、事件 schema、积分切窗、聚合精度、提交片段格式）
- 规则包工具链：schema 校验、静态检查（越权、缺剖面层、绑定冲突）、热加载、固定向量测试（C++/Python 等价）、版本迁移
- 写权登记：登记、迁移、fencing
- 组合层：管线描述、订阅、工作流、开放义务
- 投影：派生属性、受限查询、因果追溯
- 存储与性能：UE 侧批量存储（SoA/Mass 风格）需早定

### 7.8 Demo 应证明的组合性证据

1. 同一池引擎、同一冲击管线同时结算士兵和城门。
2. 只加规则包即可加入新资源或改变受击行为，内核零改动。
3. 同一过程原语复用于传令、运输、修缮。
4. 跨 Owner 组合：原子批次 + 异步订阅（伤亡→士气→阵型）。
5. 只改登记就能迁移某类事实，回放一致。
6. 个体与聚合精度往返切换，总量与身份守恒。
7. 换规则包版本后旧存档仍按旧版本回放。

## 8. 与原方案的对照（轮次 6）

公共底座（Command、EventStore、WRK、三本账、epoch/lease、暂停、回放）完全沿用草案；替换的只是"Owner 领域"与"模型与结算"两部分。

| 维度 | 原方案（草案 23 Owner） | 新方案（原语 + 规则包 + 登记） |
|---|---|---|
| 基本单位 | 23 个领域 Owner | 8 个原语 + 规则包 + 写权登记 |
| 设定位置 | Owner 合同 + 领域内模型 | 规则包；原语不含设定 |
| 加精神力 | 定归属 → 改合同、写权矩阵、节奏矩阵、模型包、交付证据，或新建 Owner | 加一条池定义 |
| 士气 | 独立 Morale Owner 自行实现 | 同一池原语挂个人与队伍，聚合模型 |
| 非生命体受伤 | 只定义了角色伤害链，城门/器械/粮车未定义 | 冲击管线 + 受击剖面 |
| 重复实现 | 多个 Owner 各自实现有界数值、阈值、tick、积分 | 原语实现一次 |
| Owner 名单 | A2 冻结 | 登记可改，epoch 迁移 |
| 远场聚合 | 各 Owner 自理或交 Population | 原语自带 |
| 交付量 | 23 份完整交付包 | 8 个原语完整验证 + 工具链；登记轻量 |
| Demo 证明 | 内容切片可玩 | Owner 可组合出玩法 |

**优势**：能换设定；加资源/状态/可受伤实体只是加数据；机制一致；写权划分不过早定死；不变量测试只做一次。

**代价与风险**：
1. 前期投入大、出效果晚；原语设计错误影响全局。
2. 只能通用化状态，不能通用化规则：市场撮合、指挥继任、政治承认、通信失真仍需领域 Resolver。治理、经济、外交收益较小。
3. 与 Paralls 现有按领域写的 authority 距离更远，需拆分或适配。
4. 可读性与调试更难，需命名规范、投影视图、调试工具。
5. 通用结构的性能需要批量存储才能保证。
6. 登记项数量多，需工具与静态检查。
7. 规则包"只用数据"还是"允许脚本"需尽早决定。

**两者关系**：新方案不推翻原方案，而是把 23 Owner 从"基础设施"降为第一份配置。身体、状态、生命周期、装备、设施、士气、生存可写成"汉末写实"默认规则包 + 默认登记；Dispatch、Organization、Economy、Politics 等规则密集领域基本保持领域 Owner 形态，改为基于关系、过程、容器原语存状态。收益集中在"数值—效果—状态"主干。

## 9. 性能影响分析（轮次 7）

结论：新方案**不会自动更快**。它的性能上限更高，因为同类计算集中一处，可统一批量化、聚合与存储优化；但若规则包运行时逐条解释，会比专用代码慢。前提是加入"规则包加载时编译"环节。以下分析无实测数据。

### 9.1 压力热点

近场每帧计算（体力积分、效果 tick、士气、命中）；远场规模（县城约 5 万人口口径，五阶段十三州）；事件量（存储、回放、checkpoint）；Bridge 同步。

### 9.2 可能的提升

| 方面 | 原方案 | 新方案 |
|---|---|---|
| 数据布局 | 6 套结构各自优化 | 同一池定义存为连续数组（SoA），批量处理；UE 对应 Mass Fragment，Python 用 numpy |
| 调度 | 各 Owner 自有定时器 | 统一调度按节奏分桶；稳定池用"变化率 + 起始时间"惰性求值 |
| 命中链 | 同进程，但 4–6 个 Owner 片段协调 | 剖面编译为扁平分层表，一个循环产出一个批次 |
| 远场聚合（收益最大） | 各自决定 | 池原语自带分布精度，千人队伍只存几组统计量 |
| 事件与存档 | 各领域格式 | 统一增量事件，同窗口合并；checkpoint 整块导出数组 |
| 同步 | 每 Owner 一套序列化 | 单一差量编码路径 |

### 9.3 代价与缓解

| 代价 | 缓解 |
|---|---|
| 间接寻址 | 加载时编译为槽位索引表，运行时整数下标访问 |
| 解释执行 | 编译为扁平表或字节码，热路径不跑脚本 |
| 写权检查频繁 | 按批次和作用域检查一次，epoch 缓存 |
| 事件更大 | 定义表 + 整数编码，版本放批次头 |
| 分析器难定位 | 按池定义打统计标签 |

### 9.4 对比

- 近场单次命中：量级相近，新方案协调开销略优（需剖面已编译）。
- 近场大量 Actor 持续计算：新方案更好。
- 远场与五阶段规模：新方案明显更好。
- 原型阶段：原方案更快跑起来、更好调。

### 9.5 建议的基准测试（原语定稿前）

与"手写专用结构"对比：
1. 100/500 近场 Actor，每个 3 池 + 5 效果，每帧耗时。
2. 单次命中 4 层剖面，结算到提交耗时。
3. 1 万远场实体，个体存储 vs 分布存储的内存与窗口耗时。
4. 30 世界日事件流的回放速度与 checkpoint 大小。

若编译后通用实现慢不到一两成，同时远场聚合有数量级收益，新方案在性能上成立；否则考虑混合：热路径池用专用结构，其余用原语。
