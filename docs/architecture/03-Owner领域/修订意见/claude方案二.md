下面改成三层：**通用事实原语（引擎）、规则包（设定数据）、Owner 注册（写权划分）**。Owner 不再是一份固定名单，而是基于原语、由配置组装出来的写权单元。

# 一、分层

```
L0 内核      时钟 · 身份 · EventStore/revision/receipt · Command Gateway · 投影 · 模型注册 · 写权登记与迁移 · 暂停/恢复
L1 事实原语  数值池 · 属性修正 · 效果 · 状态机 · 容器 · 关系 · 过程 · 空间        ← 只管机制和不变量，不含任何设定
L2 规则包    实体类型 · 构成 · 池定义 · 效果定义 · 状态机 · 受击剖面 · 模型 · 命令目录   ← 设定在这一层，有版本、可替换
L3 Owner 注册  哪类事实、在哪些实体上、由谁写、宿主在哪、近场还是远场                 ← 写权划分，按配置决定
L4 玩法组合  交互管线 · 工作流 · 订阅                                                ← 守城、传令、补给都是组合出来的
```

# 二、事实原语

| 原语 | 保证的不变量 | 生命体上的例子 | 非生命体或集体上的例子 |
|---|---|---|---|
| **实体与构成** | 稳定 ID；实体类型声明自己有哪些构成 | 人、马 | 城门、冲车、粮车、仓区、队伍、人群 |
| **数值池** | 有上下界；预留后才消耗，不会超支；连续变化按窗口积分；阈值带滞回 | 生命、体力、**精神力**、**个人士气**、饱食 | 门扇耐久、城墙完整度、器械结构、燃料、**队伍士气** |
| **属性与修正** | 只存基础值，有效值由修正源推导（是投影，不存储） | 力量、速度 | 防护等级、通行速度 |
| **效果实例** | 记录来源、层数、持续时间和 tick 规则；tick 时向目标池的 Owner 发请求，自己不直接写别人的池 | 流血、恐慌、鼓舞 | 燃烧、受潮、锈蚀 |
| **状态机** | 只允许合法转移，转移条件有版本 | 存活/倒地/濒死/死亡 | 完好/破损/破口/废墟；门开/关/闩；阵型状态 |
| **容器与堆叠** | 总量守恒，预留和转移是原子操作 | 随身携带的物品 | 仓库、车厢、账户 |
| **关系与凭据** | 有有效期，可撤销，有作用范围 | 亲缘、忠诚、授权 | 产权、保管、控制 |
| **过程** | 每一步都幂等，有进度和开放义务，可以中断和恢复 | 治疗、训练 | 传令、运输、修缮、生产 |
| **空间** | 占用、通行和到达有语义提交点 | 人的位置 | 车、器械、队伍的位置 |

心智（记忆、信念）单独一本账，不属于世界真相原语。

# 三、对任意实体的伤害：冲击管线

战斗 Resolver 只产出一次**冲击**，内容包括来源、伤害类型与数值、作用部位和证据。它不需要知道打中的是人还是门。

具体怎么结算，由目标的实体类型在规则包里声明的**受击剖面**决定：

| 目标 | 受击剖面（按层顺序） |
|---|---|
| 士兵 | 盾（耐久池）→ 甲（耐久池，减伤模型）→ 部位 → 生命池和伤势 → 按阈值挂流血效果 → 生命周期状态机 |
| 城门 | 门扇（耐久池）→ 门闩（耐久池）→ 完整度低于阈值时转为破口状态 → 空间的通行性随之改变 |
| 冲车 | 防护棚（耐久池）→ 结构（耐久池）→ 进入不可移动或残骸状态 |
| 粮车 | 车体（耐久池）→ 货物容器（按伤害类型折算货损）→ 火焰类型额外挂燃烧效果 |
| 仓库着火 | 环境火场效果按 tick 产生冲击 → 建筑完整度 → 容器内物资质量下降 |

每一层由该层事实的 Owner 产出各自授权的结果片段。同一宿主内的多层合成一个原子批次提交，跨宿主时走开放义务。**新增一类可受伤的东西，只需要写一份剖面，不用改战斗、不用改 Owner。**

# 四、换设定：规则包

规则包是一组带版本的数据。实体类型、池定义、效果、状态机、剖面、模型和绑定、命令目录、默认的 Owner 划分，都在规则包里定义。

**例一：加精神力。** 规则包里新增一个池定义 `spirit`，要写的内容有：
- 挂在人的哪个构成上
- 恢复模型和节奏
- 哪些技能的成本消耗它
- 哪些效果会扣它
- 低于什么阈值时触发什么状态

**内核和引擎都不用改。**

**例二：士气。** 同一个池定义可以同时挂在个人和队伍上。队伍士气用聚合模型，读取成员和事件来计算。它是世界真相，和 Agent 主观的恐惧分属两本账，这一点不变。

**例三：换一套设定**，比如写实和偏奇幻两版。可以换整个包，也可以只叠一层覆盖包。剧本绑定某个包的版本，存档固定这个版本，升级时用迁移事件来表达。

**规则包的边界：** 不能违反原语的不变量，不能声明跨 Owner 写入。缺输入时只能返回 unknown，不能默认补成零。

# 五、Owner 现在是什么

**Owner 就是一条登记项**：哪些事实类型 × 作用在哪些实体上 × 宿主和 epoch。写权的最小粒度是“某个实体的某类事实”，比如“城门 #3 的耐久池”。怎么划分，按四条判据决定：

1. 必须原子一起改的放在一起；
2. 节奏和宿主不同的拆开；
3. 近远场迁移单位不同的拆开；
4. 可见性和安全要求不同的拆开。

举例：守城用的规则包可以默认把“人和马的池、效果、生命周期”划成一个近场 Owner，把“建筑和器械的池与状态”划成另一个。以后要拆、要合，只改登记，再走已有的 epoch 迁移流程，不改内核。草案原有的 23 个 Owner，在这套框架里只是其中一种划分。

# 六、完整基础设施清单

- **L0 内核**：草案已经列全，这次不改。
- **L1 原语引擎**：每个原语都有同一套规格，即不变量、命令语义、事件 schema、积分和切窗方式、聚合精度（例如池在队伍或人群上用“分布”表示，展开和收拢时守恒）、提交片段格式。
- **规则包工具链**：
  - schema 校验；
  - 静态检查，查越权写入、缺少剖面层、绑定冲突；
  - 编辑器内热加载；
  - 固定向量测试，同时保证 C++ 和 Python 两端结果等价；
  - 版本迁移。
- **写权登记**：登记、迁移、fencing、作用域划分。
- **组合层**：管线描述（冲击管线是第一种）、订阅、工作流、开放义务。
- **投影**：派生属性、受限查询、因果追溯。
- **存储与性能**：池和效果数量最大，UE 侧要适合批量处理（SoA 或 Mass 风格）。这一点要早定。

# 七、Demo 应该证明什么

Demo 的目标是证明“玩法可以由 Owner 组合出来”，所以验收应该是下面这些**组合性证据**，而不是内容量：

1. 同一个池引擎、同一条冲击管线，同时结算士兵和城门。
2. 只加规则包，就能加入新资源（比如精神力），或改变一类实体的受击行为，内核零改动。
3. 同一个过程原语，复用在传令、运输、修缮上。
4. 跨 Owner 组合：一个原子批次，加上异步订阅（伤亡触发士气，士气再影响阵型）。
5. 只改登记，把某类事实迁到另一个 Owner，回放结果一致。
6. 个体和聚合两种精度来回切换，池的总量和身份守恒。
7. 换了规则包版本之后，旧存档仍能按旧版本回放。

# 八、需要你们定的

1. 接受“原语、规则包、Owner 登记”这三层吗？
2. 原语清单还缺什么？比如“关系”和“凭据”要不要分成两个原语？
3. **规则包里能不能带逻辑。** 只用数据加注册模型，最容易保证确定性和两端等价，但表达力有上限。允许脚本（比如受限 DSL）更灵活，但跨 UE 和 Python 的等价性和回放成本会高很多。这一点决定工具链怎么建，建议尽早定。
4. 池和效果在 UE 侧用什么存储模型。
