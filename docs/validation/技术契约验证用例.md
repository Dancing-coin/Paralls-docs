<a id="owner-ten-checks"></a>

## 每个新 Owner 的十项门槛

### 每个新 Owner 的验收门槛

新 Owner 在接入玩法前必须证明：

1. 只有它能写入自己的事实流；
2. 命令来源、权限、能力和作用范围可审计；
3. 成功和拒绝都返回结构化 Result；
4. 旧 revision 的 Command 不会写入新状态；
5. 相同幂等键只产生一次事实事件；
6. 提交后可从事件重建状态；
7. 角色只能获得合法暴露的信息；
8. UE 表现可以从真相和行为结果重建；
9. 群体模拟只能提交被允许的低精度候选；
10. 失败、延迟、部分完成和恢复不会丢失世界时间或责任归属。

<a id="compatibility-checks"></a>

## 传统能力与 Paralls 八项验收

### 验收标准

文档所定义的基建在第一阶段至少要能证明：

1. 玩家发出守城命令后，能看到命令经过合法传令节点，而不是瞬间修改队伍状态。
2. 命令可因失效、权限、阻挡、通信中断或目标已变更而被拒绝，并保留原因。
3. 玩家、传令兵、守军和运输队的事实状态有唯一 Owner，Actor 只是投影或局部执行器。
4. 玩家站在运输路线、运输遭遇攻击或路线被堵时，能形成等待、绕行、拦截或货损结果。
5. 近场动画提供即时反馈，但最终命中、伤害、死亡、入库和胜负均有 Owner receipt。
6. 暂停后所有世界推进停止，恢复后从相同 `world_tick` 继续，旧结果不会越权写回。
7. 能从事件账和 checkpoint 重建阶段性状态，并能解释一次命令、战斗或运输结果的因果链。
8. 第一阶段的胜利路径包括援军抵达或敌军提前撤退；失败路径包括失守后的投降、死亡或逃跑。

<a id="owner-landing-checks"></a>

## Owner 三项落地判据

### 落地判据

Owner 完成不能只以“类名里有 Authority”或“有一个接口”为准。至少要证明正常提交、拒绝、重复幂等、旧 revision 拒绝、事件回放、权限过滤和相邻 Owner 不变量未被破坏。

<a id="character-checks"></a>

## 角色档案与事实/心智对接验收

### 对接验收

实现前逐项记录角色字段语义、数据空间、唯一事实来源、Owner、Agent 可见范围、公式输入资格、source revision/freshness、Agent 可写范围、冲突处理和回放证据。

全量 Owner 的 UE 更新分类以[UE 协作与节奏矩阵](../architecture/05-运行时接入/01-UE本地提交与Paralls同步.md#ue-cadence-matrix)为准。角色激活只交接意图推进权，不改变 Body/LifeState 等领域写权；本地强制反应不等待 Agent，但不能借此产生未经授权的新自主策略。

<a id="settlement-checks"></a>

## 结算、实时协作与交接验收补充

### 第一阶段验收补充

第一阶段高影响闭环至少证明公式版本和输入 revision 固定、Owner 接受/拒绝有明确原因、幂等重试不重复消费、receipt 可追踪、projection 可回放。接入 UE 还要验证本地预测在拒绝/冲突后收敛。完整五阶段基础设施要求以[县城守城 Demo 执行计划](../production/县城守城Demo执行计划.md)为准。

专项验收场景：同一命中重投不重复扣血/扣耐久；流血与治疗并发不覆盖彼此数值；已死亡角色拒绝迟到治疗；药材不足不产生治疗收益；长时治疗中断按实际消费阶段结算；暂停期间不扣血/回血/消耗药物；近远场与 UE/后端交接后效果不中断、不重放 tick；提交结果未知经查询恢复；checkpoint/replay 重建生命、伤势、效果和库存一致。这些是设计要求，不代表本轮已通过运行时测试。

高频协作专项还须验收：

- 攻击、奔跑并发时体力检查与扣除不超支；连续消耗切窗后与回放一致，中途耗尽能及时影响动作。
- 在登记的延迟预算内完成命中到身体反馈、体力耗尽到动作限制、战场事件到士气/阵型反应；分别记录模拟、提交、投影和 Agent 决策耗时，不把后端或 LLM 往返放进本地反应的必经路径。
- 生命归零只产生规则依据，倒地/濒死/死亡由 LifeState 的合法转换确认；普通治疗不能覆盖已确认死亡。
- 同一次目睹伤亡在重试后只影响士气一次；未目睹且未收到报告的角色不能凭全局事件自动得知；相同士气允许不同角色判断。
- 本地权威路径在后端桥接断开后继续产生唯一 receipt，恢复后去重补同步；仅后端提交配置在断线时保持 pending，不出现第二权威。
- 在本地提交后、后端同步前模拟崩溃，恢复 checkpoint/事件/outbox 后不丢已确认结果、不重复扣血；旧 epoch 的迟到提交被拒绝。
- Agent 推理变慢或不可用时，获准动作和强制身体反应仍执行，新的自主策略按已登记降级策略处理；暂停期间这些路径全部服从时停。

Workflow/Composite 仅用于需要跨域过程的路径；单域命令和已注册实时链可经受控本地路由直接调用 Owner，不强制每次碰撞走远端 WRK、ESM 或通用协调器。

<a id="model-fixture-checks"></a>

## 模型基础设施十项 fixture

### 第一阶段基础设施验收

第一阶段不需要制作所有五阶段内容，但必须用正式 fixture 证明模型基础设施可泛化：

- 同一 Inventory Owner 分别运行食品变质和木材腐朽模型；
- 不匹配的资源标签、设施能力或作用域被拒绝；
- 数值、条件和混合模型均能固定版本并写入评估上下文；
- 模型结果只能通过 Inventory Owner 提交库存事件；
- 公式升级后旧事件仍按旧版本 replay；
- 绑定停用后新窗口不再评估旧模型；
- 两个损耗模型不会在同一库存 revision 上重复扣减；
- 删除投影后可从事件流重建模型导致的库存结果；
- 暂停期间不推进模型评估、tick 或状态转移；
- Bridge 断线、重复投递和未知结果不会重复消费库存。

## 合同、EventStore、WRK 与查询验收

<a id="gate-0"></a>

### 阶段 0：基线盘点和证据规范


**验收：** 不修改受保护关卡；能说明当前实现、规划能力和缺口；所有 Owner 均有明确的当前/规划状态，不把 planned 当作 current；有一次定向 PIE 截图、日志和 Actor 数量记录。

<a id="gate-1"></a>

### 阶段 1：五阶段 Owner 与公共合同冻结



**验收：** 23 个 Owner 的 Registry、write set、公共合同、宿主/节奏矩阵与 ESM 迁移映射齐全且无重叠写权；schema 能表达成功、拒绝、过期、部分完成、取消、损失和恢复结果，Static Data、模型输入单位/版本、Binding、revision 和 Evaluation Context 可固定，并通过类型/合同 fixture 检查。按领域定义适用的模型、非法绑定、幂等、旧 revision/epoch/lease 与恢复用例，不强迫每个领域都有同一种模型。此门冻结合同；模型实际运行、重复命令仅一批事实、版本冲突拒绝等运行保证由阶段 2—4 随对应纵向切片逐项提供执行证据，不能在合同门提前宣称全量实现完成。

<a id="gate-2"></a>

### 阶段 2：EventStore、WRK 和恢复内核



**验收：** 暂停屏障生效后不提交新世界事实，不应用异步结果或推进语义 handoff；外部回调可以到达隔离队列，但不得改变世界、写权或角色知识，恢复后须重新校验；恢复后从同一 tick 继续；事件流可重放所有已登记 Owner 的状态；checkpoint 后继续运行与完整 replay 的结果一致；断线和重复投递不会产生第二次事实。

<a id="gate-3"></a>

### 阶段 3：Command Gateway 和受限投影


**验收：** 人类玩家、角色 Agent 和群体模拟提交相同领域命令时走同一规则；重复幂等键只产生一个事实事件；拒绝、过期、取消和部分完成都有原因。

## 高频桥接、组织、战斗与动画能力检查

<a id="gate-5"></a>

### 阶段 5：Presence、UE Mirror 和高频桥接


**验收：** 60Hz 局部移动保持响应；到达、阻挡和绕行可提交；玩家挡住运输路线时不会瞬移；预测被拒绝时可恢复到权威状态。

<a id="gate-6"></a>

### 阶段 6：组织、军令和 Agent/Handoff


**验收：** 玩家下达求援和守城命令后能看到传令节点、理解/接受/拒绝和执行结果；玩家离开范围后队伍继续自治；指挥头目失能后可按继任链继续行动。

<a id="gate-7"></a>

### 阶段 7：Combat、Morale、Formation


**验收：** 攻击动画即时响应；Combat、Equipment、Body、Status 分别返回命中/伤害评估、防护耐久、身体变化和效果回执；至少一次阵型变化和士气变化可回溯；单骑冲锋不能稳定替代组织协同。

<a id="gate-8"></a>

### 阶段 8：Objective 和胜负闭环


**验收：** 至少验证援军胜利、敌军提前撤退胜利、投降失败、死亡失败、逃跑失败五条结局；Objective Owner 能指出触发事件和 receipt。

<a id="gate-9"></a>

### 阶段 9：资源、运输、生产和生存


**验收：** 资源能经过生产/储存/运输/入库/配给/消费产生连续后果；运输阻挡、敌袭和损失可观察；拆解房屋或农具获得材料会损伤原设施或工具；生产停工有可解释原因。

<a id="gate-10"></a>

### 阶段 10：Agent—动画—表现一致性


**验收：** 关键角色在玩家视野内能依据命令、状态和环境改变动作；离开视野降级后再回来不重置身份、位置和记忆；暂停时动画和 Agent 同时冻结。

玩家应能在地图上看到实际执行状态，并通过战报或追问获知“原目标已失效/侧翼暴露/通信中断”等自然原因；以下反例按可观察结果检查，不据示意文字登记运行通过。

<a id="fidelity-protocol-checks"></a>

## Fidelity 协议、时停、可玩链与证据产物

“激活角色智能体的动画表现持续”并不是看 Agent 是否还活着，而是看**角色是否仍有未完成的认知责任，以及 UE 是否仍有未完成的空间/表现责任**。两边责任都结束后才允许完整降级；任何一边仍有责任，另一边都必须通过共享 `action_ref`、`world_tick` 和 `handoff_id` 保持可重建的连续性。

### 验证方案

第一阶段不以“画面上人都在动”作为完成标准，而以连续性和 Owner 边界的证据为准。

### 协议验证

- 同一 `character_id` 远/中/近转层不生成第二身份；
- duplicate `handoff_id` 和 `idempotency_key` 不重复创建 Actor、lease 或事实；
- stale `revision` 被拒绝并可从最新 snapshot 重试；
- embodiment lease 冲突不会出现 UE 与 Paralls 双重写入世界状态，intent lease 与玩家控制交接不会双重驱动身体；
- full replay 与 checkpoint + tail replay 得到同一 handoff/receipt 结果；
- handoff 准备失败、原子提交前失败、提交后通知丢失，都能查询唯一结果并恢复；
- prewarm 不读取私有记忆；
- presentation-only 输出不写入世界事实；
- 玩家视野内 C3 Agent 的 `body_intent` 经 UE 映射后能驱动姿态/移动/动作动画，队伍循环动画不能覆盖个体意图；
- Agent intent 被碰撞/能力/路径约束拒绝或中断时，UE 返回原因，动画与实际行动保持一致；
- Agent 通道断开时不会继续播放新的伪自主动作；暂停时 Agent intent 与动画时钟同时冻结。

### 时停验证

- 暂停 10 秒期间 `world_tick`、Agent cadence、运输位置、动画时间、战斗和 handoff 状态均不变；
- 暂停中修改的命令在恢复后才出现新的 `received`/`accepted` 事件；
- 暂停前发出的异步 Agent 请求在旧 `control_epoch` 下不能提交动作/记忆/表现状态；
- 恢复后不重复发送暂停前已确认的事件。

### 可玩场景验证

1. 玩家靠近传令兵：P1/C1 -> P3/C3，身份、位置、当前命令和知识边界连续。
2. 玩家离开传令兵：P3/C3 -> P1/C1，未完成行动进入 `pending_merge`，不丢失。
3. 玩家阻挡粮车：路线事实、等待/改道动画和最终货运结果一致。
4. 粮车遭袭：Transport 记录运输损失过程，Inventory 提交货物增减；若对应 Owner 部署于 UE，本地可靠提交再同步 Paralls，受限 P0/P1 投影显示同一已确认库存结果。
5. 队长自主改变行动：地图、战报和角色解释引用同一 `action_ref`、`causation_id` 和 receipt。
6. 重要将领被击倒：Body/Status 和 LifeState 按各自写集确认身体变化与生命周期转换，Organization 按确认的失能事实处理继任；角色私有反馈按受限投影继续，不能由动画直接宣称死亡。
7. 玩家直接接管近场队长后松手：玩家 lease 释放、Agent 基于最新 revision 再决策、UE 动画重新服从新的 Agent 意图。

### 证据产物

- handoff 事件日志：`event_id`、`handoff_id`、旧/新 fidelity、lease epoch、revision；
- 近场 PIE 截图：传令兵、粮车、队长和重要将领各一张；
- 暂停前/暂停中/恢复后三段日志和世界 tick；

<a id="gate-4"></a>

## 阶段4：全量Owner Authority与跨域Workflow检查

**验收：** 每个 Owner 都能独立重建自己的 Runtime State，并至少执行一次成功、拒绝和恢复结算；部分完成、损失与补偿按领域适用性验证，不适用时明确拒绝，不制造假流程；任何跨域流程都能列出已提交 Owner、拒绝 Owner、当前 revision 和 recovery action；不得出现 UniversalOwner、Gateway 写领域事实或两个 Owner 写同一事实；第一阶段启用的召陵县数据能走完整链路，未启用的五阶段事实用正式 fixture 完成覆盖验证。
