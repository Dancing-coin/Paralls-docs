## 设计、实现和证据分开

设计合同写“要求/目标”；建设任务写“计划/待办”；真实实现状态必须有当前代码、测试、运行记录。设计案例的日志、时间、run_id和置信度均为示意，不能登记为执行证据。文档迁移校验只证明文档整理，不证明UE玩法完成。


<a id="source-demo-slice-evidence"></a>

### 12.5 每轮切片的完成证据

每个 V 切片必须单独保存：

- 一个可启动的 PIE/试玩入口和固定测试剧本；
- Command、Owner、revision、epoch、receipt 和事件流导出；
- 至少一条成功路径、一条拒绝/失败路径和一次暂停恢复记录；
- 三本账的关键投影、UE 截图、角色/群体激活记录和动画对齐证据；
- checkpoint/replay 对比结果；
- 当前硬件上的帧率、内存、显存、Actor 数量和加载时间。

任何切片没有这些证据，只能标记为“开发中”，不能标记为“完成”或作为下一切片的稳定基线。

<a id="source-demo-evidence-discipline"></a>

## 15. 运行证据和开发纪律

每一阶段都必须保存：

- 事件流和 receipt 导出；
- Owner、Command、revision、epoch 和 handoff 日志；
- 资源、Actor 数量、PIE 状态、帧率、内存和显存记录；
- 定向 UE 编辑器截图和 PIE 截图；
- replay/checkpoint 重建结果；
- 资源来源、许可证、面数/纹理预算和导入验证记录。

UE 操作遵守项目 `AGENTS.md`：不清空受保护关卡，不批量导入未经验证资源，只运行一个 UE 实例，内存不足时停止大型操作；任何“完成”结论都必须有日志、资产/Actor 数量、PIE 状态和截图证据。

## 14. 统一验收与停止扩张条件

| 门 | 必须取得的证据 |
|---|---|
| G1 合同门（A） | 23 Owner 与基础权威矩阵；schema/模型/Binding 样本验证；全量 UE 节奏/部署/提交图；ESM 合同与 Godot 执行器拆分、旧写权迁移表；环境来源无悬空项 |
| G2 内核门（B） | CAS、幂等、未知结果、暂停、checkpoint/replay、投影重建；V0 可启动 |
| G3 命令与连续性门（C） | 五类来源同路；传令成功/失败、旧命令与接管；三本账不泄漏；V1 可启动 |
| G4 实时门（D） | 本地提交崩溃恢复；并发体力、命中、治疗/LifeState、士气/Agent；延迟实测；V2 可启动 |
| G5 主线门（E） | 援军/敌退两条胜利，投降/死亡/逃跑三类失败；不强制出城；V3 可完成 |
| G6 全量 Owner 门（V4 结束前） | 23 Owner 完整包；资源社会链；未启用五阶段领域正式 fixture；跨阶段保存/回放一致 |
| G7 交付门（V5） | V0—V4 全回归、完整试玩、失败注入、稳定性/性能、证据包和已知问题 |

重点失败注入包括：提交前后崩溃、提交后回执丢失、Bridge 断线、投影落后、重复/乱序/旧 epoch 输入、模型输入过期、绑定冲突、暂停期间迟到回调、hand-off 中断、资源不足以及角色失能。

每个 V 切片保存固定场景/操作步骤、Command/事件/receipt 导出、三本账与激活记录、checkpoint/replay 差异、定向 PIE 截图、UE 日志、Actor 数量、帧率、加载时间、内存与显存。性能门限先登记再实测，不用未经测试的估计宣称达标。

如果出现双权威、确认事件丢失、恢复重复扣算、暂停继续推进、全知泄漏、模型跨域写入或 handoff 双跑，停止增加实体/资产/玩法，先修复基础设施并回归。基础设施未过门，不用内容脚本补洞。

## 记录格式与判定

每条真实记录填写：日期/操作者、代码与数据版本、合同/模型版本、硬件、入口/固定剧本、实际步骤、预期/实际、Command/事件/receipt关联、日志/截图相对路径、资源/Actor/PIE状态、帧率/加载/内存/显存、replay差异、结论、已知风险。结论只用“未执行/阻塞/通过/失败”；推断与观察分栏。

截图应来自CaptureEditorImage/Slate或实际PIE；不得以桌面截图冒充。预算先登记后测量；历史硬件数字不得充当永久保证。各切片至少成功、失败/拒绝、暂停恢复与回放；未提供证据不能标记完成。

县城用例和真实证据入口见[测试用例与证据索引](县城守城Demo/测试用例与证据索引.md)；资源来源/授权和可见验证沿用[README](../art_resources/README.md)。
