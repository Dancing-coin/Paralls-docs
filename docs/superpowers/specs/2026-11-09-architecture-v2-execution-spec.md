## 目的

把 v2 架构从设计文档转成带阶段门的实施项目：先降低运行时基础机制的重复，同时保持领域行为；随后证明新增事实类型和玩法组合可以通过声明与规则包完成。

这是面向县城守城 Demo 的架构建设，不重新定义 Demo 的玩家体验、范围、内容或验收标准。上述事项仍由 PRD 和现有生产计划维护。

## 成功标准

1. 抽取共享运行时机制期间，既有领域行为保持一致；以定向行为对照和相对基线无新增失败证明。
2. 可见性、三种时间轴、权威 epoch 栅栏均有可执行测试，并在读取和提交边界强制执行。
3. 首个域（2026-11-16 起为 credential，原为 Inventory）完成一条代表性的 L2–L5 路径：FactType 注册、规则包校验、Resolver 执行、Owner 授权提交、投影和回放。
4. 通过分水岭实验：新增至少一种 FactType 时，Owner 实现和 runtime 实现均零改动；只允许改规则包和注册数据。
5. UE 与 Agent 接入遵守同一权威契约，不能产生第二条事实写入路径。**（2026-11-17 起延期，随 G5 搁置；搁置期间 v2 是否成立只按第 1–4 条判断，第 5 条无证据，不得写成已满足。）**

Pool/Bond 原型通过不等于 v2 成功，只满足 [D1 原型记录](../../architecture-v2/09-验收/04-原型验证记录.md)中所记的原型级前置条件。

## 范围

包含：

- 实施批次开始前，对照当前 Paralls、代码、测试及 UE 接入情况核实 v2 契约。
- 建立可复现的测试基线和保持行为的迁移方法。
- 收敛共享 Owner runtime 机制，同时保留领域特有的校验、事件 schema、摘要语义和副作用。
- 强制可见性、event/known/presented 三种时间以及 authority epoch 栅栏。
- 完成一条 Inventory 参考链路，覆盖 FactType、Resolver、规则包和 play-pattern 组合。
- 分阶段执行分水岭实验并保存可复查证据。
- 让 UE/Agent 接入边界与 PRD、当前生产计划保持一致。

不包含：

- 重写所有玩法 runtime，或为了统一而把 native Owner 全部改成 stewarded Owner。
- 修改领域规则、产品行为、县城 Demo 范围、场景内容、美术资源、关卡或用户界面。
- 把所有已知基线失败都纳入本架构项目；缺陷修复另开任务，除非它阻塞某个明确阶段门。
- 仅凭单元测试或 D1 原型宣称性能、UE 接入、玩家体验或完整 v2 已验收。

## 约束

- 保持行为的迁移一次处理一个领域或可独立回退的工作单元。
- 每个实施批次开始前记录源代码提交、测试命令、测试范围、运行环境和失败集合。
- 验收按所记录基线比较：改动分支在相同测试范围内不得增加失败；已存在的失败必须单独保留，不能悄悄改称通过。
- 结构重构不得夹带语义缺陷修复。剩余的幂等回放事件引用校验属于独立缺陷轨道。
- L2 及以上实施前，须根据证据复核 D1 已通过。现有记录称原型已通过；只有在执行启动时无法核验原型产物或源版本才重跑。
- D2–D6 只在下一个阶段门确实依赖时解决；不得把未决项猜成正式运行行为。
- 本次文档整理不启动 UE、导入、构建或资产操作。后续 UE 操作遵守项目的资源、证据和单实例限制。

- 基线状态=通过 且 改动后状态=失败 → **新增失败（阻塞当前迁移）**

**基线复现协议：**
- 审阅者在相同环境（Docker 镜像或虚拟环境快照）运行
- 失败集合的测试名列表与顺序完全一致

### G2：L0 强制机制

实现并测试读取时的可见性强制、event/known 时间语义和提交时的 authority epoch 栅栏。共享接口和基线冻结后，各项机制可按依赖分别排程。2026-11-11 项目负责人决定：`presented_time` 已移出，不在 G2 验收内，移至 G5，需真实客户端表现层才能验证。

2026-11-10 已完成 synthetic visibility budget 测量并登记候选阈值；交错配对复跑出现一轮尾延迟超限、另一轮在阈值内，故当前只保留测量证据，暂停扩大读取范围。代码仓库的 `docs/verification/g2-visibility-budget/boundary-audit.md` 记录了真实调用者和实施前置；这不代表可见性、三时间或 epoch 已实现。

退出条件（2026-11-11 项目负责人澄清）：不要求全部读取路径改经 `read_as`。须形成面向主体的读取边界清单，每个调用点标注“可信权威/恢复”“面向主体”或“未判定”，未判定不得默认视为可信；可见性、`known_time`、authority epoch 各至少有一条端到端切片，在真实强制边界上有正向和反向用例。切片中旧 epoch 不能提交，未授权读取者无法取得受保护事实，回放与投影保留所需时间语义，并相较改动前路径完成性能测量。G2 通过只证明这些切片，不证明全部读取路径已强制；其余面向主体路径的接入是后续独立工作。缺证据或不匹配时使用明确错误码拒绝，不返回 `None` 或空集。

**2026-11-11 收口口径（项目负责人采纳）：** G2 以三条选定切片收口，每条只证明其所标范围：

1. **可见性：** 仅“已绑定发起者读取自己的 session 提案”。参与者、观察者、送达者受众未做；其他参与者路径阻塞于“两角色同一世界 tick 在场”的权威来源，尚无来源。
2. **known_time：** 社交送达的领域视图，以及 session 提案的写入侧记录。session 读取侧尚未对其他受众按 `known_time` 过滤。
3. **authority epoch：** 仅存储层栅栏（受保护流登记、同一数据库事务内校验、精确重试、旧数据兼容），默认不启用，当前没有任何生产流受保护。

在线交接、受理冻结、恢复证据、`pending`/`reconcile`/`activate`、双 writer 对账告警、可信 control head，以及首流 `population-cadence:<world_ref>` 的 publisher 接线，移出 G2，列为 B4 前置设计项；G2 不证明这些能力，也不证明备份新鲜度或 UE 本地权威。该收口使 epoch 切片的“真实强制边界”为存储层事务边界，而非生产写入路径。

**session 读取性能预算（2026-11-12 项目负责人采纳，候选，不是已批准的生产 SLO）：**
- 2026-11-12 两轮真实 WebSocket 正向读取在 4,096 事件单流下 p95 约 160 ms，超出原候选 40 ms，分类为“超出”，原样保留。读取成本约 98.7% 来自对整条 session 流的复制，而不是主体检查。
- 预算改按现实规模表述：session 流 ≤100 事件时正向读取 p95 < 40 ms；4,096 事件档只作扩展性检查，要求成本不再随无关事件线性增长，不作通过门槛。读取方式修正（只取首个 proposed 事件，代码仓库 `38e57119`）后，同一脚本一轮内存 Store 重测：100 事件 p95 0.50 ms，4,096 事件 p95 1.03 ms，主要成本已去除；但内存 Store 仍先线性筛选，成本随流长仍略有增长，不得写成“严格持平”。该结论仅为一轮内存 Store 数据，未覆盖 Durable SQLite、持久库竞争、远程身份或响应时序。
- 原“相对基线 p95 增量 ≤ 10%”不适用于本路径：没有完整旧服务器的可比基线，只有局部旧 handler 对照。
- 仍须记录：session 流事件数没有与参与者数量无关的固定上限（静态推导完整成功路径约 `2N+3`，N 为参与者数，尚未实测）。

仍开放：session 读取性能仅有一轮内存 Store 数据，未测 Durable SQLite 与持久库竞争；响应时序不可区分性未验证，远程身份接入前须复查；旧快照兼容样本为派生 fixture；Godot live probe 被拒绝且未运行；`presented_time` 属 G5。上述缺口须随 G2 记录一并呈现，不得以“切片通过”替代。

**G2 收口批准（2026-11-12，项目负责人）：** 批准三项：(1) 以三条选定切片收口；(2) 按上述候选性能预算接受现有测量，保留其限制；(3) 参与者/观察者/送达者 session 路径经 PRD 核查“未明确要求双角色 session 握手”，列为范围外的后续独立工作，若日后需要，须先有“两角色同一世界 tick 在场”的权威来源。**G2 通过不改变任何生产流的保护状态：** epoch 栅栏默认不启用，没有生产流受其保护；可见性强制仅覆盖已绑定发起者读取自己的 session 提案；其余面向主体读取路径（读取边界清单中 871 个“未判定”及面向主体的其他调用点）未接入。证据见代码仓库 `docs/verification/g2-closure-evidence/`（收口记录 `g2-closure-record.md`）。本批准基于项目报告与归档证据，不是独立评审或独立复现。

### G3：首个域 L2–L5 参考链路（credential）

**2026-11-16 项目负责人决定：** G3 首个域由 Inventory 改为 `credential`。原因：Inventory 被 9 个 Owner 读取，是回归面最大的枢纽，[Owner 重构影响评估](../../architecture-v2/08-迁移/05-Owner重构影响评估.md) §五 建议试点不先动枢纽；credential 为 269 行、3 种事件类型、3 个导入者，且已完成 replay 迁移。盘点依据见代码仓库分支 `codex/g0-b3-ingress-20261109` 在 `d6c30d58` 的 Owner 现状报告（仓库外，`D:\Temp\owner-inventory-20261112\report.md`）。

注册 credential FactType，并连接规则包校验、Resolver/模型注册、Owner 授权命令、投影和回放。样例范围以能贯通完整契约为准，不要求迁移所有领域。

**边界：** 本域事实为 issued / revoked / superseded。凭证有效性依赖 ownership 与 inventory 两个投影，这两项以只读 `reads` 声明进入依赖图，**不**注册为 credential 的 FactType，写主仍归各自 Owner。校验器对“读取未声明的事实”须拒绝。

**回放验收：** R1 幂等记录、digest、原 receipt（现状已有）；R2 receipt 的 `committed_event_ids` 全部可解析、事务一致、事件数匹配；R3 删除 checkpoint 后重建，`state_digest` 一致。R2 对 credential 是行为改变，必须单独成一个提交并写明，不与结构迁移混在同一提交。

**探针：** credential 链路冻结后，做一次“只加 FactType + 规则包”的新增，记录 diff；失败按[分水岭实验](../../architecture-v2/08-迁移/04-分水岭实验.md) §四归因。这取代原先“G4 全部通过才继续”的门，细则待首域完成后补入 G4。

退出条件：确定性 fixture 从注册走到回放；无效引用和非法写入均会被拒绝；R2、R3 有证据；证据明确列出所有改动的代码和数据文件。D2（严格）、D3（代码模型进同一注册表）、D4（拓扑生成 resolution_order）、D5（由项目负责人裁定）按 2026-11-16 批准的推荐执行，D9 按校验器规则关闭为“仅非运行态”。

**首域结论（2026-11-18，项目负责人接受，限定口径）：** credential 的 FactType 合并为单个 Machine `fact:credential:*:link`（状态集 absent / issued / revoked / superseded），写入走每实例一条流与 `holder` 流，旧 v1 事件原样保留，投影器双读。代码仓库分支 `codex/g0-b3-ingress-20261109`，最终提交 `49f52dd5`，设计与证据见该仓库 `docs/verification/g3-credential-design.md`。

- **可以宣称：** 在每实例一条流、v2 事件、停写栅栏激活的现状下，只改规则包新增一个凭证种类（`seal`），签发、重放、R2、吊销、R3 重建均走通，且 `backend/` 下代码改动为 0 行（探针在临时 worktree 完成，未作为提交保留，记录见设计文档）。写入侧准入由规则包声明驱动；读取侧不依赖当前规则包，已提交事件在任何规则包下都能被读出。land-right 对 `seal` 的业务拒绝是预期行为：凭证种类可扩展，不等于下游业务策略接受新种类。
- **探针发现的缺陷（过程证据，不是失败）：** 方案 B 之后，reference chain 的投影与重试检查、presentation 的集合传递、land-right 与 closure 的无参投影器，各有遗漏，均已修复；原先的 338 节点与定向集没有覆盖这些分支。该事实说明“全部现有测试通过”不能替代对下游消费者的专门核查。
- **语义变化须知：** 投影器读取侧不再校验 `credential_kind`、`proves` 是否属于当前集合，写入侧准入成为唯一防线。依据是回放用旧版本、不得用当前规则重新解释已提交历史。
- **不得宣称：** credential 已满足 v2；v2 的 Owner 迁移已验证；探针证明 v2 成立。
- **仍未验证：** 没有真实旧 credential 存档样本，v1 兼容只来自构造 fixture，不是历史数据证据；可见性强制未做，`role:credential_authority` 仅为占位声明；其他 Owner 未迁移。本节基于线程报告、提交范围与 diff 核对，未经独立复跑。

### G5：UE/Agent 接入与 Demo 对齐

**2026-11-17 项目负责人决定：G5 搁置。** 原因：G5 的前置是 UE 动作底座线（目前 UE 端零实现），与 G3/G4 及 Owner 迁移无依赖；Owner 迁移到 v2 不需要 G5。搁置的含义：
- 成功标准第 5 条延期，无证据；

- **B4 前置设计项（在线 handoff、受理冻结、恢复证据、首流 publisher 接线）不属于 G5，不随之搁置**，它是 epoch 栅栏保护生产流的前提；

- 恢复 G5 须项目负责人明确决定；以下原有条文保留，作为恢复时的依据。

## 风险与停止条件

- Pool/Bond 出现不一致或缺少不变量时，阻塞 L2 及以上工作，重新审视原语规格。
- 出现无法解释的行为变化或新增基线测试失败时，停止当前迁移单元。
- B0、司命或 Agent 的第二份状态无法与 Owner 事实对齐时，阻塞相应接入路径。
- 可见性强制超出已登记的延迟预算时，暂停扩大范围，先按 principal 测量并评估缓存。
- 分水岭实验需要修改 runtime 时，记录具体缺口；不得放宽零代码改动标准以宣告通过。
- v2 与当前 PRD/生产权威在产品行为上冲突时，记录冲突；权威来源未解决前，不实施该行为。
