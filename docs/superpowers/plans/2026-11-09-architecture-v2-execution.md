# Architecture v2 执行计划

> **执行提示：** 使用项目现有任务流程。一次执行一个有阶段门的任务；步骤用复选框追踪。G0 的有条件批准、G1 选定批次结果及当前 G2 工作状态见[阶段记录](../../architecture-v2/09-验收/G1-status-2026-11-10.md)；不能把一项阶段批准外推为全部领域迁移或 G2 已验收。

**目标：** 将 v2 架构转成有证据支撑的分阶段实施，在保持现有玩法行为的同时验证规则包组合判据。

**架构：** 先核对权威来源并建立精确基线，再按可回退单元迁移共享 runtime 机制、强制 L0 契约、贯通 Inventory 参考链路，最后运行分水岭实验。UE/Agent 接入作为独立阶段门，并与县城 Demo 验收对齐。

**技术栈：** 现有 Paralls 玩法 runtime 与测试、UE 5.8 项目及其 runtime 接入、v2 规则包/FactType/Resolver/证据契约。本计划不授权新增依赖。

**规格：** [`2026-11-09-architecture-v2-execution-spec.md`](../specs/2026-11-09-architecture-v2-execution-spec.md)

## 全局约束

- 结构迁移保持领域行为；不把缺陷修复混入重构批次。
- 每个改动测试范围都与同一已记录基线对照；不得产生新增失败。
- 一次迁移一个边界清楚且可独立回退的单元。
- 只有 L3 Owner 写事实；L4 规则包和 L5 玩法组合不得获得写权。
- 本架构计划不改变县城 Demo 范围、玩法需求、关卡或资产。
- UE 实施遵守 `AGENTS.md` 中的 UE 实例、内存/显存阈值、资产操作、证据和受保护文件要求。

## 审查重点

- 幂等回放遇到缺失或损坏的引用事件时必须拒绝，不能返回虚假成功；此项与保持行为的抽取分轨处理。
- 共享机制迁移后，各领域的摘要和幂等键变体仍保持原语义。
- handoff 后的旧 authority epoch 和旧 pinned revision 不能提交。
- 未获知或无权的 principal 不能通过直接读取、投影、回放或调试路径取得受保护事实。
- UE/Agent/B0/司命的重复状态不能成为第二权威或悄然偏离 Owner 事实。

    - “已知缺陷”类别中有”直接影响幂等/revision/投影”的项 → 先修复再启动 G1
    - “未知根因”类别必须归零，否则 G0 不通过
  - **分离修复轨道：** 已知缺陷修复不与架构迁移混合，独立分支和测试

**验证：** 审阅者可复现所记定向基线并看到相同失败集合；每条就绪度判断都链接到当前证据。

### 任务 2：强制 L0 可见性、时间和 epoch 契约

**文件：** 由任务 0 确认 EventStore、投影/读取、提交、回放和权威代码；契约见 `01-内核/02-可见性强制.md`、`03-权威栅栏与提交.md`、`04-三本账与投影.md`、`06-存档回放与恢复.md`。

**输入：** G0 基线和冻结接口；只有共享读写机制构成依赖时才依赖任务 1。

**产出：** 在选定的真实读取和提交强制边界执行约束，并为可见性、`known_time`、authority epoch 各至少一条端到端切片建立正向和反向测试。

**2026-11-11 项目负责人决策：** G2 不要求全部读取路径改经 `read_as`。先形成面向主体的读取边界清单，每个调用点标注“可信权威/恢复”“面向主体”或“未判定”，未判定不得默认视为可信。G2 通过只证明选定切片，不证明全部读取路径已强制；其余面向主体路径的接入是后续独立工作。缺证据或不匹配时使用明确错误码拒绝，不返回 `None` 或空集。`presented_time` 已移出，不在 G2 验收内，移至 G5，需真实客户端表现层才能验证。

- [ ] **步骤 1：盘点读取边界并编写可见性测试。** 按上述三类逐调用点记录；选定端到端切片覆盖允许/拒绝的 principal、secret 事实、未送达信息、debug-only 数据及投影/回放路径。缺证据或不匹配时使用明确错误码拒绝，不返回 `None` 或空集。
- [ ] **步骤 2：编写 event/known 时间测试。** 固定 `event_time`、`known_time` 在追加、延迟信息、投影、checkpoint 和回放中的行为；`known_time` 切片须有真实强制边界的正向和反向用例。`presented_time` 已移出，不在 G2 验收内。
- [ ] **步骤 3：编写 epoch 栅栏测试。** 范围按 2026-11-11 收口口径限定为存储层：登记的受保护流在同一数据库事务内校验 `(stream, scope, epoch, writer)`，旧 epoch 与缺失上下文原子拒绝，同键同 digest 的精确重试仍取回原 receipt，两个 Durable 实例共库时串行。在线 handoff、受理冻结、恢复证据、双 writer 对账和首流 publisher 接线属 B4 前置设计项，不在本步骤验收内；设计见代码仓库 `docs/verification/g2-visibility-budget/epoch-design.md`。
- [ ] **步骤 4：分别实现选定切片的强制边界。** 读取边界负责可见性强制，提交边界负责 epoch 校验。不得用 UI 过滤冒充机制强制；其余面向主体读取路径后续独立接入。
- [ ] **步骤 5：测量读取/提交开销。** 已用固定 synthetic fixture、G0 Python 3.12 环境记录读取环境与延迟分布；按技术负责人授权登记了暂定 10% p95 增量、4,096 事件低于 40 ms 的工程候选预算。历史运行包含超限样本；2026-11-11 在代码 HEAD `0b587890` 对 owner、authority、denied principal 的现有 Economy domain view 做两轮 60 样本交错测量，最高 p95 比例 1.028、4,096 事件最高 p95 为 24.49 ms。该样本未覆盖 session `read_as`、网络发送或持久库竞争，故会话可见性性能门仍开放。实际会话强制读取和提交开销尚未测量；完整数据与停止条件见代码仓库 `docs/verification/g2-session-visibility-denial/` 和 `docs/verification/g2-visibility-budget/`。
- [ ] **步骤 6：运行定向测试和基线对照。** 出现信息泄漏、旧 epoch 成功提交、回放不一致或新增基线失败时停止扩大范围。

**验证：** 可见性、`known_time`、authority epoch 各至少一条端到端切片在真实强制边界上的正反向契约测试通过、回放确定、旧提交被拒；扩大覆盖前须明确接受实测开销预算。G2 通过只证明这些切片，不证明全部读取路径已强制。

**收口口径（2026-11-11，项目负责人采纳）：** 可见性切片仅覆盖已绑定发起者读取自己的 session 提案；`known_time` 切片为社交送达领域视图及 session 提案写入侧记录；epoch 切片仅为默认不启用的存储层栅栏，无生产流受保护。记录必须同时写明未验证项：参与者/观察者/送达者路径、session 读取性能、响应时序、历史真实旧存档兼容（现有为派生 fixture）。

## 最终自检

- 规格覆盖：G0–G5 覆盖基线、共享机制、L0 契约、Inventory 组合、分水岭实验和运行时接入。
- 阶段顺序：G0 在实施前；G2 各项按实际依赖排程；实验遇首个前置失败即停止。
- 基线处理：实施任务均与同一测试集合对照，并单独保留历史失败。
- 审查重点：回放损坏、摘要/幂等键差异、旧 revision/epoch、可见性泄漏、第二真相风险都分配给对应任务。
- 范围：县城 Demo 内容和验收继续由现有生产与验证文档维护。
